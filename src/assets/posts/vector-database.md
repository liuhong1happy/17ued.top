向量数据库（Vector Database）是专为向量嵌入（Vector Embedding）设计的一类数据库：它索引并存储 embedding，提供快速的相似性检索能力，同时具备 CRUD、元数据过滤、水平扩展等我们熟悉的数据库特性。

为什么会需要这样一类数据库？因为我们正处在 AI 浪潮之中。大语言模型、生成式 AI、语义搜索这些应用都建立在 embedding 之上——它是一种携带语义信息的向量表示，是模型建立"理解"，以及维持一份可随时取用的"长期记忆"的基础。Embedding 由 AI 模型（例如大语言模型）生成，往往有成百上千个属性（维度），这些维度刻画了数据的不同侧面，是理解模式、关系与内在结构的关键。

问题在于，传统基于标量（scalar）的数据库——行、列、字符串、数字——无法应对这类数据的复杂度和规模，既难以提取洞察，也做不了实时分析。我们需要一类专门为这种数据类型而生的数据库：它既要有独立向量索引所缺失的传统数据库能力，又要有传统标量数据库所不具备的向量处理专长。

## 向量数据库的工作流程

一个典型的 RAG / 语义检索应用是这样串起来的：

1. 用嵌入模型为我们想要索引的内容生成向量
2. 向量写入数据库，同时保留一份指向原始内容的引用
3. 应用发起查询时，用**同一个**嵌入模型为查询生成向量，去库中检索相似的向量
4. 相似的向量关联回当初生成它们的原始内容，作为结果返回

![向量数据库在应用中的角色：内容与查询经嵌入模型转成向量写入数据库，查询结果返回应用](/images/blog/vector-database/what-is-vector-database.png)

借助向量数据库，我们可以给 AI 加上知识：语义检索、长期记忆等等。

## 与独立向量索引的区别

像 FAISS（Facebook AI Similarity Search）这样的独立向量索引，能显著提升向量的检索效率，但它缺少数据库应有的能力。向量数据库相比独立索引的优势：

| 能力 | 说明 |
| --- | --- |
| 数据管理 | 提供插入、删除、更新的易用接口；独立索引往往还需要额外对接一套存储方案 |
| 元数据存储与过滤 | 可为每个向量条目附带元数据，查询时用元数据做更细粒度的过滤 |
| 扩展性 | 面向数据量与请求量增长而设计，天然支持分布式与并行处理；独立索引想做到同等扩展性，通常要自己部署到 Kubernetes 之类的系统上 |
| 实时更新 | 支持数据的实时更新，新增数据立即可查；独立索引可能需要全量重建（re-index），代价高、耗时长 |
| 备份与集合 | 数据库负责日常的备份工作。以 Pinecone 为例，还可以选择性地把某个索引备份成 "collection"，日后用来填充新索引 |
| 生态集成 | 更容易接入 ETL 管道（如 Spark）、分析工具（如 Tableau、Segment）、可视化平台（如 Grafana），也便于对接 LangChain、LlamaIndex、Cohere 等 AI 工具链 |
| 安全与访问控制 | 内置的数据安全与访问控制机制；通过 namespace 实现多租户，可以在同一个索引内做出完全隔离的分区 |

## 向量数据库如何工作

传统数据库的查询通常是**精确匹配**——找出行里值等于查询条件的记录。向量数据库则不同：它施加一个**相似度度量**，找出与查询向量最相似的向量。

它的内部是一组算法的组合，共同服务于**近似最近邻（ANN）搜索**。这些算法或通过哈希、或通过量化、或通过图结构来加速搜索，并组装成一条流水线，为查询向量快速、准确地取回近邻。由于结果是近似的，核心权衡就在**精度与速度**之间：结果越精确，查询越慢。好消息是一套好的系统可以做到"极快的搜索 + 接近完美的精度"。

常见的流水线分三步：

![向量数据库流水线：索引（Indexing）→ 查询（Querying）→ 后处理（Post Processing）](/images/blog/vector-database/pipeline.png)

- **索引（Indexing）**：数据库用 PQ、LSH、HNSW 之类的算法为向量建立索引，把向量映射到便于快速检索的数据结构上
- **查询（Querying）**：把查询向量与库中已索引的向量逐一比较，用该索引所用的相似度度量找出最近邻
- **后处理（Post Processing）**：某些场景下，数据库会把取回的近邻再做一轮处理，比如换一种相似度度量做重排序（re-ranking），然后返回最终结果

## 索引算法

不同的算法都能用于构建向量索引，它们的共同目标是：构造一个能被快速遍历的数据结构，从而加速查询。为此，它们通常会把原始向量转换成某种压缩表示。

### 随机投影（Random Projection）

基本思路是用一个**随机投影矩阵**把高维向量投影到低维空间。我们生成一个随机数矩阵，矩阵的大小就是目标低维空间的维度，然后计算输入向量与矩阵的点积，得到一个维度更少但**相似性得以保留**的投影矩阵。

查询时用同一个投影矩阵把查询向量也投影到低维空间，再与库中已投影的向量比较，找出近邻。由于维度降低了，检索速度显著提升。

![随机投影：用随机投影矩阵把高维向量投影到低维空间](/images/blog/vector-database/random-projection.png)

需要注意随机投影是近似方法，投影质量取决于投影矩阵的性质。一般来说矩阵越随机，投影质量越好；但生成一个真正随机的投影矩阵在计算上是昂贵的，数据集越大越明显。

### 乘积量化（Product Quantization, PQ）

PQ 是一种面向高维向量的**有损压缩**技术。它把原始向量切成更小的片段，为每个片段构造一个代表性的"编码"来简化表示，再把片段拼回去——同时不丢失相似度计算所必需的信息。整个过程分四步：

1. **切分（Splitting）**：把向量切成若干段
2. **训练（Training）**：为每一段构建一个"码本"（codebook）。具体做法是对该段的向量做 k-means 聚类，用聚类中心构成码本；码本大小就等于 k-means 的 k 值
3. **编码（Encoding）**：为每个片段分配一个编码。训练完成后，找到与片段最接近的码本值，该值在码本中的标识就是这段的 PQ 编码。每段可以使用多个 PQ 编码
4. **查询（Querying）**：把查询向量也切段、用同一个码本量化，再用索引中的编码找出离查询向量最近的向量

![乘积量化：把向量切分成子向量，各自用码本中的编码表示](/images/blog/vector-database/product-quantization.png)

码本中代表向量的数量，是**表示精度**与**计算开销**之间的权衡：代表向量越多，子空间内的表示越准确，但检索码本的开销越大；越少则相反。

### 局部敏感哈希（Locality-Sensitive Hashing, LSH）

LSH 是为近似最近邻检索而生的索引技术，优先保证速度，返回的是近似的、非穷尽的结果。它用一组哈希函数把相似的向量映射进同一个"桶"：

![局部敏感哈希：相似的向量经哈希函数落入同一个桶](/images/blog/vector-database/lsh.png)

查询时，用与建桶相同的哈希函数把查询向量哈希到某张哈希表，然后只在该表内与其他向量比较，找出最近的匹配。因为单张哈希表内的向量数远少于整个空间，这种方法比全量扫描快得多。

同样地，LSH 是近似方法，近似质量取决于哈希函数的性质。哈希函数越多，近似质量越好，但计算开销也越大，大规模数据集上未必可行。

### 分层可导航小世界（HNSW）

HNSW 构建的是一个分层的、类树的结构：树的每个节点代表一组向量，节点之间的边代表向量之间的相似性。

算法先创建一批节点，每个节点持有少量向量——可以随机划分，也可以用 k-means 之类的聚类算法，让每个簇成为一个节点。然后算法考察各节点的向量，在相似度最高的节点之间连边。

查询 HNSW 索引时，它沿着这张图在树中导航，优先访问最可能包含查询向量近邻的节点。

![HNSW：每个节点持有一组向量，先在相似度最高的节点之间连边](/images/blog/vector-database/hnsw.png)
![HNSW：连边后的图结构，查询时沿图在层级间导航](/images/blog/vector-database/hnsw-2.png)

## 相似度度量

相似度度量是向量数据库比较向量、判断结果相关性的基础。它是一套数学方法，用来衡量向量空间中两个向量的相似程度。常见的有三种：

| 度量 | 含义 | 取值范围与解读 |
| --- | --- | --- |
| 余弦相似度（Cosine Similarity） | 两个向量夹角的余弦值 | -1 ～ 1：1 表示方向完全一致，0 表示正交，-1 表示方向完全相反 |
| 欧氏距离（Euclidean Distance） | 两个向量之间的直线距离 | 0 ～ ∞：0 表示完全相同，值越大越不相似 |
| 点积（Dot Product） | 两个向量的模长与夹角余弦的乘积 | -∞ ～ ∞：正值表示方向大体一致，0 表示正交，负值表示方向相反 |

选择哪种度量会直接影响检索结果。每种度量各有优劣，要结合具体场景和需求来定。

## 元数据过滤

数据库中的每个向量都可以带上元数据。除了按相似度检索，向量数据库还能基于元数据查询来过滤结果。

![后置过滤与前置过滤：元数据过滤发生在向量检索之后或之前](/images/blog/vector-database/filtering.png)

实现方式通常是维护**两个索引**：一个向量索引、一个元数据索引，然后在向量检索之前或之后执行元数据过滤——两种方式都有各自的代价，都会拖慢查询：

- **前置过滤（Pre-filtering）**：先按元数据过滤，再做向量检索。好处是缩小了检索空间；风险是可能漏掉那些本不匹配元数据条件、但实际上相关的结果，而且大范围的元数据过滤会因为额外的计算开销拖慢查询
- **后置过滤（Post-filtering）**：先做向量检索，再按元数据过滤。好处是能确保所有相关结果都被纳入考虑；代价是检索完成后还要筛掉不相关的结果，同样带来额外开销

为优化过滤过程，向量数据库会采用各种手段，比如为元数据建立更高级的索引、或者用并行处理加速过滤。在检索性能与过滤准确度之间取得平衡，是提供高效、相关查询结果的关键。

## 数据库层面的能力

与单纯的向量索引不同，向量数据库配备了一整套面向大规模生产环境的能力。

![数据库运维组件总览：分片、副本、scatter-gather、监控、备份、集合、访问控制与 SDK](/images/blog/vector-database/db-operations.png)

### 性能与容错

性能与容错紧密相关：数据越多，需要的节点越多，出错和故障的概率也越大。我们既要保证查询尽可能快，又要在部分底层节点失效时（硬件故障、网络故障或其他技术缺陷）依然可用——这类故障可能导致服务不可用，甚至返回错误结果。

为此，向量数据库使用**分片**与**副本**：

- **分片（Sharding）**：把数据切分到多个节点上。切分方式有多种，例如按数据簇的相似性切分，让相似的向量落在同一个分区。查询时请求发往所有分片，结果取回后再合并——这就是 **scatter-gather** 模式
- **副本（Replication）**：在不同节点上保存数据的多份拷贝。这样即便某个节点挂了，其他节点也能顶上。副本涉及两种主要的**一致性模型**：
  - **最终一致性**：允许不同副本之间短暂不一致，换来更好的可用性和更低的延迟，但可能产生冲突甚至数据丢失
  - **强一致性**：写操作必须等所有副本都更新完成才算成功，一致性更强，但延迟更高

### 监控

要管好一个向量数据库，需要一套健壮的监控系统，持续跟踪性能、健康度和整体状态。监控是发现隐患、优化性能、保障生产平稳运行的关键。需要关注的方面包括：

- **资源使用**：CPU、内存、磁盘空间、网络活动，据此识别可能影响性能的瓶颈
- **查询性能**：查询延迟、吞吐量、错误率，它们往往指向需要处理的系统性问题
- **系统健康**：单个节点的状态、副本同步过程以及其他关键组件

### 访问控制

访问控制负责管理和约束用户对数据与资源的访问，是数据安全的重要一环，确保只有被授权的用户才能查看、修改或操作库中的敏感数据。它的意义体现在几个方面：

- **数据保护**：AI 应用常常涉及敏感、机密信息，严格的访问控制机制可以防止未授权访问和数据泄露
- **合规**：医疗、金融等行业受严格的数据隐私法规约束，做好访问控制才能满足合规要求，避免法律和财务风险
- **可追责与审计**：访问控制机制会留下用户操作记录，既可用于审计，也能在安全事件发生后追溯未授权的访问或篡改
- **可扩展与灵活性**：组织发展过程中权限需求会变化，一套好的访问控制体系能平滑地调整和扩展用户权限

### 备份与集合

兜底手段是备份。备份可以存放在外部存储或云存储上，保证数据的安全与可恢复性；一旦发生数据丢失或损坏，可以用备份把数据库恢复到之前的状态，把停机时间和影响降到最低。以 Pinecone 为例，用户还可以只备份特定索引，保存为 "collection"，后续用来填充新的索引。

### API 与 SDK

这是真正落地的地方。开发者希望用趁手的工具集、通过易用的 API 来操作数据库。友好的 API 层让构建高性能向量检索应用这件事变得简单。

除了 API，向量数据库通常还会提供按编程语言封装的 SDK。SDK 让开发者能更轻松地在应用中访问数据库，从而把精力集中在自己的业务场景上——语义文本搜索、生成式问答、混合检索、图像相似性搜索、商品推荐——而不必操心底层基础设施的复杂度。

## 无服务器向量数据库

前面描述的架构能带来精确、快速、可扩展的向量数据库，但**成本高昂**——这是第一代向量数据库的形态。随着 AI 场景对成本和弹性的要求越来越高，第二代无服务器（serverless）向量数据库应运而生。

第一代向量数据库有三个关键痛点：

- **存储与计算分离**：为了优化成本，计算只应在需要时使用。这意味着索引存储要与查询、检索解耦，且只能检索需要检索的部分——在还要兼顾延迟的前提下，这件事很难
- **多租户**：需要在索引内处理 namespace，确保不常被查询的 namespace 不产生额外成本
- **新鲜度（Freshness）**：数据库要能提供新鲜数据，即新数据写入后几秒内即可被查询到。需要注意的是，大批量写入时，Pinecone Serverless 的新鲜度可能会延迟

为了解决存储与计算分离的问题，可以用相当复杂的**几何分区**算法把一个索引拆成若干子索引，让检索聚焦到特定分区：

![几何分区：把搜索空间划成若干区域，每次查询只落在少数几个分区里](/images/blog/vector-database/geometric-partitioning.png)

有了分区，一次查询的检索空间就从整个索引收敛到少数几个分区。典型的检索行为会显示某些分区的访问频率明显高于其他分区，据此可以在计算成本与冷启动时间之间调到一个成本与延迟的最优平衡点。

分区解决了存储与计算的分离问题，但几何分区在**索引构建期**是个较慢的过程——新数据必须等被正确写入索引后才能检索，这就带来了新鲜度问题。

为此需要另加一层**新鲜度层（Freshness Layer）**：它充当向量的临时"缓存"，可以立即被查询；同时索引构建器在后台把新向量放进几何分区索引中。

![新鲜度层：查询同时发往新鲜度层与已分区的索引，结果合并返回](/images/blog/vector-database/freshness-layer.png)

这样一来：

- 查询路由器把查询同时发往**索引**和**新鲜度层**，新鲜度问题得以解决
- 新鲜度层跑在计算实例上，容量有限，无法存放完整索引，只等新向量写入索引后就被移出

最后是多租户问题。很多第一代向量数据库早已支持多租户，但在无服务器架构下它更复杂：必须避免把不同类型的用户混部在同一批硬件上，否则成本和延迟都会被拖累。想象用户 A 几乎每天每秒 20 次查询，而用户 B 一个月才 20 次查询，如果两者混部，用户 B 就得为满足用户 A 的低延迟而 24 小时占用着计算硬件。

解决思路是：识别使用模式相近的用户，把他们**共置（colocate）**在一起，同时保持彼此之间的完全隔离。这可以基于用户的使用指标来完成，并根据使用情况自动分配冷热基础设施。

第一代向量数据库 + 存储与计算分离 + 多租户 + 新鲜度，就构成了新一代的现代向量数据库。这套架构配合向量数据库的基本功，是当前 AI 技术栈的优先选择。

## 总结

NLP、计算机视觉以及其他 AI 领域里向量嵌入的爆发式增长，使向量数据库成为我们在应用中有效地与 embedding 交互的计算引擎。

向量数据库是**专用数据库**，专门解决生产环境中管理向量嵌入时遇到的问题。正因如此，相比传统标量数据库和独立向量索引，它有明显的优势。

本文梳理了向量数据库的关键方面：它如何工作、用到哪些算法，以及让它具备生产可用性的那些数据库能力。
