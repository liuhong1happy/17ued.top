做语音相关的产品，绕不开一个现实：**国内开源语音模型的迭代速度，已经快过了任何人写文档的速度**。CosyVoice、FunASR、SenseVoice、GPT-SoVITS、sherpa-onnx 这些名字每隔几个月就会换一版，社区里每天都在产生新的对比和使用心得。

这篇文章不去追最新的榜单，而是做一件更有长期价值的事：**把这条技术链路拆开，说清楚每一环在解决什么问题、有哪些主流的开源实现、它们各自适合什么场景**。名字和版本会变，但分层的结构和选型的判断依据相对稳定。

范围聚焦国内开源生态（阿里系、B站、小红书、清华系、社区项目），也会提到 Whisper 这条国际基线作为参照。

![语音交互的两条路线：级联式的 VAD、ASR、轮次检测、LLM、TTS 流水线，与端到端的语音 Tokenizer、语音大模型、解码器](/images/blog/opensource-tts-asr/speech-pipeline.svg)

# 一、先建立坐标系

## 1.1 语音链路的五个环节

一个能"听懂并回答"的语音系统，最小的环节划分是这样的：

| 环节 | 作用 | 关键技术点 | 国内代表 |
| --- | --- | --- | --- |
| VAD | 判断"人是不是在说话"，切出有效音频 | 端点检测，抗噪声 | FSMN-VAD（FunASR）、Silero VAD |
| ASR | 语音转文字 | 流式 / 非流式、热词、时间戳 | FunASR、SenseVoice、Paraformer |
| 轮次检测 | 判断"用户说完了没有" | 语义断句，比静音检测准得多 | 各家的语义 VAD 模型 |
| LLM | 理解与生成回复 | 首 token 延迟决定体验 | 通用大模型 |
| TTS | 文字转语音 | 音色克隆、流式、情感控制 | CosyVoice、GPT-SoVITS |

**有两个环节最容易被低估，但它们对体验的影响最大**：

- **VAD 的准确率直接决定误唤醒和截断**。切早了，用户话没说完就被打断；切晚了，系统反应迟钝。很多"这个语音助手不好用"的问题，根因在 VAD 而不是 ASR。
- **轮次检测比 VAD 更关键**。用户说"帮我查一下……嗯……明天的天气"，中间那个"嗯"的停顿，静音检测会误判成说完了。用语义模型判断"这句话说完整了吗"，是这一两年体验提升的主要来源。

## 1.2 两条路线：级联 vs 端到端

| 维度 | 级联式（ASR + LLM + TTS） | 端到端（语音大模型） |
| --- | --- | --- |
| 链路长度 | 长，每一环可独立替换 | 短，整体一个模型 |
| 信息损失 | 文字是有损压缩，韵律情绪丢失 | 保留副语言信息 |
| 延迟 | 相对高（各环节累加） | 可以很低，支持全双工 |
| 可控性 | 高，能插工具调用、知识库 | 低，黑盒 |
| 可观测性 | 好，每一步都有中间结果 | 差，出问题难定位 |
| 换组件的代价 | 低，换 ASR 不动 TTS | 高，可能要重训 |
| 工程成熟度 | 成熟，生产系统主流 | 快速演进中 |

**工程上的现实答案通常是折中**：级联式作为主干（因为要接知识库、调工具、走业务流程），在关键环节用大模型增强——比如用语义模型做轮次检测，用大模型 TTS 做情感化播报。

端到端适合的是另一类场景：**拟人化闲聊、情绪陪伴、需要极低延迟的全双工对话**。这类场景不需要精确的工具调用，情感表达和自然度权重更高。

下面的内容按这条链路展开：先讲 ASR，再讲 TTS，然后是端到端模型，最后落到部署。

# 二、ASR：语音识别

## 2.1 先分清工具链和模型

这是理解 ASR 生态最关键的一点：**工具链和模型是两层，混在一起谈就会很乱**。

- **工具链**解决"怎么用"：怎么加载模型、怎么串流水线、怎么部署成服务
- **模型**解决"准不准"：识别精度、语言覆盖、延迟

同一个模型（比如 SenseVoice）可以被不同的工具链加载；同一个工具链（比如 FunASR）也能加载不同来源的模型。

![国内开源 ASR 生态：左列是工具链框架 FunASR、sherpa-onnx、WeNet、PaddleSpeech，右列是模型谱系，底部是选型提示](/images/blog/opensource-tts-asr/asr-landscape.svg)

### 工具链

| 工具链 | 出品 | 特点 | 协议 |
| --- | --- | --- | --- |
| **FunASR** | 阿里达摩院 | 统一 `AutoModel` 接口，把 VAD、ASR、标点、说话人分离串成流水线；支持 Docker 服务化，流式与离线一套接口 | MIT |
| **sherpa-onnx** | k2-fsa 社区 | 基于 ONNX Runtime，**纯离线、无 Python 依赖**，12 种语言绑定；端侧部署的事实标准 | Apache-2.0 |
| **WeNet** | 出门问问 + 西工大 | U2/U2++ 把流式与非流式统一在一个模型里；工业级训练框架 | Apache-2.0 |
| **PaddleSpeech** | 百度 | ASR / TTS / 声纹一体化，中文文档完整 | Apache-2.0 |
| **Whisper / whisper.cpp** | OpenAI / 社区 | 多语种基线，中文需配 VAD 分段 | MIT |

**FunASR 的价值在于"统一接口"**：它把一条完整语音处理链路抽象成 `AutoModel` + `pipeline`，VAD、ASR、标点恢复、说话人分离、情感识别都可以按名字组合，几行代码就能跑起来一条离线转写流水线。

**sherpa-onnx 的价值在于"能装到任何地方"**：它把模型转成 ONNX，用 ONNX Runtime 推理，因此能吃下 x86、ARM、RISC-V，能跑在 Android、iOS、开源鸿蒙、openKylin 上，也能装到树莓派、RK3588、RV1126、Jetson 这些板子上。

**一个容易被忽略的技术细节**：ONNX Runtime 支持把算子卸载到厂商的 NPU 执行提供者（Execution Provider），比如高通的 QNN、瑞芯微的 RK NPU、昇腾 NPU。这是纯 ggml 路线（whisper.cpp 那一类）做不到的——**如果你要跑在高通或瑞芯微的板子上，这个差异是决定性的**。

### 模型

阿里系（通义实验室 / 达摩院）是国内开源 ASR 的主力：

| 模型 | 定位 | 特点 |
| --- | --- | --- |
| **Paraformer** | 通用中文 | 非自回归（NAR）单步解码，比自回归快约一个量级；支持时间戳和热词，有流式版本 |
| **SenseVoice-Small** | 端侧 / 低延迟 | 中英日韩粤，**同时输出情感识别与音频事件检测**；延迟极低，量化后体积小，是端侧最常被选中的档位 |
| **Fun-ASR-Nano / MLT-Nano** | 高精度 / 多语言 | SenseVoice 编码器 + Qwen 系解码器的 LLM-ASR 路线，覆盖更多方言与口音；MLT 版面向多语言 |

其他值得关注的国内模型：

- **FireRedASR**（小红书）：公开评测中在中文标准测试集上 CER 表现突出。
- **Dolphin**（DataoceanAI + 清华）：面向东方语言，覆盖小语种与方言。
- **TeleSpeech-CTC**（TeleAI）：运营商场景积累，中文与方言覆盖广。
- **Zipformer / Conformer** 系（k2 生态）：流式骨干，sherpa-onnx 的主力模型。

## 2.2 FunASR 快速上手

FunASR 最实用的部分是它把链路封装得足够简单：

```python
from funasr import AutoModel

# 一条流水线：VAD 切分 + ASR 识别 + 标点恢复
model = AutoModel(
    model="paraformer-zh",
    vad_model="fsmn-vad",
    punc_model="ct-punc",
    # spk_model="cam++",       # 需要说话人分离时打开
)

res = model.generate(
    input="meeting.wav",
    batch_size_s=300,          # 按秒数分批发，长音频友好
    hotword="开源语音 向量检索",  # 热词，提升专有名词识别率
)
print(res[0]["text"])
```

**热词（hotword）是中文 ASR 落地最实用的功能**。业务里有大量专有名词（产品名、人名、行业术语），通用模型必然识别错，而热词可以在**不改模型**的前提下显著提升这些词的识别率。这比为了几个专有名词去微调模型划算得多。

**SenseVoice 走的是另一条路径**——它不只输出文字，还输出情感和事件：

```python
from funasr import AutoModel

model = AutoModel(model="iic/SenseVoiceSmall", trust_remote_code=True)
res = model.generate(input="audio.wav", language="auto", use_itn=True)
# 输出带富文本标签：<|zh|><|HAPPY|><|Speech|><|woitn|>识别到的文字
```

这几个标签分别是：语种、情感、音频事件（是否有人声、音乐、掌声等）、是否做过逆文本正则化。**情感和事件标签是"白送"的额外信号**——可以用来做客服质检里的话术情绪分析，或者判断一段录音里有没有有效人声。

## 2.3 流式与离线

| | 流式（Streaming） | 离线（Offline / 非流式） |
| --- | --- | --- |
| 输出时机 | 边说边出字 | 整段音频处理完再出 |
| 延迟 | 低，适合实时交互 | 高，但精度通常更好 |
| 模型 | `paraformer-streaming` 等 | `paraformer-zh`、SenseVoice |
| 典型场景 | 实时字幕、语音助手 | 录音转写、会议纪要 |

**不要指望流式模型达到离线模型的精度**。流式模型必须在看不到后文的情况下做决定，这是信息量的硬约束。常见的工程做法是**双路**：流式用于实时反馈（把字显示出来给用户看），离线用于最终结果（存库、做分析）。

## 2.4 ASR 选型速查

| 你的约束 | 推荐 |
| --- | --- |
| 服务端，要精度、要多语言方言 | Fun-ASR-Nano 一类 LLM-ASR |
| 端侧 / 嵌入式，要快、要省 | SenseVoice（量化后纯 CPU 可跑） |
| 纯中文 + 要时间戳 / 热词 | Paraformer |
| 要跨平台装到手机 / 开发板 | sherpa-onnx 路线 |
| 要一条流水线搞定转写（含标点、说话人） | FunASR |
| 通用离线多语种基线 | Whisper large-v3 / turbo，但中文通常不如上面几档 |

# 三、TTS：语音合成

## 3.1 三个代际

TTS 这几年的变化比 ASR 剧烈得多。理解代际差异，比记住模型名字重要。

![语音合成技术代际演进：拼接与参数合成、神经声学模型、大模型零样本克隆三个阶段](/images/blog/opensource-tts-asr/tts-generations.svg)

**核心转变是**：从"训练一个声音"变成"描述一个声音"。

- **第一代（拼接 / 参数合成）**：从录音库里挑音素片段拼接，或建模声学参数再合成。换音色要重新录数据。
- **第二代（神经声学模型）**：Tacotron、FastSpeech、VITS、HiFi-GAN。端到端从文本学出波形，音质大幅提升，但**要得到一个特定音色，仍然需要几百句录音去微调**。
- **第三代（大模型零样本克隆）**：把语音当成 token 序列，用 LLM 的架构去做"续写"。**给一段 3~10 秒的参考音频，推理时就能克隆出这个音色，不需要训练**。这是质变。

三代之间的差距，可以归纳成五个维度：

| 维度 | 第一代 | 第二代 | 第三代 |
| --- | --- | --- | --- |
| 数据要求 | 数小时录音底库 | 数小时精标数据 | **3~10 秒参考音频** |
| 换音色代价 | 重录重训 | 微调数小时 | **推理时给参考音频** |
| 控制维度 | 只能控制说什么 | 语速、音高 | **自然语言指令控制情绪、方言、风格** |
| 架构 | 声学模型 + 声码器 | 端到端 | **语音 token + LLM + 流式解码** |
| 延迟 | 离线合成 | 数百毫秒 | **首包 150ms 级别** |

## 3.2 CosyVoice：阿里系的代表

**CosyVoice** 由阿里巴巴通义实验室语音团队开源（仓库 `FunAudioLLM/CosyVoice`），是目前国内讨论度最高的大模型 TTS 之一。CosyVoice 2 在 2024 年底发布，是这条线上被引用最多的一版。

它的技术要点值得单独讲，因为它是"第三代 TTS"的典型结构：

| 组成部分 | 做法 | 意义 |
| --- | --- | --- |
| LLM backbone | 用 Qwen2.5-0.5B 这类小 LLM 替换传统的文本编码器 + Transformer | 把 TTS 变成"文本 token → 语音 token"的生成任务 |
| 语音 token 量化 | 用 FSQ（有限标量量化）替换 VQ | 码本从 4096 扩到 6561 且几乎全部激活，表达能力更强 |
| 流式建模 | 离线与流式一体化建模 | 首包延迟做到 **150ms 级别**，可双向流式 |
| 指令控制 | 自然语言指令控制 | 支持粤语、四川话、天津话等方言，以及角色扮演式的风格控制 |

**为什么"流式 + 低延迟"对语音助手是决定性的**：用户说完话到听到第一个字，间隔超过 500ms 就会感觉"卡"。TTS 的首包延迟直接落在这个体感区间里。而传统的"等整句合成完再播"根本达不到这个要求，必须边生成边播。

**关于版本**：CosyVoice 迭代很快，2.0 之后社区也有更新的版本讨论。**具体版本号和能力边界请以官方仓库和 ModelScope 模型页为准**——这类项目的 README 更新频率远高于任何第三方文章。

| 项目 | 出品 | 特点 | 协议注意 |
| --- | --- | --- | --- |
| **GPT-SoVITS** | 社区（RVC-Boss） | 少样本克隆的口碑之选：几秒音频零样本，1 分钟数据可微调；中文社区生态极强 | MIT，商用友好 |
| **Fish Speech** | Fish Audio | 情感标签内联控制强，多语言覆盖广 | 自定义研究协议，**商用需确认授权** |
| **IndexTTS / IndexTTS2** | B 站 IndexTeam | 工业级零样本，情感与音色解耦，中文表现突出 | Apache-2.0 |
| **ChatTTS** | 社区 | 对话场景优化，韵律自然，曾引发广泛关注 | 需确认 AGPL / 商用条款 |
| **F5-TTS** | 社区 | Flow Matching 架构，克隆效果好 | 需确认 |

# 四、端到端语音大模型

第三条路是把整条链路合成一个模型：**语音进、语音出**。

## 4.1 架构共性

尽管实现各异，端到端模型的结构是统一的：

```text
音频 → Speech Tokenizer → 语音 LLM（直接生成语音 token）→ Detokenizer → 波形
```

三个关键组件：

1. **Speech Tokenizer**：把连续音频压成离散 token。分语义 token（偏内容）和声学 token（偏音色音质），也有统一的。常用做法是在 Whisper 编码器或 VQ 基础上改造。
2. **语音 LLM**：就是在文本 LLM 上扩展词表，把语音 token 当成一种"语言"来生成。
3. **Detokenizer**：把 token 还原成波形，主流用 Flow Matching + 声码器。

## 4.2 国内主要项目

| 项目 | 出品 | 特点 |
| --- | --- | --- |
| **GLM-4-Voice** | 智谱 / 清华系 | 每秒音频仅需约 12.5 个离散 token，token 效率高；支持中英语音交互 |
| **Step-Audio / Step-Audio 2** | 阶跃星辰 | 全双工实时交互，双码本语音 tokenizer；2 代主打副语言理解（音色、音高、节奏、语速、风格等维度） |
| **Qwen-Omni（Qwen3-Omni）** | 阿里通义 | 多模态感知（文本 / 图像 / 音频 / 视频），综合能力均衡，中英混说场景表现好 |
| **Kimi-Audio** | 月之暗面 | 音频理解与生成统一 |
| **MiniCPM-o** | 面壁智能 | 端侧多模态，语音能力集成在小参数模型上 |
| **Freeze-Omni** | 清华系 | 冻结 LLM 主干、只训适配层，训练成本低 |

**端到端模型的核心卖点是"全双工"**：可以边听边说、可以在用户插话时自然停顿，这是级联式很难做到的——级联式必须在"听完 → 识别 → 生成 → 合成"之间串行推进，天然无法同时进行。

**但它的短板也很实在**：工具调用、知识库检索、业务流程编排这些让语音助手"有用"的能力，端到端模型目前都不如级联式灵活。所以你会看到一个有意思的现象——**很多产品用端到端模型做"门面"（闲聊、情绪陪伴），用级联式做"里子"（办事）**。

# 五、工程落地：从模型到服务

## 5.1 三种部署形态

![开源语音模型的三种部署形态：PyTorch 原生服务、ONNX Runtime 端侧推理、GGUF 单二进制，以及各自适配的目标平台](/images/blog/opensource-tts-asr/deployment-forms.svg)

| 形态 | 依赖 | 体积 | 平台 | 适用 |
| --- | --- | --- | --- | --- |
| **PyTorch 原生** | Python + GPU + CUDA | 数百 MB ~ 数 GB | 服务器 / 云 GPU | 追求精度的服务端 |
| **ONNX Runtime** | onnxruntime（可无 Python） | INT8 量化后约 200~300MB | x86 / ARM / RISC-V / Android / iOS / 鸿蒙 | 端侧与嵌入式 |
| **GGUF** | 无（单文件） | 量化后约 250MB 级 | x86 / ARM CPU | 不想碰深度学习环境的最简部署 |

**选型时先问"跑在哪"，再问"哪个模型准"**。顺序反了会白折腾——一个在服务器上效果惊艳的模型，可能根本装不进你的嵌入式板子。

## 5.2 一个参考架构：小智

**xiaozhi-esp32** 这条开源链路（ESP32 固件 + 自建后端）是国内语音助手落地最完整的公开参考，值得研究它的分层：

```text
ESP32 设备（麦克风 + 扬声器 + 唤醒词）
        ↓ WebSocket / MQTT+UDP，Opus 帧
后端服务
        ├─ VAD + ASR        →  FunASR（本地）或云端 ASR
        ├─ LLM              →  通用大模型
        └─ TTS              →  CosyVoice / 云端 TTS
```

它的后端把 ASR、LLM、TTS 都抽象成**可插拔的 provider**，通过配置切换本地或云端实现。这个设计很有参考价值：**本地实现（FunASR / sherpa-onnx）保住了隐私和成本，云端实现保住了精度，配置化让两者可以混用**。

它还有一个细节值得注意：设备端只做**唤醒词 + 音频前端**（采集、编码、播放），真正的 VAD、ASR、LLM、TTS 全在服务端或局域网内的另一台机器上。**ESP32 的算力根本跑不动这些模型**——很多人在选型时会低估这一点。

## 5.3 实时性的三个指标

做实时语音交互，必须盯住这三个数：

| 指标 | 含义 | 目标 |
| --- | --- | --- |
| **首包延迟** | 从收到请求到吐出第一段音频 | TTS 越低越好，150ms 级别是优秀 |
| **端到端延迟** | 用户说完 → 听到第一个字 | 500ms 以内体感流畅，超过 1s 明显卡顿 |
| **RTF**（实时因子） | 处理时长 / 音频时长 | < 1 才能实时，越小越有余量 |

**端到端延迟是各环节之和**，所以要优化就得找最大头。常见情况是：ASR 很快（几十毫秒）、LLM 首 token 慢（几百毫秒）、TTS 首包中等（一两百毫秒）——**瓶颈通常在 LLM**，而不是语音模型。

**一个实用的优化**：TTS 不必等 LLM 说完。LLM 一边生成文字，TTS 一边按标点断句合成播放（流式管道），能把端到端延迟砍掉一大截。

## 5.4 并发与资源

- **GPU 显存是硬约束**：ASR + TTS + LLM 三个模型同时驻留，显存可能比你以为的高得多。要么量化，要么把不常用的模型做懒加载。
- **批处理能提高吞吐但会牺牲延迟**：服务端可以攒一小批请求一起推理（dynamic batching），代价是最早到的那个请求要等。实时语音交互对延迟敏感，批处理窗口要设得很小。
- **CPU 也能跑，但要选对模型**：量化后的 SenseVoice 这类小模型在纯 CPU 上可跑，而大模型 TTS 在 CPU 上基本不现实。

## 5.5 和 LiveKit 结合

前面讲的都是"模型"，而**把模型组织成一次可用的实时对话，需要一层会话编排**——管音频轨道、管打断、管轮次、管并发。这正是 LiveKit Agents 在做的事，细节见另一篇《LiveKit：为开发者打造的实时音视频与数据通信能力》里的 Agent 章节。

需要知道的关键一点：**LiveKit 的插件机制允许你把自建的国内模型服务接进去**。只要你的 FunASR 或 CosyVoice 服务暴露一个 OpenAI 兼容的接口，就可以用 `livekit-plugins-openai` 指向自建的 base URL，把 STT、LLM、TTS 三段全部换成自己的实现。这是把国内开源模型接入实时语音应用最省力的路径。

# 六、选型原则

把上面的内容收成几条：

1. **先定路线，再选模型**。级联式还是端到端，决定了后面所有的技术选择。要办事 → 级联；要拟人 → 端到端。
2. **先定部署位置，再定模型**。服务器、端侧、还是板子？这一步排除掉的选项比精度对比排除的更多。
3. **先看许可证，再看效果**。MIT / Apache-2.0 可放心商用，自定义协议的项目要在原型阶段就确认清楚。
4. **分清楚工具链和模型**。换工具链不改模型，换模型不改工具链——想清楚你要换的是哪一层。
5. **热词和标点这类"小功能"的性价比被严重低估**。它们不改模型，却能解决大量业务专有名词的识别问题。
6. **实时场景盯端到端延迟，不要只盯模型延迟**。瓶颈通常在 LLM，或者在链路之间的排队。
7. **端侧跑前端，服务端跑大脑**。别指望 ESP32 跑大模型，把唤醒和音频前端放设备上，其余放服务端。
8. **这个领域每三个月变一次**。把架构做成分层的、可替换的，比押注某一个具体模型更重要——上面这些项目的名字会变，但分层的结构不会。
