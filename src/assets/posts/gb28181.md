在安防行业待过的人都听过一句话：**"能不能做国标，决定你能不能进这个市场。"** 这里的"国标"指的就是 GB/T 28181——《公共安全视频监控联网系统信息传输、交换、控制技术要求》。

它要解决的是一个非常具体、也非常难的问题：**让不同厂商的摄像头、录像机、平台之间能互相联通**。在它出现之前，海康、大华、宇视各有一套私有 SDK 和私有协议，一个市级平台要接入几十个厂家的设备，就得维护几十套适配代码，每加一个品牌都是一次开发。GB/T 28181 用一套统一的信令和媒体规范终结了这种局面。

这篇文章按 标准定位 → 体系结构与编码 → SIP 之上的扩展 → 核心信令流程 → 媒体传输 → 2022 版变化 → 开源实现 的顺序展开。**阅读前建议先了解 SIP 的基础**（事务、对话、INVITE 流程、SDP 结构），因为 GB28181 的信令层就是 SIP——它做的事情是在 SIP 这个信封里塞进自己的 XML 消息体。

# 一、标准定位

## 1.1 版本演进

| 版本 | 发布 / 实施 | 主要特征 |
| --- | --- | --- |
| GB/T 28181-2011 | 2011 / 2012 | 首版，确立 SIP + RTP 的基本框架 |
| **GB/T 28181-2016** | 2016 / 2017 | **使用最广的版本**，完善了目录、回放、云台、报警；附录 L 定义 TCP 媒体传输 |
| **GB/T 28181-2022** | 2022-12-30 / 2023-07-01 | 现行版本。新增注册重定向、NAT 下 TCP 长连接、TCP 重连、H.265/AAC、图像抓拍、精准云台等 |

**实践中的现实是：2016 版仍是事实上的互通基线。** 大量在网设备和平台只支持 2016，新平台必须向后兼容。2022 版的新特性（尤其是注册重定向和 TCP 重连）在新建项目里值得用，但对接老设备时不能假设对方支持。

## 1.2 与 ONVIF / RTSP / GA/T 1400 的关系

这是选型时最容易混淆的一组概念，它们其实是**不同层次、不同场景**的东西：

| 标准 | 层级 | 解决什么 | 典型场景 |
| --- | --- | --- | --- |
| **GB/T 28181** | 联网信令 + 媒体 | **跨平台、跨网域**的设备接入、目录、直播、回放、云台 | 政府/公安联网、雪亮工程、大型园区 |
| **ONVIF** | 设备发现 + 控制 | 局域网内设备发现、能力查询、媒体配置、PTZ | 单点集成、NVR 对接摄像头 |
| **RTSP** | 媒体拉流 | 直接向设备拉一路实时流 | 局域网内取流、调试 |
| **GA/T 1400** | 视图库 | **图片、结构化数据**（人脸、车辆）的采集、级联、订阅 | 与 28181 互补：28181 管视频流，1400 管视图数据 |
| **GB 35114** | 安全 | 视频内容的签名、加密、完整性 | 高安全等级场景（A/B/C 三级） |

**关键判断**：**只要涉及"跨组织、跨网域、上级平台级联"，就是 28181 的领域。** 局域网内单点接摄像头用 RTSP/ONVIF 更简单直接，没必要上国标。而如果做的是人脸/车辆卡口的图片汇聚，那是 GA/T 1400 的活。

## 1.3 相关的安全与编码标准

| 标准 | 内容 |
| --- | --- |
| **GB 35114** | 公共安全视频监控联网信息安全技术，定义 A/B/C 三级安全，用数字证书与签名保证设备身份与视频完整性 |
| **GB/T 25724** | 公共安全视频监控数字视音频编解码（SVAC），国产编解码标准 |
| **GB/T 2260** | 行政区划代码，是 28181 设备编码前 8 位的来源 |

# 二、体系结构与编码规则

## 2.1 角色划分

GB28181 把联网系统拆成几类角色，理解它们的职责边界是排障的基础：

| 角色 | 职责 | 典型实现 |
| --- | --- | --- |
| **前端设备** | 采集与编码，作为 SIP UAS 被平台控制 | IPC（网络摄像机）、NVR/DVR、编码器 |
| **SIP 服务器（中心信令控制服务器）** | 注册、鉴权、路由、目录、控制命令转发 | Kamailio / 自研 SIP 栈 / WVP-PRO 内置 |
| **信令安全路由网关** | 跨域信令路由与安全隔离 | 边界网关 |
| **媒体服务器（流媒体服务器）** | 接收 PS 流、转封装（RTSP/HLS/WebRTC/FLV）、分发、录像 | ZLMediaKit、SRS、自研 |
| **客户端** | 用户操作界面，发起点播、云台、回放 | Web/PC/移动端 |
| **上级/下级平台** | 平台级联，下级向上级注册并提供资源 | 同构或异构平台 |

**一个常见误解是以为"平台"是一个整体。** 实际上信令服务器和流媒体服务器通常是两个独立进程、甚至两台机器，通过 HTTP API 交互。**信令通不等于媒体通**——这是国标排障里最重要的一条分界线。

## 2.2 设备编码：20 位里的信息量

国标编码是 20 位十进制数字，分五段：

| 码段 | 位数 | 含义 |
| --- | --- | --- |
| **中心编码** | 1–8 | 行政区划：省级（1-2）、市级（3-4）、区县（5-6）、基层接入单位（7-8），依据 GB/T 2260 |
| **行业编码** | 9–10 | 所属行业（公安、交通、教育等各有代号） |
| **类型编码** | **11–13** | **设备 / 用户类型**，最需要记的一段 |
| **网络标识** | 14 | 承载网络：0/1 公安视频传输网、2 行业专网、3 政法信息网、4 公安移动信息网、5 公安信息网、6 电子政务外网、7 互联网、8 专线、9 预留 |
| **序号** | 15–20 | 6 位序号，同一类型下的个体编号 |

类型编码的关键取值：

| 类型编码 | 含义 | 类型编码 | 含义 |
| --- | --- | --- | --- |
| 111 | DVR | **132** | **网络摄像机（IPC）** |
| 112 | 视频服务器 | 133 | 显示器 |
| 113 | 编码器 | 134 / 135 | 报警输入 / 输出设备 |
| 114 | 解码器 | **200** | **中心信令控制服务器** |
| 118 | NVR | 202 | 媒体分发服务器 |
| 130 | HVR | 211 | 信令安全路由网关 |
| **131** | **摄像机** | 215 / 216 | 业务分组 / 虚拟组织 |
| 300–399 | 中心用户 | 400–499 | 终端用户 |

看一个例子就清楚了：

```
34020000001320000001
│      │ │ ││ │    │
│      │ │ ││ │    └── 序号 000001
│      │ │ ││ └─────── 网络标识 0（公安视频传输网）
│      │ │ └┴───────── 类型编码 132（网络摄像机）
│      └─┴─────────── 行业编码 00
└──────────────────── 中心编码 34020000（安徽省芜湖市）
```

**排障时的第一个检查点就是编码的位数和分段**。设备注册失败、平台上显示不出通道、级联后资源重复，很多时候是编码规则本身填错了（比如平台用了 200 结尾而设备用了 132 结尾，级联时冲突）。

## 2.3 通信协议结构

GB28181 的协议栈是分层的：

| 层 | 协议 | 内容 |
| --- | --- | --- |
| 信令 | **SIP**（UDP / TCP） | 注册、心跳、目录、点播、控制 |
| 信令消息体 | **MANSCDP**（XML） | 控制、查询、通知、应答 |
| 回放控制 | **MANSRTSP**（类 RTSP 文本） | 播放、暂停、快进、停止 |
| 媒体传输 | **RTP / RTCP** | 承载 PS 流 |
| 媒体封装 | **PS（Program Stream）** | 复用音视频，来自 MPEG-2 Systems |
| 视频编码 | H.264 / H.265（2022 新增） | — |
| 音频编码 | G.711 A 律为主，2022 新增 G.722.1 / AAC | — |

**PS 封装是国标区别于 RTSP 方案的最大特征。** 国标不用裸 RTP 承载 H.264，而是先把音视频打成 PS 包，再塞进 RTP。这样做的好处是音视频同步与多路复用有统一规范，代价是**多了一层封装解析**——自研平台最容易出问题的地方就在 PS 解析上。

# 三、SIP 之上的国标扩展

## 3.1 MANSCDP：XML 消息体

国标在 SIP 的 MESSAGE 和 INFO 方法里携带 XML 消息体，共四类：

| 类型 | 用途 | 举例 |
| --- | --- | --- |
| **Control** | 平台 → 设备的控制命令 | 云台控制（`DeviceControl`）、录像控制、报警复位、远程重启 |
| **Query** | 平台 → 设备的查询 | 设备信息、设备状态、目录（`Catalog`）、录像文件（`RecordInfo`）、配置下载 |
| **Notify** | 设备 → 平台的通知 | 报警（`Alarm`）、心跳（`Keepalive`）、目录变更 |
| **Response** | 应答 | 对 Control / Query 的返回 |

一个目录查询的请求体长这样：

```xml
<?xml version="1.0" encoding="GB2312"?>
<Query>
  <CmdType>Catalog</CmdType>
  <SN>17430</SN>
  <DeviceID>34020000001320000001</DeviceID>
</Query>
```

应答：

```xml
<?xml version="1.0" encoding="GB2312"?>
<Response>
  <CmdType>Catalog</CmdType>
  <SN>17430</SN>
  <DeviceID>34020000001320000001</DeviceID>
  <SumNum>2</SumNum>
  <DeviceList Num="2">
    <Item>
      <DeviceID>34020000001320000001</DeviceID>
      <Name>东门摄像机</Name>
      <Manufacturer>Hikvision</Manufacturer>
      <Model>DS-2CD3T46</Model>
      <Status>ON</Status>
    </Item>
    <Item>
      <DeviceID>34020000001320000002</DeviceID>
      <Name>东门摄像机-辅码流</Name>
      <Status>ON</Status>
    </Item>
  </DeviceList>
</Response>
```

**两个必须注意的细节**：

- **`SN`（序列号）是请求与应答的配对依据**。SN 必须由请求方生成并唯一，应答里的 SN 必须与请求一致。异步、多设备并发时 SN 冲突会造成"应答串线"，表现为目录里出现了别的设备的通道。
- **字符集是 GB2312 编码**（很多实现也用 UTF-8 并声明，但对接老设备时 GB2312 更保险）。中文名称乱码基本都出在这里。

## 3.2 MANSRTSP：回放控制

历史回放的控制不用 SIP 的 XML，而是用一套类似 RTSP 的文本消息，通过 SIP 的 INFO 方法携带：

| 消息 | 作用 |
| --- | --- |
| `PLAY RTSP/1.0` | 播放（可带 `Range` 指定时间范围与 `Scale` 倍速） |
| `PAUSE RTSP/1.0` | 暂停 |
| `TEARDOWN RTSP/1.0` | 结束回放 |

倍速用 `Scale` 头：`0.5` 为半速、`2.0` 为二倍速、负值表示倒放。**只有部分设备支持倒放和变速**，能力要提前查（设备能力集里有 `PlaySpeed` 之类的描述）。

## 3.3 国标对 SIP 头域的约定

| 头域 | 国标用法 |
| --- | --- |
| **Subject** | 携带媒体流标识，格式如 `设备编码:媒体序号,媒体服务器编码:媒体序号`，用于关联信令与媒体 |
| **X-GB-Ver** | **2022 新增**，声明协议版本：`3.0` = 2022 版，`2.0` = 2016 版，用于双方互认能力 |
| **Contact** | 设备注册后，平台按这个地址向设备发 INVITE |
| Content-Type | 信令 XML 为 `Application/MANSCDP+xml`，回放控制为 `Application/MANSRTSP` |

# 四、核心信令流程

![GB/T 28181 的核心信令时序：注册与心跳维持在线状态，目录查询同步资源，INVITE 点播建立媒体流](/images/blog/gb28181/gb28181-flow.svg)

## 4.1 注册与鉴权

设备和平台建立关系的第一步。流程与标准 SIP 注册一致，但有几处国标特有的约束：

```
设备 → REGISTER sip:34020000002000000001@3402000000 SIP/2.0
       （Contact 里带上自己的编码与地址，Expires 通常 3600）
平台 → 401 Unauthorized  WWW-Authenticate: Digest ...
设备 → REGISTER ... Authorization: Digest username="34020000001320000001", ...
平台 → 200 OK
```

| 约束 | 说明 |
| --- | --- |
| **注册有效期** | 缺省 86400s（1 天），**不应短于 3600s**。实际部署常配 3600s |
| **重试间隔** | 注册失败后重试间隔**不应短于 60s**，避免海量设备反复冲击平台 |
| **鉴权** | 支持摘要认证，用户名即设备编码 |
| **在线判定** | 注册成功只是"绑定"，真正的在线状态靠心跳维持 |

### 2022 新增：注册重定向

2016 版没有这个能力，海量设备直连一台 SIP 服务器会形成并发瓶颈，且服务器故障时无法自动转移。2022 版引入**注册重定向**：

```
设备 → REGISTER 到全局重定向服务器
重定向服务器 → 302 Moved Temporarily（按负载均衡策略在 Contact 里给出 SIP 服务器 A 的地址）
设备 → 向 SIP 服务器 A 重新 REGISTER
```

**这个机制的价值在于把"设备指向哪台服务器"从静态配置变成了动态调度**。对动辄几十万路的省级平台，这是刚需。

### 2022 新增：NAT 下的 TCP 长连接

标准明确规定：位于 NAT 内侧的 SIP 代理**宜用 TCP 发起注册，注册成功后保持 TCP 连接不关闭**，之后的心跳、刷新注册、点播、控制消息都在这个通道内传输；**通道断开即认为掉线**。

这解决了 UDP 时代两个老问题：NAT 映射超时导致的"假在线"、以及媒体端口无法预知造成的防火墙放行困难。

## 4.2 心跳

心跳通过 SIP `MESSAGE` 携带 XML（`CmdType` 为 `Keepalive`）发送：

```xml
<?xml version="1.0" encoding="GB2312"?>
<Notify>
  <CmdType>Keepalive</CmdType>
  <SN>1</SN>
  <DeviceID>34020000001320000001</DeviceID>
  <Status>OK</Status>
</Notify>
```

| 参数 | 标准值 | 实践值 |
| --- | --- | --- |
| 心跳间隔 | 缺省 60s | 常配 20–30s（更快发现掉线） |
| 判定离线 | 连续 3 次心跳失败 | 同 |

**心跳和注册是两个独立机制**：注册维持位置绑定（Expires 到点才失效），心跳维持在线状态（几次收不到就判离线）。**"设备在线但一星期后掉线"通常是注册过期没刷新；"拔网线后平台仍显示在线几分钟"则是心跳周期决定的。**

## 4.3 目录查询：资源同步

平台通过 Catalog 查询获取设备下的通道列表。关键机制是**分页**：

- 响应里的 `SumNum` 是**通道总数**，`DeviceList Num` 是**本次返回的数量**
- 如果 `SumNum` 大于单次返回数，平台需要继续查询直到收齐
- 大设备（NVR 下挂几百路）如果不做分页，会返回超大 XML，超过 UDP 承载能力

**这是国标排障里的高频问题**：UDP 下单包上限约 1500 字节，几百个通道的目录响应必然要分片或被截断。**标准做法是把 SIP 信令切到 TCP**——这也是国标明确允许的。

目录还可以用 `SUBSCRIBE`/`NOTIFY` 做订阅，设备在资源变更时主动推送。2022 版增强了订阅模型，支持摘要（Summary）与增量推送。

## 4.4 实时点播：Invite 与 SDP

这是国标最核心也最容易出错的一环。流程如下：

```
平台/媒体服务器 → INVITE 到设备（地址来自注册时的 Contact）
                  SDP 里 s=Play，y=SSRC，f=媒体描述
设备           → 200 OK（带上设备自己的 SDP，确认收发地址）
媒体服务器     → ACK
设备           → 向媒体服务器推 PS over RTP 流
```

**方向容易被搞反**：实时点播里，**媒体流是设备主动推给媒体服务器**的，不是平台去拉。设备推的目标地址来自平台 INVITE 中的 SDP。

国标 SDP 的几个特有字段：

| 字段 | 含义 |
| --- | --- |
| `s=Play` | 实时点播；`Playback` 回放；`Download` 下载 |
| `u=<设备编码>:<通道编码>` | 标识点播的具体通道 |
| **`y=<SSRC>`** | **媒体流标识**，10 位十进制，见下表 |
| `f=v/2/5/25/1/4000a/...` | 媒体描述：音视频编码、帧率、分辨率、码率等 |
| `a=setup:active` / `passive` | RTP over TCP 时的连接方向（主动连 / 被动等连） |
| `a=ssvcratio` | **2022 新增**，空域编码增强层与基本层的比例（如 4:3、2:1） |

### SSRC 的生成规则

SSRC 是 10 位十进制数字串，用于让媒体服务器在一堆 RTP 流里认出"这是哪一路点播"：

| 位数 | 含义 |
| --- | --- |
| **第 1 位** | **0 = 实时流，1 = 历史流**（回放/下载） |
| 第 2–6 位 | 域标识，取 20 位 SIP 监控域 ID 的**第 4 到第 8 位** |
| 第 7–10 位 | 域内媒体流标识，**同域内后 4 位不重复**的 4 位整数（0–9999） |

**规则要点**：点播本域设备时，SSRC 由本域平台生成并通过 INVITE 下发；点播外域设备时，SSRC 由**被点播域**生成并在 200 OK 中返回，被点播域的 RTP 流使用该值。**SSRC 冲突会导致"点开一路，另一路黑屏"**，多路并发点播必须做去重分配。

### TCP 还是 UDP

| 模式 | 适用 | 说明 |
| --- | --- | --- |
| **UDP** | 局域网、丢包容忍度高 | 简单，NAT 下有端口不可预知的问题 |
| **TCP 主动（active）** | 媒体服务器主动连设备 | 媒体服务器发起连接，需要能路由到设备 |
| **TCP 被动（passive）** | 设备主动连媒体服务器 | **NAT 场景的首选**，设备侧发起连接，穿 NAT 无压力 |

**判断谁来发起连接，看的是 `a=setup` 值**：`active` 表示 SDP 的发送方会主动发起 TCP 连接，`passive` 表示它会等待对方连接。这条规则在对接设备时经常被搞反，表现为"信令全通但媒体端口一直没建立"。

## 4.5 历史录像：检索、回放、下载

历史录像的流程比实时点播多两步：

| 步骤 | 信令 | 说明 |
| --- | --- | --- |
| 1. 检索 | `RecordInfo` Query | 按时间段查询录像文件列表，返回文件名、起止时间、大小、类型 |
| 2. 回放 | `INVITE` + `s=Playback` | SDP 中带 `t=<开始时间> <结束时间>`，用 UNIX 时间戳 |
| 3. 控制 | `INFO` + MANSRTSP | 暂停、继续、倍速、拖动（`Range` 头指定新的时间点） |
| 4. 结束 | `BYE` 或 `TEARDOWN` | — |
| 替代方案：下载 | `INVITE` + `s=Download` | 带 `Speed` 参数，以文件方式传输，适合归档 |

**`t=` 用 UNIX 时间戳**（从 1970-01-01 起的秒数），格式为 `开始时间 结束时间`，用空格分隔。**设备与平台的时钟必须同步**，否则检索出来的时间段完全对不上——这是回放问题里最常见的根因，几乎所有国标部署文档都会强调设备必须配置 NTP。

## 4.6 云台、报警、语音广播

| 功能 | 实现 |
| --- | --- |
| **云台控制（PTZ）** | `DeviceControl` 的 `PTZCmd`，控制码为 8 字节字节串（方向、速度、变倍、聚焦、光圈） |
| **精准 / 绝对云台** | **2022 新增**，支持绝对位置、精准控制、看守位查询、巡航轨迹查询、目标跟踪 |
| **报警** | 设备主动 `Notify` 上报 `Alarm`；平台可订阅（`SUBSCRIBE`/`NOTIFY`） |
| **语音广播** | 平台向设备下发 `Broadcast`，设备接收并播放 |
| **图像抓拍** | **2022 新增**，最多一次 10 张，间隔最小 1s |
| **设备升级 / 存储卡状态** | **2022 新增**，远程升级命令与存储介质状态查询 |

PTZCmd 的字节结构是国标里少见的"二进制协议"部分，对接时需要严格按位操作，出错的表现是"云台往错误方向转"或"速度参数无效"。

## 4.7 级联

平台级联是国标设计里最巧妙的部分：**下级平台向上级平台注册时，把自己伪装成一台"设备"**。

因此级联的信息流完全复用设备接入的机制：

| 下级角色 | 上级视角 |
| --- | --- |
| 下级平台（编码以类型 200 结尾） | 一台设备 |
| 下级平台的通道 | 该设备下的通道 |
| 下级平台的媒体服务器 | 提供媒体流的"设备" |

**级联的两个常见问题**：

- **编码冲突**：两级平台用了相同的中心编码，导致资源 ID 重复、上级平台目录里出现同名通道
- **媒体路径绕行**：上级点播下级通道时，媒体可能先到下级平台再到上级。**优化做法是级联时让上级的媒体服务器直接向下级设备取流**，但这要求网络可达，很多跨网域场景做不到，只能中继

# 五、媒体传输

## 5.1 PS 封装

国标用 MPEG-2 Program Stream 复用音视频：

```
RTP 包 → PS 头 + PES 包（视频） + PES 包（音频）
```

解析时要处理 PSM（Program Stream Map）来识别音视频的流 ID。**PS 解析是自研平台最容易踩坑的地方**——少一个字节的对齐处理，画面就会出现花屏或音视频不同步。

## 5.2 传输方式与编码

| 维度 | 选项 |
| --- | --- |
| 传输协议 | RTP over UDP / RTP over TCP（RFC 4571） |
| 2022 扩展 | 新增 RTP over RTSP 等可选方式 |
| 视频编码 | H.264 为主，**2022 新增 H.265** |
| 音频编码 | G.711 A 律为主，**2022 新增 G.722.1、AAC** |
| 加密 | **推荐 SRTP**；GB 35114 场景下用签名与加密 |

## 5.3 媒体保活与断流判定

平台**收不到 RTP 就会判定断流**并可能主动发 BYE 拆除会话。为此国标定义了媒体保活机制：

- 在无媒体数据时，按周期发送保活包（空 RTP 包）维持通道
- **2022 新增 TCP 重连机制**：首次连接失败应间隔 ≥1s 重连，**重连次数 ≥3 次**

**这条规则解决了 TCP 模式下的一个老问题**：网络抖动导致 TCP 断开后，2016 版的实现往往直接放弃，表现为"流断了一直不恢复，必须重新点播"。2022 版要求自动重连，对稳定性提升明显。

# 六、2022 版相对 2016 的关键变化

| 变化点 | 2016 | 2022 |
| --- | --- | --- |
| **注册重定向** | 无 | 新增 `302` 重定向，支持负载均衡与故障转移 |
| **NAT 传输要求** | 未明确 | NAT 内侧宜用 TCP 注册并保持长连接，断连即判离线 |
| **协议版本标识** | 无 | 新增 `X-GB-Ver`（3.0 = 2022，2.0 = 2016） |
| **TCP 媒体传输** | 附录 L | 改为附录 D，**新增 TCP 重连机制** |
| **视音频编码** | H.264 / G.711 | 新增 H.265、G.722.1、AAC |
| **图像抓拍** | 无 | 支持，最多 10 张、最小间隔 1s |
| **云台控制** | 基本方向控制 | 新增绝对定位、精准控制、看守位、巡航轨迹、目标跟踪 |
| **设备运维** | 有限 | 新增远程升级、存储卡状态查询 |
| **信令安全** | — | 明确 SIP over TLS 支持 |
| **目录订阅** | 基本订阅 | 增强为摘要 + 增量推送 |

**对接策略上的建议**：新建设备优先按 2022 实现，同时在 `REGISTER` 里带 `X-GB-Ver` 声明版本；对接老设备时按 2016 基线处理，**不要假设对方支持重定向或 TCP 重连**，这两项要做能力探测或配置开关。

# 七、开源实现与部署

## 7.1 主流开源方案

| 项目 | 语言 | 协议 | 定位 |
| --- | --- | --- | --- |
| **WVP-PRO（wvp-GB28181-pro）** | Java | MIT | 国内最常用的整套开源国标平台：SIP 信令 + Web 管理 + 设备/通道管理 + 级联；支持 GB28181-2016 并兼容 2022 的部分特性（巡航轨迹、精准 PTZ、OSD、H.265+AAC） |
| **ZLMediaKit** | C++ | MIT | 高性能流媒体服务器，国标 PS 流的接收与转封装（转 RTSP/HLS/HTTP-FLV/WebSocket-FLV/WebRTC） |
| **SRS** | C++ | MIT | 通用流媒体服务器，也支持 RTP 推流与多协议分发 |
| **gb28181-sip / 各类 Go 实现** | Go | 各不同 | 轻量信令服务，适合嵌进自己的平台 |
| **LiveGBS / EasyGBS** | — | 商业 | 商业化的国标平台，功能完整、支持较好（部分高级功能需付费） |

**注意 WVP-PRO 的授权边界**：自有代码是 MIT，可以自由商用；但它集成了部分第三方开源组件，商用前需要自行确认这些组件的许可。另外 ONVIF 接入与部分 2022 高级功能并非开源，需要另外获取。

## 7.2 典型部署架构

```
摄像头（GB28181 设备）
    │  SIP 信令（UDP/TCP 5060）
    ↓
WVP-PRO（SIP 信令服务器 + Web 管理）  ←→  数据库 / Redis
    │  HTTP API 交互
    ↓
ZLMediaKit（流媒体服务器）
    │  RTSP / HLS / HTTP-FLV / WebRTC
    ↓
前端播放器（jessibuca / WebRTC）
```

**分工很清晰：WVP-PRO 管信令和业务，ZLMediaKit 管媒体。** 两者通过 HTTP API 交互——WVP 告诉 ZLMediaKit "开一个收流端口"，ZLMediaKit 把收到的流地址回给 WVP，WVP 再通过 INVITE 把地址告诉设备。

## 7.3 部署与排障要点

**部署前必须确认的四件事：**

1. **编码规则统一**：平台编码（类型 200）、设备编码（类型 132 等）、通道编码三段规则一致，级联时中心编码不能冲突
2. **时钟同步**：设备和平台都配置 NTP。**回放检索不准、录像时间对不上一律先查时钟**
3. **端口放行**：SIP 5060（UDP/TCP）、RTP 端口段（可配置，通常 30000–30500 或更大范围）、HTTP API 端口
4. **NAT 策略**：有 NAT 时信令走 TCP，媒体用 TCP 被动模式（设备主动外连）

**症状 → 病因对照表**：

| 症状 | 最可能的原因 |
| --- | --- |
| 设备注册不上 | 编码位数/格式错、认证信息错、平台 IP/端口不通、5060 被占用 |
| 设备显示在线但一星期后掉线 | 注册 Expires 到期未刷新（设备侧未配或平台未回 200） |
| 拔网线后平台仍显示在线 | 心跳判定周期未到；检查心跳间隔与失败次数配置 |
| 目录能查到但点播黑屏 | 媒体服务器未收到流；SDP 里的收流地址不可达；`a=setup` 方向搞反 |
| 点播卡在"正在连接" | INVITE 发出但设备没回 200：设备忙、通道已满、Contact 地址不可达 |
| 有声音没画面 / 有画面没声音 | PS 解析问题；或音频编码不匹配（如设备发 AAC 而平台只认 G.711） |
| 多路点播相互影响、随机黑屏 | **SSRC 冲突**，检查后 4 位分配是否去重 |
| 回放时间对不上 | 设备与平台时钟不同步（NTP 未配） |
| 大 NVR 目录不全 | UDP 分片导致 XML 被截断，把 SIP 切到 TCP 或让平台正确处理分页 |
| TCP 模式下断流不恢复 | 未实现 2022 的 TCP 重连机制 |
| 中文通道名乱码 | XML 字符集声明与实际编码不一致（GB2312 / UTF-8） |

**排障的基本顺序**（与 SIP 一致，但多了一层）：

1. **信令层**：用 sngrep 抓 5060，看注册、心跳、目录、INVITE 是否走完
2. **协议层**：看 XML 消息体的 `CmdType`、`SN` 配对、`DeviceID` 是否正确
3. **媒体层**：在流媒体服务器上抓 RTP，确认流有没有到、SSRC 是否与 SDP 一致
4. **解封装层**：确认 PS 流能否被正确解析、音视频编码是否被支持

**第 3 步是最关键的分水岭**：流媒体服务器收到流说明问题在解封装或分发；没收到流说明问题在信令或网络路径。这一刀切开，能省掉大量猜测。

---

GB/T 28181 的知识密度很高，但结构其实很清晰：**用 SIP 传信令，用 XML 传控制语义，用 RTP + PS 传媒体，用 20 位编码标识一切资源**。把这个骨架记住，剩下的都是细节填充。

如果你在做的是"让 AI 接电话、打电话"这类应用，那用到的其实是本文的前置知识——标准 SIP。而如果要做的是语音 AI 的实时编排（STT、LLM、TTS 的流水线），下一篇《Pipecat：构建实时语音 AI Agent 的开源编排框架》会更直接相关。
