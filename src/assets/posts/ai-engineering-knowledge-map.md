在强监管行业（金融、政务、医疗）做 AI，评价标准和通用互联网场景很不一样：**不是谁的模型刷得高，而是谁能把模型稳稳地放到生产上，并且在出问题时说得清、追得到、退得回**。这决定了知识结构不能只堆在算法一侧——传统机器学习与统计、大模型的原理与工程、部署与监控、可解释性与合规，四块缺一不可。

这篇文章把这几块串成一张地图。它是一份知识梳理，也适合作为 AI 方向技术复盘的索引：每一节尽量给出**结论 + 原理 + 易错点**，而不是停在名词解释。

# 一、先建立一个判断框架

面试和落地中最容易区分水平的一个问题：**模型指标好，业务指标不好，怎么办？**

能答好这个问题，说明你理解 AI 落地的三层结构：

| 层次 | 回答的问题 | 决定 |
| --- | --- | --- |
| 算法层 | 模型能不能学到规律 | 效果**上限** |
| 工程层 | 能不能稳定、低延迟地服务 | 效果**下限** |
| 治理层 | 能不能被解释、被审计、被追责 | 能不能**上线** |

很多团队卡在第二层和第三层，却一直在第一层加投入——换更大的模型、调更复杂的结构，收益远小于把特征一致性、监控闭环、可解释性补齐。

贯穿全文的三个判断原则：

1. **先看数据，再看模型**。金融风控里特征工程的价值远大于模型选型，LR 加好的特征经常打败特征粗糙的深度模型。
2. **先看业务指标，再看模型指标**。AUC 提升 0.01 但通过率下降 5%，是负收益。
3. **先看可运维性，再看先进性**。一个能被监控、能被回滚的旧模型，胜过无法定位问题的 SOTA 模型。

# 二、传统机器学习与统计

这部分常被大模型热潮掩盖，但在风控、评分卡、反欺诈这类场景仍是主力。它们的特点是**强可解释、可审计、样本需求相对可控**。

## 2.1 逻辑回归：可解释性的基准线

LR 是线性加权后接 Sigmoid：

```text
z = w·x + b
p = σ(z) = 1 / (1 + e^(-z))
```

**损失函数用对数似然（等价于交叉熵）而不是 MSE**，原因有两条：

- **凸性**：交叉熵 + Sigmoid 是凸函数，能保证收敛到全局最优；MSE + Sigmoid 是非凸的，容易陷入局部最优。
- **梯度形态**：交叉熵的梯度是 `(p - y) · x`，误差越大梯度越大；MSE 的梯度里带着 `σ'(z)`，在 Sigmoid 饱和区（预测极度错误时）梯度趋近于 0，出现"错得越离谱、学得越慢"的梯度消失。

```text
∂L/∂w = (p - y) · x        # 交叉熵：梯度与误差成正比
∂L/∂w = (p - y) · σ'(z) · x # MSE：多乘一项饱和因子，饱和区梯度消失
```

**可解释性来自系数**：把特征标准化后，系数绝对值大小即重要性排序，符号表示正负相关；取 `exp(w_i)` 得到优势比（odds ratio），含义是"该特征每增加一个单位，坏样本几率变为原来的多少倍"。对离散特征做 WOE 分箱后再进 LR，就得到标准的**评分卡**——这也是它至今仍是信贷主模型的原因：每个变量对分数的贡献可以逐条打印给监管和客户。

## 2.2 GBDT 家族：XGBoost 与 LightGBM

两者都是梯度提升树的高效实现：**加法模型 + 前向分步**，每轮拟合上一轮残差（更准确地说，拟合损失函数的负梯度）。

目标函数由"损失 + 正则"组成，XGBoost 的关键贡献是对损失做**二阶泰勒展开**，从而能自定义损失函数：

```text
Obj = Σ [ g_i·w + ½·h_i·w² ] + γT + ½λ‖w‖²
```

其中 `g_i`、`h_i` 是一阶、二阶梯度，`T` 是叶子数，`w` 是叶子权重。正则项同时惩罚**树的复杂度**（`γT`，控制叶子数）和**叶子权重的幅度**（`½λ‖w‖²`，防止单叶子输出过大）——这是它比传统 GBDT 更抗过拟合的根本原因。

叶子权重的最优解和分裂增益都能闭式写出：

```text
最优叶子权重  w* = -G / (H + λ)
分裂增益      Gain = ½[ G_L²/(H_L+λ) + G_R²/(H_R+λ) - G²/(H+λ) ] - γ
```

注意增益里的 `- γ`：**只有增益大于 `γ` 才分裂**，这就是"预剪枝"的数学形式。

两者的核心差异：

| 维度 | XGBoost | LightGBM |
| --- | --- | --- |
| 特征处理 | 预排序（pre-sorted），精确贪心 | 直方图（histogram）分桶，近似贪心 |
| 树生长 | level-wise（按层） | leaf-wise（按叶，误差下降最快） |
| 内存与速度 | 内存占用高，训练较慢 | 内存低、速度快数倍 |
| 采样技巧 | 行/列采样 | GOSS（梯度采样）+ EFB（互斥特征捆绑） |
| 过拟合风险 | 相对稳健 | leaf-wise 容易长深，必须用 `num_leaves` + `max_depth` 双重限制 |

**Leaf-wise 的坑**：同样的叶子数下 leaf-wise 拟合能力更强，所以 `num_leaves` 不能用 `2^max_depth` 来推——LightGBM 官方建议 `num_leaves < 2^max_depth`，否则小数据上极易过拟合。

防过拟合的常规手段（两套通用）：

| 方向 | 参数 |
| --- | --- |
| 控制复杂度 | `max_depth`、`num_leaves`、`min_child_weight` / `min_data_in_leaf` |
| 增加随机性 | `subsample` / `bagging_fraction`、`colsample_bytree` / `feature_fraction` |
| 正则化 | `lambda`（L2）、`alpha`（L1）、`gamma`（最小分裂增益） |
| 训练策略 | 降低 `learning_rate` 同时增加树数量、早停（early stopping） |

**风控里的经典组合是 GBDT + LR**：用 GBDT 把原始特征映射成叶子索引（one-hot 后作为新特征）喂给 LR。这样既拿到了树模型的非线性与交叉能力，又保留了 LR 的线性可解释性——是一个非常典型的"效果与合规折中"的工程解法。

## 2.3 样本不平衡

违约样本通常只占 1%~5%。可选手段：

| 手段 | 做法 | 风险 |
| --- | --- | --- |
| 欠采样 | 丢弃多数类 | 丢失信息 |
| 过采样 | 复制少数类 | 加剧过拟合 |
| SMOTE | 在少数类近邻间插值合成 | 合成样本在特征空间可能不真实，引入噪声 |
| 代价敏感 | `scale_pos_weight` / `class_weight` | 需要调参，但最接近业务本质 |
| 阈值移动 | 不重采样，输出概率后按成本选阈值 | 需要明确的业务成本矩阵 |

**两条必须记住的纪律**：

1. **重采样只能作用于训练集**。对验证集、测试集重采样会让评估指标失去意义——你评估的不再是真实分布下的表现。
2. **风控场景更常见的做法是不重采样**。保持真实先验能让模型输出的概率接近真实违约率，便于做额度、定价这类决策；排序能力用 AUC/KS 衡量，阈值按业务通过率反推。

## 2.4 评估指标：为什么风控看 AUC 和 KS

**准确率在不平衡场景下是无效指标**：违约率 1% 时，把所有样本都预测为"不违约"就有 99% 准确率，但业务价值为零。

| 指标 | 定义 | 特点 |
| --- | --- | --- |
| 精确率 Precision | TP / (TP + FP) | 关注"预测为坏的人里有多少真的坏" |
| 召回率 Recall | TP / (TP + FN) | 关注"真的坏的人里抓出了多少" |
| F1 | 精确率与召回率的调和平均 | 需要平衡两者时使用 |
| ROC / AUC | 曲线下面积，等价于"随机取一个好样本和一个坏样本，好样本得分更高的概率" | 衡量**排序能力**，对阈值不敏感，**对类别比例不敏感** |
| KS | `max(TPR - FPR)` | 好、坏样本累计分布曲线的最大分离度，风控核心指标 |
| PR 曲线 | 精确率-召回率曲线下面积 | 正类极度稀少时比 ROC 更敏感 |

**AUC 与 KS 的核心价值在于它们衡量的是排序能力而非点预测**。信贷业务的实际动作是"按分数排序后切一条通过率线"，模型只需要把坏客户排到前面——不需要它输出精确的概率值。

经验刻度（仅作参考，不同业务差异很大）：KS > 0.3 可用，> 0.4 良好；若 KS > 0.5 要警惕**信息穿越**（特征里混入了未来信息）或样本泄漏，而不是先庆祝。

**模型指标必须映射到业务指标**：通过率、坏账率、额度使用率、挽回损失、人工审核工作量。上线前要回答"如果 AUC 涨 0.02，业务上会发生什么"。

## 2.5 过拟合与欠拟合

| | 过拟合 | 欠拟合 |
| --- | --- | --- |
| 现象 | 训练集好、验证集差 | 训练集和验证集都差 |
| 诊断 | 学习曲线上两条线持续张开 | 两条线都收敛在较差的水平 |
| 处理 | 增数据、降复杂度、加正则、早停、交叉验证、特征筛选 | 增特征、增复杂度、减正则、换模型 |

一个容易忽略的点：**过拟合不一定来自模型，也可能来自流程**。反复用同一份验证集调参、按验证集结果挑选特征，本质上就是让验证集参与训练——这是"流程性过拟合"，靠单个模型的正则化解不了。正确做法是保留一份从不参与调参的测试集，或做嵌套交叉验证。

## 2.6 特征工程：IV 与 PSI

特征工程是风控模型里投入产出比最高的环节。两个必会指标：

**IV（Information Value，信息量）**——衡量单变量区分好坏样本的能力：

```text
WOE_i = ln( Bad%_i / Good%_i )          # 第 i 个分箱的权重证据
IV    = Σ ( Bad%_i - Good%_i ) × WOE_i
```

因为 `(Bad% - Good%)` 与 `ln(Bad%/Good%)` 符号总是一致，所以每一项都非负，IV 天然 ≥ 0。经验刻度：

| IV | 预测力 |
| --- | --- |
| < 0.02 | 几乎无区分度 |
| 0.02 ~ 0.1 | 弱 |
| 0.1 ~ 0.3 | 中等 |
| 0.3 ~ 0.5 | 强 |
| > 0.5 | 过强，优先怀疑穿越或泄漏 |

**PSI（Population Stability Index，群体稳定性指标）**——衡量两个时间窗口的分布差异，是监控漂移的标准工具：

```text
PSI = Σ ( 实际%_i - 预期%_i ) × ln( 实际%_i / 预期%_i )
```

常用阈值：< 0.1 稳定，0.1 ~ 0.25 需关注，> 0.25 显著漂移。**注意 PSI 只是"分布变了"的信号，不等于"模型坏了"**——要结合业务结果判断。

其余要点：

- **分箱**：等频、等距、卡方分箱、决策树分箱。分箱后要检查**单调性**——WOE 随分箱序号单调，模型才稳定、可解释。评分卡几乎全靠分箱。
- **缺失值**：树模型能处理缺失（每个分裂点学习默认方向），LR 需要填充或把缺失单独作为一箱。**缺失本身经常是信息**（"客户未提供收入证明"本身就是风险信号），不要无脑填均值。
- **异常值**：分箱天然鲁棒；连续特征可用 winsorize 截断到分位点。
- **特征筛选顺序**：先按 IV/相关性粗筛，再用模型重要性精筛，最后检查多重共线性（VIF）。用未来数据计算 IV 是典型的穿越。

## 2.7 偏差方差与集成思想

```text
期望泛化误差 = 偏差² + 方差 + 不可约噪声
```

- **偏差**：模型假设与真实规律的偏离——欠拟合的来源。
- **方差**：模型对训练集扰动的敏感度——过拟合的来源。

这个分解直接解释了两种集成的差异：

| 方法 | 机制 | 主要降低 |
| --- | --- | --- |
| Bagging（随机森林） | 并行训练多个模型后平均 | **方差** |
| Boosting（XGB/LGBM） | 串行拟合残差，逐步逼近 | **偏差** |

**随机森林的"随机"有两层**：样本有放回采样（bagging）+ 每次分裂只看随机特征子集。后者用于**降低树之间的相关性**——如果所有树都强相关，平均就起不到降方差的作用。

## 2.8 KMeans 与聚类

算法只有两步，反复迭代直到收敛：

1. **分配**：每个样本归到最近的簇中心
2. **更新**：把簇中心移到簇内均值

它最小化的是簇内平方误差 SSE。**K 值的选择**：

| 方法 | 做法 |
| --- | --- |
| 肘部法 | 画 SSE 随 K 的曲线，取下降明显变缓的拐点 |
| 轮廓系数 | 衡量"簇内紧密度 vs 簇间分离度"，取值 [-1, 1]，越大越好 |
| Gap Statistic | 与均匀随机分布的期望 SSE 对比 |
| 业务可解释性 | 分群结果能否被业务命名、能否对应差异化策略（最实用） |

**KMeans++ 改进的是初始化**：第一个中心随机选，后续每个中心以正比于 `D(x)²`（到最近已选中心的距离平方）的概率被选中。这使初始中心尽可能分散，显著缓解了标准 KMeans 因随机初始化陷入差局部最优的问题——注意它改进的只是**初始化**，不改变算法本质。

**KMeans 的局限（常被追问）**：

- 必须预设 K，且对 K 敏感
- 隐含假设簇是**球形、大小相近、方差相似**的，遇到长条形或密度差异大的簇会失效
- 用均值做中心 → 对离群点非常敏感（可用 K-Medoids 缓解）
- 只能找到凸的、线性可分的簇（可用 GMM、DBSCAN、谱聚类替代）
- 每次结果受初始化影响，实践中要 `n_init` 多次取最优

## 2.9 统计基础

- **正态分布与中心极限定理**：无论总体分布如何，样本量足够大时**样本均值的分布**近似正态——这是很多统计推断和 A/B 实验的基础。
- **假设检验**：`H0` 原假设、`H1` 备择假设，构造统计量，在 `H0` 成立下计算 p 值。
- **p 值的准确含义**：*在 H0 成立的前提下，观察到当前或更极端结果的概率*。**它不是"H0 为真的概率"**，也不是"效应很大的概率"——这是最高频的误解。
- **两类错误**：第一类错误（弃真，`α`）与第二类错误（取伪，`β`），`1 - β` 是检验功效。样本量不足会导致功效低，真实效应检测不出来。
- **多重检验**：同时检验 20 个特征，即使全部无效，按 `α = 0.05` 也期望有 1 个"显著"。修正方法有 Bonferroni（严格）和 FDR 控制。
- **A/B 实验**：上线前要算清**最小可检测效应**和所需样本量；注意辛普森悖论（分组后结论反转）和样本比例失衡（SRM，通常意味着分流存在 bug，此时实验结论直接作废）。

# 三、Transformer 与大模型核心机制

## 3.1 整体架构

Transformer 由若干相同层堆叠，每层包含**多头注意力 + 前馈网络**，中间穿插残差连接和 LayerNorm。

| 结构 | 注意力方式 | 擅长 | 典型用途 |
| --- | --- | --- | --- |
| Encoder-only | 双向（无掩码） | 理解、表征 | BERT 类，分类、抽取、向量嵌入 |
| Decoder-only | 因果掩码（只能看左侧） | 生成 | GPT / Qwen / Llama，当前主流 |
| Encoder-Decoder | Encoder 双向 + Decoder 交叉注意力 | 序列到序列 | 翻译、摘要 |

**各组件的职责**：

- **多头注意力**：把 `d_model` 拆成 `h` 个子空间并行做注意力，再拼接投影。单头只能学到一种"关注模式"，多头让模型同时捕捉语法依赖、指代关系、远距离关联等不同关系。约束是 `h × d_head = d_model`，所以头数增加时每个头的维度必须减少——**总计算量基本不变，换的是表达多样性**。
- **残差连接**：让梯度有一条"高速公路"直接回传，是深层网络能训练起来的前提。
- **LayerNorm**：归一化每个 token 的特征维度，稳定激活分布。**Pre-LN**（归一化放在子层输入前）比原始 Post-LN 训练更稳定，通常不需要精心设计的学习率预热；**RMSNorm** 是它的简化版，去掉了均值中心化，只保留缩放，更快且效果相当（LLaMA 系列采用）。
- **前馈网络 FFN**：逐位置独立作用，通常中间维度扩展到 4 倍，**是参数量的主要来源**（约占 2/3）。
- **复杂度**：注意力时间/空间复杂度都是 `O(n²·d)`，这个平方项是长文本问题的根源。

## 3.2 Self-Attention 与位置编码

```text
Attention(Q, K, V) = softmax( Q·Kᵀ / √d_k ) · V
```

**为什么除以 `√d_k`**：`Q·K` 是 `d_k` 个乘积之和，若各分量独立且方差为 1，点积的方差就是 `d_k`，维度越高点积数值越大。数值一大，softmax 就会进入饱和区（输出接近 one-hot），梯度趋近于 0。除以 `√d_k` 把方差拉回 1，稳定训练。

**为什么必须加位置编码**：注意力对输入是**置换等变**的——打乱词序，输出只是跟着打乱，模型无法感知顺序。"猫追老鼠"和"老鼠追猫"在纯注意力下没有区别。

| 方案 | 机制 | 特点 |
| --- | --- | --- |
| 正弦/余弦绝对编码 | 用不同频率的三角函数叠加 | 无需训练，但外推能力有限 |
| 可学习位置编码 | 每个位置一个可训练向量 | 简单，但超出训练长度直接失效 |
| 相对位置编码 | 编码位置差 | 更符合语言直觉 |
| **RoPE** | 把位置编码写成对 Q/K 的**旋转矩阵** | 使注意力分数**只依赖相对位置**；天然支持长度外推，可通过插值/缩放扩展 |

**RoPE 的优势**在于它把绝对位置信息和相对位置信息统一了起来：位置 `m` 的向量旋转角度 `mθ`，两个向量的点积只与 `(m - n)` 有关。因此它既有相对编码的合理性，又实现简单，还便于通过**位置插值**（把超出训练长度位置压缩回已知区间）或 NTK-aware 缩放来扩展上下文。

## 3.3 推理加速

**KV Cache 是自回归解码的必需优化**。生成第 `t` 个 token 时，前面 `t-1` 个 token 的 K、V 不会变，缓存下来即可，每步只需计算新 token 的 Q 与全部 KV 做注意力，把单步复杂度从 `O(n²)` 降到 `O(n)`：

```text
KV 显存 ≈ 2 × layers × heads × head_dim × seq_len × batch × dtype_bytes
```

代入一个 7B 模型（32 层、32 个 KV 头、head_dim 128、fp16）：每 token 约 `2 × 32 × 32 × 128 × 2 = 512 KB`。序列长度 8192、并发 32 时就是 `0.5MB × 8192 × 32 ≈ 128 GB`——**长上下文 + 高并发的显存瓶颈几乎全在这里，而不是权重**。

这也是为什么现代模型普遍改用 **GQA / MQA**：让多个查询头共享少量 KV 头（例如 32 个查询头共享 4 个 KV 头），KV 显存直接降到约 1/8，而效果损失很小。选型时看清模型是 MHA 还是 GQA，对部署成本的影响是数量级的。

| 手段 | 降低什么 | 代价 |
| --- | --- | --- |
| KV Cache | 重复计算 | 显存占用，且变长序列会产生碎片 |
| PagedAttention（vLLM） | 解决 KV 显存碎片，提升并发 | 需要专门的推理引擎 |
| 量化（INT8 / INT4） | 权重与显存，提升吞吐 | 精度损失；权重量化（GPTQ/AWQ）成熟，激活量化更难 |
| 蒸馏 | 模型规模 | 需要训练教师-学生，能力有损 |
| 剪枝 | 冗余参数 | 结构稀疏不易加速，非结构化稀疏需专用硬件 |
| 投机解码 | 用草稿模型猜、大模型验，一次接受多个 token | 需要额外草稿模型 |
| 连续批处理 | 不等整批结束就插入新请求 | 需引擎支持（vLLM / TGI） |

**推理服务的三个关键指标**要分清：`TTFT`（首 token 延迟，影响"感觉快不快"）、`TPOT`（每 token 时间，影响"读得快不快"）、`吞吐`（tokens/s，影响"能服务多少人"）。三者互相制约：批处理提高吞吐但拉高 TTFT。

## 3.4 长上下文方案

限制来自两方面：注意力 `O(n²)` 的计算成本，以及训练时的长度上限（超出后位置编码失效、性能骤降）。

| 方案 | 思路 |
| --- | --- |
| 位置插值 / NTK 缩放 / YaRN | 调整位置编码的频率或缩放区间，让模型"理解"超出训练长度的位置 |
| ALiBi | 用线性衰减的偏置代替位置编码，外推性天然更好 |
| 滑窗 / 稀疏注意力 | 每个 token 只看局部窗口 + 少量全局 token，把复杂度降到 `O(n·w)` |
| 分块 + 检索 | **把长文本问题转化为 RAG 问题**：切成块分别嵌入，只把相关块放进上下文 |
| 状态空间模型（Mamba 等） | 用线性复杂度的递推结构替代注意力 |

**工程上的建议**：显式扩上下文（改 RoPE 缩放）代价高、效果常打折；而实际业务里"长文本"多数场景真正需要的只是其中一小段——**先考虑检索，再考虑扩窗**。

## 3.5 开源模型选型

选型不是选榜单第一，而是**在效果、成本、可运维性之间找平衡点**：

| 维度 | 要问的问题 |
| --- | --- |
| 语言能力 | 中文语料占比、中文长尾任务表现（金融术语、古汉语、合同表述） |
| 许可证 | 是否允许商用、有无 MAU 或场景限制、衍生模型是否受限 |
| 上下文长度 | 训练长度 vs 实际可用的有效长度（名义 128K 不等于 128K 都好用） |
| 部署成本 | 权重显存 + KV 显存，决定单卡/多卡与并发上限 |
| 微调生态 | 社区 LoRA 是否丰富、chat template 是否规范、工具链支持 |
| 可私有化 | 能否完全离线部署（强监管场景往往是硬性要求） |
| 生态与维护 | 版本迭代频率、社区问题响应、是否有量化版本 |

**一个务实的判断顺序**：先看许可证和私有化要求（一票否决项），再看中文效果是否达标，最后才在候选里按成本和吞吐挑选。

# 四、RAG：把知识从参数里拿出来

RAG（Retrieval-Augmented Generation）的核心思想是：**不要指望模型记住事实，而是把事实查出来给它**。

![RAG 双链路：离线完成文档解析、切片、嵌入与入库；在线完成查询改写、混合召回、重排、上下文组装与生成，向量库同时承载向量、元数据与权限标签](/images/blog/ai-engineering-knowledge-map/rag-pipeline.svg)

## 4.1 完整链路

**离线索引**：文档加载 → 解析（PDF / Word / 表格 / 扫描件 OCR）→ 清洗去噪 → 切片 → 嵌入 → 入库（向量 + 元数据 + 权限标签）

**在线问答**：查询改写 / 扩展 → 混合召回 → 重排 → 上下文组装 → 生成 → 引用溯源

**金融场景里最容易出问题的是第一步**。真实的业务文档是 PDF 合同、带合并单元格的表格、多栏排版、扫描件——解析质量直接决定后面所有环节的上限。表格被按字符切成碎片、条款编号和内容分离，检索阶段再怎么优化也救不回来。**解析环节的投入回报率远高于换嵌入模型**。

## 4.2 为什么能缓解幻觉，但又不能消除

**缓解的原因**有三个层次：

1. 把任务从"回忆"变成"阅读理解"——模型不需要从参数里检索事实，只需理解给定上下文并归纳
2. 提供**出处**，答案可核查、可追责
3. 知识可更新——改文档即可生效，不需要重训模型

**但不能消除**，因为幻觉的入口更多了：

| 失败环节 | 表现 |
| --- | --- |
| 召回失败 | 正确文档根本没被检索出来（知识不在库 / 切片切断了语义 / 术语不匹配） |
| 排序失败 | 正确文档在 Top-50 里，但没进 Top-5 |
| 生成失败 | 上下文里有答案，模型仍按旧参数知识作答，或过度外推 |
| 上下文冲突 | 多个版本制度并存，模型取错了版本或混着答 |
| 权限越界 | 召回了用户无权访问的文档 |

**治理幻觉的标准动作**：强制引用（答案必须标注来源片段）、无法回答时明确拒答（而不是强行编）、关键结论做交叉验证、输出侧做规则校验（数字、日期、金额格式）。

## 4.3 切片策略

切片的本质矛盾：**切得小检索准，切得大上下文全**。

| 策略 | 说明 |
| --- | --- |
| 固定长度 + 重叠 | 最基础；重叠 10%~20% 避免语义在边界被切断 |
| 结构感知 | 按标题、段落、列表、表格、代码块切，保留文档层级 |
| 父子切片（small-to-big） | 用**子块**（小）做检索保证精度，命中后返回**父块**（大）给模型保证上下文完整——实践中效果提升明显 |
| 语义切片 | 按句子嵌入的相似度断点切分，成本较高 |

**Chunk 大小怎么选**：常见起点 256~512 token。金融合同、条款类文档上下文依赖强，倾向于更大的块或用父子方案；FAQ、参数表这类自包含内容可以更小。**没有普适值，要用真实查询做召回率评测来定**。

## 4.4 检索：混合召回与重排

单一向量召回的问题是**专有名词、编号、代码、精确短语**表现差——语义相似的"基金份额登记"和"股份登记"在向量空间很近，但业务上完全不同。标准做法是混合召回：

```text
最终得分 = 归一化后的向量相似度 + 归一化后的 BM25 关键词得分
```

或者更稳健的 **RRF（Reciprocal Rank Fusion）**：不比较不同类型的分数，只比较排名，`score = Σ 1/(k + rank_i)`，避免了不同打分体系量纲不一致的问题。

**重排（Rerank）**是性价比最高的优化之一。召回阶段用双塔（Bi-Encoder）——查询和文档分别编码，可以离线建索引，快但精度有限；重排阶段用 Cross-Encoder——查询和文档拼在一起过模型，精度高但必须在线计算：

| 阶段 | 模型结构 | 候选规模 | 目标 |
| --- | --- | --- | --- |
| 召回 | 双塔 / BM25 / 混合 | 全库 → Top 50~100 | 高召回率、低延迟 |
| 重排 | Cross-Encoder | Top 50 → Top 5~10 | 高精度 |

**顺序不能反**：Cross-Encoder 无法离线索引，对全库做重排的延迟不可接受。

其余要点：

- **查询改写**：多轮对话里的指代消解（"它的额度是多少"里的"它"指什么）必须在检索前解决，否则召回必然失败；HyDE（先让模型生成假想答案再检索）、多查询扩展适合口语化提问。
- **元数据过滤**：按时间、机构、产品、文档类型过滤，能显著降低噪声。
- **权限必须在检索层过滤**，而不是生成后过滤——后者意味着无权内容已经进了模型上下文，既可能泄漏也可能被复述出来。

## 4.5 向量库选型

| 方案 | 特点 | 适用 |
| --- | --- | --- |
| FAISS | 是**库**不是服务，无持久化、无分布式、无权限模型 | 离线实验、小规模、嵌入式 |
| Milvus | 分布式、多索引类型、标量过滤、云原生 | 大规模在线服务 |
| Elasticsearch | 已有 ES 生态时最省事，8.x 起原生 kNN，混合检索天然一体 | 已有 ES、需要混合检索 |
| pgvector | 与关系数据同库，享受事务与一致性，运维成本最低 | 中小规模、强一致要求 |

选型先问三个问题：**数据量级、是否已有基础设施、权限与一致性要求**。多数中小规模场景用 pgvector 或 ES 就够了，上 Milvus 反而增加运维负担。

**高并发下的检索优化**：

- 索引类型：HNSW 查询快、内存占用高、构建慢；IVF 内存小、需要调 `nprobe`；实际常见组合是 IVF + PQ 做粗排、HNSW 做精确层
- 参数调优：`ef_search` / `nprobe` 越大召回越高、延迟越大——**用召回率-延迟曲线找拐点，而不是拍脑袋设值**
- 量化：标量量化（SQ）、乘积量化（PQ）压缩内存，代价是精度
- 架构：分片（水平扩容量）+ 副本（提升并发与可用性）；热点数据放缓存

# 五、Agent：从回答问题到完成任务

Agent 可以拆成五个部分：**模型（决策核心）+ 规划（拆解任务）+ 记忆（短期上下文 / 长期知识）+ 工具（对外行动能力）+ 反思（校验与纠错）**。

## 5.1 核心组件与常用框架

| 组件 | 内容 |
| --- | --- |
| 规划 | ReAct（推理-行动交替）、Plan-and-Execute（先规划再执行）、反思与重试 |
| 工具 | Function Calling、MCP（模型上下文协议，统一工具接入）、代码执行、检索、HTTP API |
| 记忆 | 短期：对话上下文；长期：向量库/知识图谱；工作记忆：任务中间状态 |
| 执行 | 工具调用编排、结果解析、错误处理、终止条件 |

框架的定位差异：

- **LangChain**：以"链"和组件抽象为中心，生态最全（Retriever、Memory、Tool、OutputParser），适合快速搭建 RAG 与工具型应用；抽象层多，调试链路长是常见吐槽点。
- **AutoGen**：以多智能体对话为中心，提供 `GroupChat`、角色分工与对话编排，适合模拟"多方协作"的任务。

## 5.2 Multi-Agent 架构

常见拓扑：

| 模式 | 结构 | 适用 |
| --- | --- | --- |
| 编排者-工作者 | 一个主 Agent 拆任务，分发给专职子 Agent | 任务可清晰分解（检索 / 计算 / 写作） |
| 辩论/评审 | 多个 Agent 给出方案后互相评审 | 需要提高可靠性、降低单点偏差 |
| 流水线 | 按固定顺序传递（解析 → 抽取 → 校验 → 汇总） | 流程确定的业务 |

**多智能体的真实难点不在架构图，而在工程**：上下文如何在 Agent 之间传递（全量传会爆窗口和成本）、一个 Agent 的错误如何不向下游传播、如何设计终止条件避免无限循环、以及 token 成本随 Agent 数量与轮次快速上升。

## 5.3 强监管场景下 Agent 的边界

这是最能体现判断力的地方。核心原则：**Agent 的输出可以影响决策，但不能直接执行不可逆的资金与合规动作**。

- **人在环路（Human-in-the-loop）**：高风险动作（转账、授信审批、合同签署）由 Agent 给出建议与依据，人工确认后执行
- **最小权限 + 白名单**：工具只开放必要能力，参数做严格校验，禁止开放任意 SQL / Shell
- **确定性兜底**：金额计算、利率、期限这类必须精确的环节走规则引擎或代码，不交给模型
- **全链路审计**：每次工具调用记录输入、输出、模型版本、耗时，可回放
- **Prompt 注入防御**：检索到的文档内容属于**不可信输入**，其中可能包含"忽略之前的指令"这类攻击文本，需要隔离与转义，工具调用前做二次确认

# 六、微调：SFT、LoRA 与 QLoRA

## 6.1 先建立正确顺序

**Prompt 工程 → RAG → 微调**，这个顺序不能反：

| 问题类型 | 解法 |
| --- | --- |
| 模型不知道这个事实 | RAG（补知识） |
| 模型知道但格式不对、口吻不对、总跑偏 | 微调（改行为） |
| 知识更新频繁 | RAG（改文档即生效，微调要重训） |

**微调改的是"风格与格式"，RAG 补的是"事实"**。用微调去注入频繁变动的知识，是一个代价高、更新慢的错误选择。

## 6.2 全量微调与 LoRA 的成本差异

![微调显存对比：全量微调中梯度与 Adam 优化器状态占大头，约为权重本身的 5 倍；LoRA 冻结基座、只训练低秩增量，可训练参数降到 0.1%~1%](/images/blog/ai-engineering-knowledge-map/lora-vs-full.svg)

**混合精度全量微调下，每个参数大约需要 12~16 字节**：

```text
权重（fp16）    2 字节
梯度            2 字节
Adam 一阶矩     4 字节（fp32）
Adam 二阶矩     4 字节（fp32）
──────────────
小计           12 字节/参数    # 若保留 fp32 主权重，还要再 +4
```

一个 7B 模型就是 `7 × 10⁹ × 12 ≈ 84 GB`——**显存大头是梯度与优化器状态（约为权重的 5 倍），而不是权重本身**。这就是全量微调必须多卡的直接原因。（上图为参数相关显存，未计入激活值——激活值与 batch、序列长度相关，可用梯度检查点大幅降低；数值为量级示意。）

**LoRA 的洞察是：微调时权重的变化量是低秩的**。

```text
原冻结权重  W₀ ∈ R^(d×k)   保持不变
增量        ΔW = B·A，其中 B ∈ R^(d×r), A ∈ R^(r×k), r ≪ min(d,k)
前向        h = W₀x + (α/r)·B·A·x
```

`A` 用高斯分布随机初始化，`B` 初始化为零，保证训练开始时 `ΔW = 0`，不破坏基座能力。可训练参数量从 `d×k` 降到 `r×(d+k)`——`r = 16` 时通常只占原模型的 0.1%~1%。

**LoRA 的真实显存优势要说得准确**：它省掉的是**梯度与优化器状态**（只对 A、B 计算），基座权重仍需常驻显存，**激活值也依然存在**——所以 batch 和序列长度开大时 LoRA 一样会 OOM。只强调"LoRA 显存只要几 GB"是不严谨的。

**QLoRA 在此基础上再加三层**：

| 技术 | 作用 |
| --- | --- |
| 4-bit NF4 量化基座 | 基座显存再降约 4 倍（NF4 是针对正态分布权重的信息论最优 4 位表示） |
| 双重量化 | 对量化常数本身再量化，再省约 0.5 bit/参数 |
| 分页优化器 | 显存尖峰时把优化器状态换出到内存，用时间换空间 |

三者叠加使得单张 48 GB 显卡微调 65B 模型成为可能（原论文的实验配置），代价是训练速度下降（约 2~4 倍）。

## 6.3 实践要点

| 超参 | 经验 |
| --- | --- |
| `r`（秩） | 8~64。任务越复杂、与基座分布差异越大，需要的秩越高；盲目加大只见显存涨不见效果涨 |
| `alpha` | 常见设为 `r` 或 `2r`，与 `r` 联动控制缩放 |
| `target_modules` | 至少覆盖注意力的 q/k/v/o；效果不够再扩展到 FFN 的 gate/up/down |
| `dropout` | 小数据集上用 0.05~0.1 防过拟合 |
| 学习率 | 通常比全量微调大一个量级（1e-4 ~ 3e-4） |

其余经验：

- **数据质量远比数量重要**。几百到几千条高质量、格式统一、覆盖边界情况的样本，效果常好于十万条噪声数据。
- **警惕灾难性遗忘**：微调过度会让模型在通用任务上退化。缓解手段是混入一定比例的通用数据、降低学习率、控制训练轮数。
- **格式一致性是硬要求**：训练数据的 chat template 必须与推理时完全一致，否则模型学到的是"另一种对话格式"。
- **微调后必须做回归评测**：除了目标任务，还要跑一遍通用能力、拒答能力、安全对齐的评测集，确认没有退化。

# 七、工程化与部署

模型效果只在实验环境成立、上线就崩，绝大多数原因在工程侧。

## 7.1 模型服务化

| 方案 | 定位 | 特点 |
| --- | --- | --- |
| **Triton Inference Server** | 通用推理服务 | 支持多框架（TensorRT/PyTorch/ONNX）、动态批处理、模型集成、多实例并发；配置驱动 |
| **vLLM** | LLM 专用 | PagedAttention + 连续批处理，当前 LLM 高吞吐事实标准；OpenAI 兼容接口 |
| **TGI** | LLM 专用 | HuggingFace 出品，量化与流式支持好 |
| **TorchServe** | PyTorch 原生 | 与 PyTorch 生态贴合，功能相对基础 |
| **自研 FastAPI 封装** | 灵活 | 可控性最高，但批处理、显存管理、并发调度全要自己做，**不建议** |

**选择逻辑**：LLM 用 vLLM/TGI（推理引擎已经解决了 KV 显存和批处理）；传统模型和 CV 模型用 Triton（多框架统一托管）。

## 7.2 推理优化与显存排查

**显存构成拆解**——排查 OOM 的第一步：

```text
权重            = 参数量 × dtype 字节数（fp16 → 2）
KV Cache        = 2 × layers × heads × head_dim × seq_len × batch × dtype_bytes
激活值          = 与 batch、序列长度正相关（推理时远小于训练）
框架与碎片       = CUDA 上下文、中间缓冲、显存碎片
```

**OOM 的常见根因与对策**：

| 现象 | 根因 | 对策 |
| --- | --- | --- |
| 并发一上来就 OOM | KV Cache 随并发线性增长 | 限制最大并发、限制 `max_model_len`、启用分页注意力 |
| 偶发 OOM | 显存碎片 | PagedAttention、预分配显存池、固定 `gpu_memory_utilization` |
| 长请求 OOM | 单条超长序列 | 截断或分块、限制单请求最大长度 |
| 显存没满却 OOM | 碎片或缓存未释放 | 分析 `torch.cuda.memory_summary()`，区分 reserved 与 allocated |

**一个常被忽略的稳定性问题**：**模型加载慢**。大模型加载动辄几分钟到十几分钟，如果按常规方式配探针，`livenessProbe` 会在加载完成前就把容器判定为失败并重启，形成"加载 → 被杀 → 再加载"的死循环。正确做法是配置 `startupProbe` 给足时间（见高可用相关实践），并让 `readinessProbe` 在模型就绪前返回失败。

## 7.3 Kubernetes 上的 AI 服务

AI 服务部署在 K8s 上有几个和普通微服务显著不同的点：

- **GPU 调度**：依赖 NVIDIA Device Plugin 把 GPU 注册为可调度资源；多卡任务要理解整卡分配与 MIG/MPS 虚拟化的差异
- **扩缩容不能只看 CPU**：GPU 服务的瓶颈在显存和队列，应按**请求队列长度或 GPU 利用率**做自定义指标扩缩容
- **冷启动代价极高**：模型加载几分钟，决定了**不能像无状态服务那样激进缩容**。实践中常保留最小副本数作为预热池，牺牲成本换响应
- **优雅停机**：终止前必须等在途推理请求返回，否则长请求会被拦腰截断；`terminationGracePeriodSeconds` 要按最长请求耗时设置
- **镜像巨大**：模型权重会让镜像到 GB 级，需要镜像预热、P2P 分发或把权重放独立存储卷（用 InitContainer 或 CSI 挂载）

## 7.4 版本管理与实验追踪

MLflow 这类工具解决的是**可复现性**问题，包含三块能力：

| 能力 | 内容 |
| --- | --- |
| 实验追踪 | 每次运行的超参、指标、代码 commit、数据版本 |
| 模型注册 | 模型版本管理、阶段流转（Staging → Production → Archived） |
| 产物管理 | 模型文件、环境依赖、评估报告的归档 |

**关键原则：模型版本必须与数据版本、代码版本、特征版本绑定**。只记录模型文件，几个月后无法复现、无法解释、无法审计——这在强监管场景是硬伤。

## 7.5 数据流水线与消息队列

**消息队列在 AI 系统里的四个作用**：

1. **异步推理**：长任务（文档解析、大模型生成）通过队列异步化，前端立即返回任务 ID
2. **削峰**：训练数据倾斜、批量推理的突发流量用队列缓冲，消费端匀速处理
3. **解耦**：上游数据生产与下游模型消费解耦，各自独立演进、独立扩缩容
4. **可靠重试**：失败进入重试队列与死信队列，保证数据不丢（配合幂等消费）

**流式特征与训练-服务偏斜（Training-Serving Skew）**是这一层最隐蔽的坑：离线训练用批处理 SQL 算特征，线上推理用另一套代码实时算——两套逻辑的边界条件、时间窗口、空值处理稍有差异，模型在线上的表现就会莫名下降。**根本解法是特征计算逻辑只写一份**（特征平台 / 特征库），离线与在线共用同一个定义。

## 7.6 灰度发布与 A/B 测试

| 方式 | 做法 | 适用 |
| --- | --- | --- |
| 影子流量 | 复制线上流量给新模型，不回传结果 | 验证稳定性与延迟，零风险 |
| 金丝雀 | 小比例流量走新模型，观察后逐步放量 | 通用的上线方式 |
| A/B 测试 | 随机分流，对比业务指标 | 验证效果增益 |
| 交错实验 | 同一用户同时体验两个模型的结果 | 样本效率高，适合排序场景 |

**A/B 测试设计的三个前提**：分流随机且稳定（同一用户始终在同一组）、样本量足够（按最小可检测效应反推）、**只对比一个变量**。模型效果指标（AUC、准确率）与业务指标（通过率、坏账率、转化率）都要看，且要预注册关注指标，避免事后挑指标。

# 八、监控与漂移治理

模型上线不是终点。**效果衰减是必然的，问题只是发现得早还是晚**。

## 8.1 两类漂移

| 类型 | 定义 | 表现 |
| --- | --- | --- |
| 数据漂移（Covariate Shift） | 输入分布 `P(x)` 变了，`P(y|x)` 没变 | 特征 PSI 上升，模型仍"逻辑正确"但外推到没见过的区域 |
| 概念漂移（Concept Shift） | 输入与输出的关系 `P(y|x)` 变了 | 特征分布正常，但模型预测准确率下降（如政策调整后同样的客户风险变了） |

两者的监控手段不同：前者靠**输入层监控**（PSI、分布对比），后者只能靠**结果层监控**（需要标签回传）。

## 8.2 分四层监控

| 层次 | 指标 |
| --- | --- |
| 系统层 | QPS、P99 延迟、错误率、GPU 利用率、显存、队列积压 |
| 数据层 | 各特征 PSI、缺失率、取值域越界、文本长度/语言分布、检索命中率 |
| 模型层 | 预测分布 PSI、滚动窗口 AUC/KS、置信度分布、拒识率、幻觉率（抽样人工评估） |
| 业务层 | 通过率、坏账率、转化率、人工复核推翻率、客诉量 |

**标签滞后是风控监控的核心难题**：违约标签可能要在放款后 6~12 个月才完整，等标签回来再发现问题就太晚了。应对方式：

- 用**代理指标**（早期逾期率 M1、人工复核推翻率）作为前哨
- 用**无标签指标**（预测分数分布一致性、特征 PSI）做早期预警
- 小流量**人工抽检**，对高风险样本直接核对

## 8.3 漂移的处理闭环

```text
监控 → 告警 → 分级处置 → 复盘 → 迭代
```

这个闭环不是监控一个环节的事，而是贯穿模型全生命周期：数据准备、训练调参、离线评估、灰度发布、线上监控、重训与回滚，每一环的输出都是下一环的输入。

![模型全生命周期闭环：数据准备与特征开发、训练与调参、离线评估与审批、灰度发布与 A/B、线上监控与漂移告警、重训与回滚，形成监控到迭代的闭环](/images/blog/ai-engineering-knowledge-map/model-lifecycle.svg)

处置动作按严重程度分级：

| 级别 | 动作 |
| --- | --- |
| 轻微（PSI 0.1~0.25） | 记录、加密度监控、排查具体特征 |
| 中等 | 调整阈值、检查数据管道、准备重训 |
| 严重（PSI > 0.25 且业务指标恶化） | **回滚到上一版模型**，同时紧急重训 |

**回滚能力必须在设计阶段就具备**：模型版本可切换、流量可快速切回、上一版模型保持可服务。没有回滚通道的"监控"只能发现问题，不能解决问题。

# 九、可解释性与模型审计

## 9.1 三类可解释性

| 类型 | 方法 | 回答的问题 |
| --- | --- | --- |
| 内在可解释 | LR、决策树、评分卡、规则 | 模型本身就是解释 |
| 全局解释 | 特征重要性、PDP（部分依赖图）、SHAP 汇总图 | 整体上哪些特征在起作用 |
| 局部解释 | SHAP 单样本、LIME、反事实解释 | **这一笔**为什么被拒 |

**强监管场景下"局部解释"往往比"全局解释"更重要**——监管和客户关心的是"我的这笔申请为什么被拒"，而不是"模型整体上重视收入"。这也是**反事实解释**（"如果收入提高 2000 元，结果会变为通过"）在金融场景特别受欢迎的原因：它能直接转化成对客户的可执行建议。

## 9.2 SHAP 与 LIME

**SHAP** 基于合作博弈论的 Shapley 值，把预测值分配到各特征上，满足几条良好性质：

| 性质 | 含义 |
| --- | --- |
| 局部准确性 | 所有特征的贡献之和 = 预测值 − 基线值 |
| 缺失性 | 未参与的特征贡献为 0 |
| 一致性 | 模型对该特征的依赖增强，归因不会反而下降 |

**TreeSHAP** 对树模型有精确的多项式时间算法，这让 SHAP 在 GBDT 上非常实用。

**需要知道的局限**：特征相关时，Shapley 值会在相关特征间"分摊"贡献，可能给两个高度相关的特征都分配中等的重要性，导致解释看起来不符合业务直觉。此时可以在去相关后的特征空间上计算，或结合业务分组做聚合归因。

**LIME** 在样本附近采样并拟合一个线性代理模型。优点是模型无关、速度快；缺点是**解释不稳定**——同一输入多次运行可能得到不同的解释，用于对外披露时需要固定随机种子并说明局限性。

**一条重要的边界**：解释不等于因果。SHAP 告诉你"模型使用了这个特征"，不告诉你"改变这个特征会改变结果"。要做策略调整，需要因果推断（如 Uplift 建模、DID）。

## 9.3 面向审计的设计

监管要求模型可审计时，需要的不是一份解释文档，而是**一套可复现的证据链**：

| 要素 | 内容 |
| --- | --- |
| 模型卡 | 用途、适用范围、训练数据描述、已知局限、评估结果 |
| 版本绑定 | 模型 + 代码 + 数据 + 特征 + 阈值，五者版本号绑定在一起 |
| 决策日志 | 每次预测落盘：输入特征快照、模型版本、输出分数、阈值、最终决策 |
| 特征血缘 | 每个特征从源头表到模型输入的完整加工链路 |
| 评估留档 | 上线前的评估报告（含分群表现、公平性指标）、上线后的定期复评 |
| 变更审批 | 每次模型变更的审批记录与回滚预案 |
| 可复现性 | 给定版本号，能重新跑出完全一致的评估结果 |

**核心一句话：决策可追溯 = 模型版本 + 特征快照 + 阈值版本，三者缺一不可**。只记录分数而没记录当时的特征，事后无法解释；只记录特征而没有版本号，无法复现。

# 十、数据安全与合规

## 10.1 通用原则

- **最小必要**：只采集业务必需的数据，能不用个人信息就不用
- **目的限制**：采集时声明的用途不能随意扩展
- **分级分类**：按敏感级别制定不同的访问与加密策略
- **全链路加密**：传输 TLS、存储加密、敏感字段级加密或令牌化
- **环境隔离**：测试、开发环境不得使用生产明文数据
- **可删除**：支持数据主体的删除请求，且删除要覆盖备份与派生数据

## 10.2 大模型带来的新风险

这是传统数据安全框架没能覆盖的部分：

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| **数据出域** | 调用外部 API 意味着数据离开可控边界 | 强监管场景优先私有化部署；确需外部调用则先脱敏 |
| **训练数据污染** | 客户数据被无意用于训练 | 明确数据使用边界，训练数据来源留痕 |
| **输出泄漏** | 模型可能复述训练数据中的敏感内容 | 输出侧过滤（正则 + 分类模型）、差分隐私训练 |
| **Prompt 注入** | 检索文档、用户输入中嵌入恶意指令，诱导越权操作 | 把外部内容视为不可信输入、工具最小权限、高危动作人工确认 |
| **不可遗忘** | 微调后的模型很难精确"忘记"某条数据 | 涉及个人信息时优先 RAG（删文档即生效），慎用微调注入敏感数据 |
| **权限旁路** | 检索层未做过滤，无权文档进入上下文 | **权限过滤必须在检索层完成**，与业务权限系统打通 |

**"不可遗忘"这一点值得单独强调**：RAG 架构下，删除一份文档即可让它从知识库消失；而一旦通过微调把知识写进参数，想精确移除几乎不可能（machine unlearning 仍不成熟）。**在涉及个人信息和强合规要求的知识注入场景，RAG 是比微调更负责任的选择**——这既是技术选择，也是合规选择。

# 十一、SQL 与代码

## 11.1 SQL 高频模式

**分组求 TopN**（最高频）：

```sql
-- 每个产品下销售额前三的客户
SELECT product_id, customer_id, amount
FROM (
  SELECT product_id, customer_id, amount,
         ROW_NUMBER() OVER (
           PARTITION BY product_id
           ORDER BY amount DESC
         ) AS rn
  FROM orders
  WHERE dt = '2026-09-01'
) t
WHERE rn <= 3;
```

**三个排名函数的区别必须说清**：

| 函数 | 并列时的行为 | 结果示例（值 100,100,90） |
| --- | --- | --- |
| `ROW_NUMBER()` | 强制唯一序号 | 1, 2, 3 |
| `RANK()` | 并列同名，**跳过后续名次** | 1, 1, 3 |
| `DENSE_RANK()` | 并列同名，**不跳名次** | 1, 1, 2 |

**组内去重取最新**：用 `ROW_NUMBER()` 按时间倒序取 `rn = 1`，比 `GROUP BY` + 子查询更高效。

**JOIN 的坑**：`LEFT JOIN` 后把右表条件写在 `WHERE` 里会**退化成 INNER JOIN**（因为过滤掉了右表为 NULL 的行），必须写在 `ON` 里。这是最经典的面试陷阱。

```sql
-- 错误：右表的条件放在 WHERE，左表未匹配行被过滤掉，等价于 INNER JOIN
SELECT * FROM users u LEFT JOIN orders o ON u.id = o.uid WHERE o.status = 'paid';

-- 正确：条件放在 ON 里，保留所有用户
SELECT * FROM users u LEFT JOIN orders o ON u.id = o.uid AND o.status = 'paid';
```

**索引优化要点**：最左前缀原则（联合索引 `(a, b, c)` 能被 `a`、`a,b`、`a,b,c` 使用，单独 `b` 用不上）、覆盖索引避免回表、**不要在索引列上做函数运算或隐式类型转换**（会让索引失效）、用 `EXPLAIN` 看 `type` / `key` / `rows` 判断是否走索引。

**其他高频**：`WHERE` 在分组前过滤、`HAVING` 在分组后过滤（聚合函数条件只能放 `HAVING`）；连续登录天数属于 gaps-and-islands 问题，思路是"日期 − 行号"构造分组键。

## 11.2 Python 要点与踩坑

| 话题 | 关键点 |
| --- | --- |
| 可变默认参数 | `def f(x=[])` 的默认值在函数定义时创建一次，跨调用共享——经典陷阱，应改用 `None` |
| 浅拷贝 vs 深拷贝 | `copy.copy` 只复制一层，嵌套对象仍共享引用；`deepcopy` 递归复制但慢 |
| 生成器 | `yield` 惰性求值，适合大文件/大结果集，**只能遍历一次**；相比列表不占内存 |
| 装饰器 | 本质是"接收函数返回函数"的高阶函数；用 `functools.wraps` 保留原函数元信息 |
| 并发模型 | GIL 使多线程无法并行执行 CPU 密集任务——**IO 密集用多线程/协程，CPU 密集用多进程** |
| 内存管理 | 引用计数 + 分代回收；循环引用需 gc；`__slots__` 可显著降低实例内存 |

**Pandas / NumPy 常见坑**：

- **链式赋值**：`df[df.a > 1]['b'] = 0` 修改的是副本，不生效且报 `SettingWithCopyWarning`；应使用 `.loc`
- **类型推断**：读入时 `object` 类型的内存占用远高于 `category`；数值列混入缺失值会被提升为 float
- **内存优化**：读大文件时指定 `dtype`、分块 `chunksize`、及时 `del` 与 `gc.collect()`
- **性能**：`apply` 逐行处理很慢，能用向量化或 `numpy` 表达就别用 `apply`；避免在循环里反复 `df.loc`
- **浮点精度**：`0.1 + 0.2 != 0.3`；金额计算用 `Decimal` 或整数分单位，不要用 float

# 十二、把知识串成能力

回到开头的问题——**模型指标好但业务指标不好**，排查顺序应该是：

1. **数据侧**：训练与线上特征是否一致（training-serving skew）？特征 PSI 是否异常？是否存在标签穿越？
2. **模型侧**：预测分数分布是否漂移？分群表现是否退化（某类客群被系统性误判）？
3. **策略侧**：决策阈值是否合理？模型分数到业务动作的映射有没有问题？
4. **业务侧**：外部环境是否变化（政策、市场）？还是业务指标本身的定义变了？

这个顺序本身就是一个能力清单：**数据 → 模型 → 策略 → 业务**，先向内查找再向外归因。

最后用四个词收束整篇的内容——在强监管行业，一个 AI 系统要上线，需要同时满足：

| 要求 | 依赖的知识 |
| --- | --- |
| **可解释** | 特征工程、SHAP/LIME、模型选型、反事实解释 |
| **可监控** | PSI/KS 指标、分层监控、标签滞后应对、告警分级 |
| **可回滚** | 版本管理、灰度发布、流量切换、模型注册阶段流转 |
| **可审计** | 决策日志、版本绑定、特征血缘、模型卡、审批留痕 |

**算法决定上限，工程决定下限，治理决定能不能上线。** 三者之中任何一环缺失，模型都只是实验室里的一个指标。
