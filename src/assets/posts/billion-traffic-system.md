「如何实现一套支持亿级次访问的系统」是系统设计面试的常客。它看起来在问架构，实际上在考四件事：

1. **你会不会把「亿级访问」翻译成可计算的 QPS、带宽、存储和连接数**
2. **你知不知道架构是演进的，不是一步到位的**
3. **你能不能说清每一层为什么存在、解决什么问题、付出什么代价**
4. **你有没有想过单点、故障、降级和成本**

先给结论：**亿级访问不是靠某一个中间件撑起来的，而是靠「分层 + 无状态 + 缓存 + 异步 + 分片 + 可观测」这一整套组合。** 没有哪一层能单独解决问题，也没有哪套架构可以脱离业务直接照搬。

# 一、先把「亿级访问」翻译成数字

## 1.1 三种口径，别混为一谈

「亿级次访问」至少要拆成三个指标：

| 口径 | 含义 | 例子 |
| --- | --- | --- |
| **PV** | 页面浏览量，包含静态资源请求 | 1 亿 PV/天 |
| **API 请求数** | 真正打到后端服务的动态请求 | 1 亿 API 调用/天 |
| **UV** | 独立用户数，决定会话和存储规模 | 1000 万 UV/天 |

它们的量级可能差一个数量级：一个 PV 可能包含几十个静态资源请求，但只有 1–3 个 API 请求；CDN 能挡掉 90% 以上的静态流量。所以面试时第一句话应该是：

> 「我先确认一下，这 1 亿是 PV、API 请求，还是用户数？静态和动态的比例大概是多少？」

不确认口径就直接算 QPS，是系统设计面试里最常见的减分项。

## 1.2 QPS 与峰值

日均 QPS 的公式很简单：

```text
平均 QPS = 日请求量 / 86400
峰值 QPS = 平均 QPS × 峰值系数
```

| 日请求量 | 平均 QPS | 峰值系数 3–5 倍 | 典型场景 |
| --- | --- | --- | --- |
| 1000 万 | 116 | 350–580 | 中小型业务 |
| 1 亿 | 1157 | 3500–5800 | 中大型 C 端 |
| 10 亿 | 11574 | 3.5 万–5.8 万 | 头部应用 |
| 100 亿 | 115740 | 35 万–58 万 | 超级 App / 平台 |

**峰值系数取决于业务形态**：资讯类早晚高峰明显，可能 3–5 倍；电商大促可能 10 倍以上；秒杀则是另一个量级（瞬时百倍），需要单独的秒杀架构，不能和常态架构混为一谈。

还要区分读写比例。典型 C 端业务读多写少（10:1 到 100:1），这意味着：

- 读路径靠**缓存 + 从库 + CDN** 扩展
- 写路径靠**分库分表 + 消息队列削峰**
- 不要用同一套容量假设对待读写

## 1.3 带宽、存储、连接数

**带宽**：

```text
日流量 = 日请求量 × 平均响应大小
平均带宽 = 日流量 / 86400
峰值带宽 = 平均带宽 × 峰值系数
```

假设 1 亿 PV、平均每个页面资源 2 MB：

```text
日流量 = 1 亿 × 2 MB = 200 TB
平均带宽 = 200 TB / 86400 s ≈ 2.31 GB/s ≈ 18.5 Gbps
峰值带宽 ≈ 55–92 Gbps（按 3–5 倍）
```

这就是为什么静态资源必须上 CDN：**没有 CDN，任何源站都扛不住这个带宽**。

**存储**：

```text
日增存储 = 日新增记录数 × 单条大小
总存储 = 日增存储 × 保留天数 × (1 + 索引/副本放大)
```

1 亿条/天、每条 1 KB，保留 1 年：

```text
原始数据 ≈ 36.5 TB
加索引、副本、备份，实际规划 100–150 TB
```

**连接数**：用利特尔法则估算并发：

```text
并发请求数 = QPS × 平均响应时间
```

1 万 QPS、平均 100 ms，就是 1000 个并发请求。这决定了线程池、连接池、Tomcat/Netty 的 worker 数量。**连接池不是越大越好**，数据库连接数受实例规格和内核参数限制，盲目调大只会把压力转移成锁竞争和上下文切换。

## 1.4 可用性：几个 9 意味着什么

| 可用性 | 年停机时间 | 月停机时间 | 架构要求 |
| --- | --- | --- | --- |
| 99.9%（3 个 9） | 8.76 小时 | 43.8 分钟 | 单机房 + 监控告警 |
| 99.99%（4 个 9） | 52.6 分钟 | 4.38 分钟 | 多可用区、自动故障转移 |
| 99.999%（5 个 9） | 5.26 分钟 | 26.3 秒 | 多地域、单元化、全链路演练 |

**可用性是设计出来的，不是监控出来的。** 先确定业务能接受几个 9，再决定要不要多活。3 个 9 的系统硬上多活，只会增加复杂度和故障面。

## 1.5 四个目标

| 目标 | 度量 | 主要手段 |
| --- | --- | --- |
| 高吞吐 | QPS、TPS | 无状态、水平扩展、缓存、异步、分片 |
| 低延迟 | P50/P95/P99 | 缓存、就近接入、减少跨网络调用、异步化 |
| 高可用 | 可用性、错误率 | 冗余、故障转移、熔断、降级、多活 |
| 低成本 | 单请求成本 | CDN、缓存命中率、弹性伸缩、冷热分离 |

这四个目标互相拉扯：加缓存降延迟但增加一致性复杂度；多活提高可用性但增加成本；异步提高吞吐但牺牲实时性。**架构设计就是在约束下做取舍。**

# 二、架构演进：不要一步到位

很多面试者一上来就画「微服务 + 分库分表 + 多活」，但说不清为什么。真实的系统是随着规模一步步演进的。

| 阶段 | 规模（QPS） | 关键动作 | 主要瓶颈 |
| --- | --- | --- | --- |
| 0 单机 | < 1k | 一台服务器跑应用 + 数据库 | CPU、磁盘、单点 |
| 1 应用/数据库分离 | 1k–5k | 独立 DB、负载均衡、会话外置 | 数据库连接、应用单点 |
| 2 缓存 + 读写分离 | 5k–2 万 | Redis、从库、CDN | 缓存一致性、主从延迟 |
| 3 无状态 + 水平扩展 | 2 万–10 万 | 多实例、网关、MQ、服务拆分 | 数据库写入、服务治理 |
| 4 分片 + 多级缓存 | 10 万–100 万 | 分库分表、本地缓存、搜索/OLAP | 跨分片、热点、运维复杂度 |
| 5 多活 / 单元化 | 100 万+ | 多地域、流量调度、单元化 | 数据同步、一致性、成本 |

![亿级访问系统的架构演进：从单机、应用与数据库分离、缓存与读写分离，到无状态水平扩展、分库分表和多活单元化，每一步都由当前瓶颈驱动](/images/blog/billion-traffic-system/traffic-evolution.svg)

**演进的核心逻辑：先解决当前最大的瓶颈，再考虑下一层。** 在 1000 QPS 时上分库分表，除了增加故障面，没有任何收益；在 10 万 QPS 时还靠单库，加多少应用实例都没用。

# 三、全局架构

## 3.1 分层职责

| 层 | 职责 | 关键技术 | 扩展方式 |
| --- | --- | --- | --- |
| DNS / GSLB | 就近接入、地域容灾、流量调度 | 智能 DNS、HTTPDNS | 多线路、多地域 |
| CDN | 静态资源、边缘缓存、动态加速 | 边缘节点、回源策略 | 多 CDN 厂商 |
| WAF / DDoS | 安全防护、恶意流量清洗 | 规则引擎、流量清洗 | 云防护 |
| 负载均衡 | 四层/七层转发、健康检查 | LVS、HAProxy、Nginx、云 SLB | 多实例 + VIP |
| API 网关 | 鉴权、限流、路由、灰度、日志 | APISIX、Kong、Spring Cloud Gateway | 水平扩展 |
| BFF | 面向端的聚合与裁剪 | GraphQL、聚合服务 | 按端拆分 |
| 业务服务 | 领域逻辑、无状态 | RPC、HTTP | 水平扩展 |
| 缓存 | 热点读、会话、计数 | 本地缓存 + Redis Cluster | 分片、多副本 |
| 消息队列 | 异步、解耦、削峰 | Kafka、RocketMQ、RabbitMQ | 增加分区/消费者 |
| 数据库 | 持久化、事务 | MySQL/PostgreSQL + 分库分表 | 读写分离、分片 |
| 搜索 / OLAP | 检索、分析 | Elasticsearch、ClickHouse、Doris | 分片、副本 |
| 对象存储 | 图片、视频、文件 | OSS / S3 / MinIO | 无限扩展 |
| 可观测 | 指标、日志、链路 | Prometheus、ELK、Jaeger | 采样、分层存储 |

## 3.2 一次请求的路径

```text
用户
 → DNS / HTTPDNS（就近接入）
 → CDN（静态资源直接返回）
 → WAF（清洗恶意流量）
 → 负载均衡（四层）
 → 网关（鉴权、限流、路由、灰度）
 → BFF / 业务服务（无状态，多实例）
 → 本地缓存 → Redis → 数据库 / 搜索 / 下游服务
 → 消息队列（异步落库、通知、积分等）
 → 返回结果
```

**每一层都应该能独立扩展、独立降级。** 如果某一层不能水平扩展，它就是整个系统的天花板。

# 四、接入层：把流量挡在核心之外

## 4.1 DNS 与 GSLB

- **地理调度**：华北用户解析到华北机房，降低 RTT
- **健康检查**：机房故障时自动摘除解析
- **HTTPDNS**：绕过 LocalDNS 劫持和缓存，适合移动端
- **多线路**：电信、联通、移动分别解析

注意 DNS 的 TTL 和客户端缓存：故障切换不是实时的，TTL 太长会导致流量切不走。关键业务要做**客户端重试 + 多域名备用**。

## 4.2 CDN

CDN 是亿级访问的第一道放大器：

- 静态资源（JS/CSS/图片/视频）尽量长缓存，用内容哈希做版本
- 动态接口可以做动态加速（回源优化、连接复用），但不要缓存用户私有数据
- 缓存 key 要设计好，避免把用户维度的数据缓存成公共数据
- 回源要限流、加锁，防止缓存击穿把源站打垮
- 发布时按版本刷新，不要全量 purge

**目标缓存命中率：静态资源 95% 以上。** 命中率每下降一个点，源站带宽和 QPS 都会成比例上升。

## 4.3 WAF 与 DDoS

- 网络层 DDoS 靠云清洗、流量调度
- 应用层 CC 攻击靠限流、人机校验、行为风控
- WAF 规则要能灰度，避免误杀正常用户
- 重要接口做签名、防重放、防篡改

## 4.4 负载均衡

- **四层（LVS）**：性能高，适合入口
- **七层（Nginx/HAProxy）**：能做路径路由、灰度、限流
- **健康检查**：主动探活 + 被动摘除
- **会话保持**：尽量不做，改用无状态 + 共享会话
- **一致性哈希**：缓存类场景可用，但扩缩容会导致部分 key 迁移

负载均衡自身也要高可用：多实例 + VIP/Anycast，避免成为单点。

## 4.5 API 网关

网关是南北向流量的统一入口，通常承担：

| 能力 | 说明 |
| --- | --- |
| 鉴权 | JWT、OAuth2、签名校验 |
| 限流 | 按 IP、用户、接口、租户多维限流 |
| 路由 | 按路径/Header/灰度标签路由 |
| 熔断 | 下游错误率超阈值快速失败 |
| 日志与追踪 | 统一 traceId、访问日志 |
| 协议转换 | HTTP ↔ gRPC、内外网隔离 |

**限流要分层**：网关做粗粒度保护，服务内部做细粒度配额，数据库层用连接池和小事务兜底。只靠网关限流，内部调用和重试仍可能打垮下游。

# 五、服务层：无状态才能水平扩展

## 5.1 无状态是水平扩展的前提

有状态的服务无法简单地「加机器」，因为请求必须落到持有对应状态的实例上。要做到无状态：

| 状态 | 外置方案 |
| --- | --- |
| 登录会话 | JWT（无状态令牌）或 Redis 共享会话 |
| 本地文件 | 对象存储（OSS/S3） |
| 本地缓存 | 只缓存可重建的数据；跨实例失效用广播 |
| 定时任务 | 分布式调度（XXL-JOB、K8s CronJob）+ 分布式锁 |
| 序列号/计数器 | Redis / 数据库号段 / 雪花算法 |
| WebSocket 连接 | 网关按连接 id 路由，或使用消息总线 |

**本地缓存是无状态里的例外**：它能极大提升性能，但会带来实例间不一致。只缓存变化少、可容忍短暂不一致的数据，并设计主动失效通道。

## 5.2 水平扩展与弹性

- 无状态服务 + 负载均衡 = 加机器就能扩容
- K8s HPA 按 CPU、QPS、自定义指标扩缩容
- 扩容要预热：JIT、连接池、缓存、配置加载
- 缩容要优雅：先摘流量、等待在途请求、再关闭
- 设置合理的 `minReplicas`，避免冷启动扛不住突发流量

## 5.3 服务拆分

拆分的依据是**业务边界和变化频率**，不是「越小越好」：

- 按领域拆分（DDD 限界上下文）
- 按读写分离/扩缩容需求拆分
- 按团队边界拆分（康威定律）
- 按故障隔离需求拆分（核心/非核心）

**拆得太细的代价**：网络调用变多、链路变长、分布式事务、联调成本、故障定位困难。单体在早期往往更高效，等团队和流量都上来再拆。

## 5.4 超时、重试、熔断、隔离

这是服务层稳定性的四件套：

```text
超时：每个 RPC 都必须有连接超时和读超时，不能无限等待
重试：只重试幂等操作，指数退避 + 抖动，限制重试次数
熔断：下游错误率/慢调用比例超阈值，快速失败一段时间
隔离：线程池/连接池/信号量按依赖隔离，避免一个下游拖垮全部
```

**重试是放大器**：下游已经过载时，无节制重试会把 1 倍流量变成 3 倍。必须配合熔断、退避和重试预算（retry budget）。

## 5.5 分布式 ID 与幂等

**分布式 ID** 的常见方案：

| 方案 | 特点 | 注意 |
| --- | --- | --- |
| 雪花算法 | 趋势递增、性能高 | 时钟回拨、workerId 分配 |
| 号段模式 | 批量取号、DB 压力小 | 号段耗尽预取、服务重启浪费 |
| Redis INCR | 简单 | 依赖 Redis、持久化 |
| UUID | 本地生成、无依赖 | 无序、索引写入差、占空间 |

**幂等**是分布式系统的必修课：

- 接口层：`requestId` + Redis `SET NX`
- 数据库层：业务唯一键 + 唯一索引
- 状态机：条件更新，防止重复流转
- 消息消费：先查后写，重复消息直接 ACK

幂等要做到「**每一层都假设上一层会重复**」，不能只依赖一个 Redis 标记。

# 六、缓存：亿级读流量的主战场

## 6.1 多级缓存

![多级缓存：浏览器、CDN、Nginx、应用本地缓存、Redis、数据库按距离和成本分层，越靠近用户越快、容量越小](/images/blog/billion-traffic-system/cache-hierarchy.svg)

| 层级 | 容量 | 速度 | 一致性 | 适合 |
| --- | --- | --- | --- | --- |
| 浏览器 | 小 | 最快 | 弱 | 静态资源、公开数据 |
| CDN | 大 | 快 | 弱（可刷新） | 静态资源、边缘动态缓存 |
| Nginx | 中 | 快 | 中 | 热点接口响应 |
| 本地缓存 | 小 | 极快 | 弱（需广播失效） | 极热、变化少 |
| Redis | 大 | 快 | 较强 | 会话、对象、计数、排行榜 |
| 数据库 | 最大 | 慢 | 强 | 最终真相 |

**多级缓存的原则**：越靠近用户，速度越快、容量越小、一致性越弱。每一层都要有 TTL 和降级策略，不能假设下一层一定可用。

## 6.2 缓存模式

| 模式 | 读 | 写 | 适用 |
| --- | --- | --- | --- |
| Cache-Aside | 未命中查库并回填 | 更新库后删除缓存 | 最常用 |
| Read-Through | 缓存层负责加载 | — | 缓存框架封装 |
| Write-Through | — | 写缓存，缓存同步写库 | 写少、强一致要求 |
| Write-Behind | — | 写缓存，异步批量写库 | 写多、可容忍丢失 |

绝大多数业务用 **Cache-Aside**：读时回填、写后删除。关键是**删除而不是更新**缓存，避免并发写导致旧值覆盖新值。

## 6.3 三个经典问题

| 问题 | 场景 | 方案 |
| --- | --- | --- |
| 穿透 | 查不存在的数据，每次都打到 DB | 空值缓存、布隆过滤器、参数校验 |
| 击穿 | 热点 key 过期瞬间大量请求打到 DB | 互斥重建、逻辑过期、永不过期 + 后台刷新 |
| 雪崩 | 大量 key 同时过期或 Redis 整体故障 | 过期时间加随机、多级缓存、熔断降级 |

**热点 key** 的额外手段：

- 本地缓存兜底，减少 Redis 访问
- key 拆分（如 `hotkey:1..N`），把压力分散到多个节点
- 读写分离/多副本读
- 热点探测（采样统计 + 实时告警），提前发现

**大 key** 要避免：一个 value 几 MB、一个集合几十万元素，会阻塞 Redis 单线程、拖慢网络和持久化。拆分、压缩、只存必要字段。

## 6.4 缓存一致性

缓存和数据库的一致性，本质是**双写**问题。常用策略：

1. **先更新数据库，再删除缓存**（推荐）
2. 删除失败 → 重试、消息队列补偿、订阅 binlog 删除
3. 延迟双删：更新后延迟一段时间再删一次，覆盖并发读回填的旧值
4. 设置 TTL 兜底，接受最终一致

**不要迷信强一致**：为了缓存强一致引入分布式锁/事务，往往得不偿失。绝大多数业务可以接受秒级不一致，关键是在业务上设计好兜底（如支付结果以 DB 为准）。

## 6.5 Redis 的扩展与故障

- **Cluster**：16384 个 slot，按 key 分片；跨 slot 的批量操作要用 hash tag
- **主从 + 哨兵**：主从异步复制，故障切换可能丢少量数据
- **持久化**：RDB 快照 + AOF；`everysec` 最多丢 1 秒
- **故障降级**：Redis 不可用时，读走本地缓存/数据库限流，写走队列或直接失败，绝不能把全部流量放到 DB

# 七、数据库：最后的事实来源

## 7.1 读写分离

- 主库写、从库读，读多写少时能线性扩展读能力
- 主从复制有延迟，**写后立即读**可能读到旧数据
- 解决方案：强制走主库、等待 binlog 位点、业务上容忍延迟
- 大查询/报表隔离到专用从库，避免影响在线业务
- 监控复制延迟，超过阈值告警并自动摘除延迟过大的从库

## 7.2 分库分表

**什么时候分**：单表数据量超过千万到亿级、单库写入/连接数达到瓶颈、且索引/归档/分区都无法解决。

**分片键选择**：

| 分片键 | 优点 | 缺点 |
| --- | --- | --- |
| `user_id` | 同一用户数据聚合，查「我的」高效 | 运营跨用户查询要广播 |
| `order_id` | 分布均匀，按 id 查快 | 按用户查需要映射表 |
| `tenant_id` | 多租户隔离清晰 | 大租户可能倾斜 |
| 时间 | 便于归档 | 热点集中在最新分片 |

**分片后的难题**：

- 跨分片 JOIN、分页、排序、聚合
- 分布式事务（尽量用最终一致替代）
- 全局唯一 ID
- 扩容迁移（成倍扩容、双写、一致性哈希）
- 跨分片查询 → 映射表、冗余宽表、ES

**分库分表是最后手段**，不是「亿级访问」的默认答案。

## 7.3 连接池与慢查询

**连接池大小**：不是越大越好。数据库连接会消耗内存、锁、上下文切换。一个实用起点是「CPU 核数 × 2 + 磁盘数」，然后压测调整；更科学的是用利特尔法则估算并发，再留余量。

**慢查询治理**：

- 慢查询日志 + `performance_schema` / `pg_stat_statements`
- 每周 Review Top SQL，纳入发布门禁
- 核心查询必须有覆盖索引
- 大报表走 OLAP，不占 OLTP 连接

## 7.4 分布式事务：能不用就不用

| 方案 | 一致性 | 复杂度 | 适用 |
| --- | --- | --- | --- |
| 本地事务 | 强 | 低 | 单库 |
| 2PC/XA | 强 | 高、性能差 | 少量跨库强一致 |
| TCC | 最终一致 | 高（要写 Try/Confirm/Cancel） | 资金、库存 |
| Saga | 最终一致 | 中（要补偿） | 长流程 |
| 本地消息表 / Outbox | 最终一致 | 中 | 异步解耦（推荐） |
| 事务消息 | 最终一致 | 中 | RocketMQ 场景 |

**优先把跨服务事务改成「本地事务 + 消息 + 幂等 + 对账」**，而不是引入重量级分布式事务。大多数业务要的是最终一致，不是强一致。

## 7.5 冷热分离与归档

- 热表只保留最近 3–6 个月，历史数据归档
- 归档任务分批执行，避免大事务和主从延迟
- 查询按时间路由到热表/归档表
- 备份、DDL、统计信息维护的成本都会下降

# 八、消息队列：异步与解耦

## 8.1 三个作用

| 作用 | 说明 | 例子 |
| --- | --- | --- |
| 解耦 | 生产者不需要知道消费者 | 下单后发短信、加积分、发优惠券 |
| 异步 | 缩短主链路响应时间 | 下单只写订单，其他异步 |
| 削峰 | 把瞬时高峰缓冲到消费能力 | 秒杀、批量导入 |

## 8.2 可靠性

```text
生产端：发送确认 + 重试 + 本地消息表
Broker：持久化 + 多副本（acks=all / 同步刷盘）
消费端：手动 ACK + 重试 + 死信队列 + 幂等
```

**消息可能重复、可能乱序、可能延迟**，消费者必须按最坏情况设计：

- 重复：业务唯一键 + 唯一索引 + 状态机
- 乱序：按业务键分区，或消费端按版本号/时间戳排序
- 延迟：监控消费 lag，设置告警
- 失败：重试队列 + 死信队列 + 人工处理

## 8.3 什么时候不该用 MQ

- 需要强一致、同步返回结果
- 调用链路很短、异步收益不明显
- 团队没有能力运维 MQ（消息丢失、积压、重复）
- 只是「为了解耦」而拆，导致链路更难排查

**MQ 不是免费的**：它带来最终一致、重复消费、消息积压、运维成本。用它之前先确认收益大于复杂度。

# 九、可用性与容灾

## 9.1 冗余与故障转移

- 每一层至少 2 个实例，跨可用区部署
- 负载均衡健康检查 + 自动摘除
- 数据库主从/多副本，Redis 主从/Cluster
- 消息队列多副本，避免单 Broker 故障丢消息
- 消除单点：DNS、VIP、网关、配置中心、注册中心都要冗余

## 9.2 多活架构

| 模式 | 特点 | 适用 |
| --- | --- | --- |
| 同城双活 | 两个机房，低延迟，数据同步 | 大多数业务 |
| 异地多活 | 跨地域，就近接入，容灾 | 全国/全球业务 |
| 单元化 | 按用户/租户分单元，单元内闭环 | 超大规模、强隔离 |
| 主备 | 备机房平时不承载流量 | 成本敏感、RTO 要求不高 |

**多活最难的不是流量调度，是数据**：跨地域同步延迟、冲突解决、一致性取舍。没有数据层方案的多活，只是「多机房部署」，不是真正的高可用。

## 9.3 降级与熔断

降级要有**预案、开关、演练**：

| 场景 | 降级动作 |
| --- | --- |
| 下游超时 | 熔断，返回兜底数据 |
| Redis 故障 | 本地缓存兜底 / 限流 / 关闭非核心功能 |
| DB 压力大 | 关闭报表、限流写入、读写分离 |
| 流量超预期 | 网关限流、排队、只放行核心用户 |
| 非核心服务故障 | 关闭评论、推荐、积分，保下单/支付 |

**降级开关要能一键操作，并且定期演练。** 没演练过的预案，等于没有预案。

## 9.4 备份与容灾

- 全量备份 + 增量备份 + binlog/WAL
- 定期恢复演练，验证备份可用
- 明确 RTO（恢复时间）和 RPO（丢失数据量）
- 关键数据异地备份，防止机房级故障
- 数据库误删、勒索软件等场景要有独立备份

# 十、可观测性与容量

## 10.1 三件套

| 类型 | 工具 | 回答什么问题 |
| --- | --- | --- |
| Metrics | Prometheus + Grafana | 现在健康吗？趋势如何？ |
| Logs | ELK / Loki | 具体发生了什么？ |
| Traces | Jaeger / SkyWalking | 慢在哪一段？调用链是什么？ |

**traceId 要贯穿全链路**：网关生成/透传，服务间通过 Header 传递，日志、MQ、DB 记录都带上。没有 traceId 的分布式系统，排障基本靠猜。

## 10.2 SLO 与告警

- SLI：可用性、延迟、错误率、饱和度
- SLO：如「99.9% 的请求在 200ms 内成功」
- Error Budget：允许的失败额度，用完就冻结发布
- 告警要分级：P0 电话、P1 群消息、P2 工单
- 避免告警风暴：聚合、抑制、静默

## 10.3 关键指标

| 层 | 指标 |
| --- | --- |
| 接入 | QPS、带宽、4xx/5xx、限流拒绝、CDN 命中率 |
| 服务 | QPS、P99、错误率、线程池、GC、连接池 |
| 缓存 | 命中率、QPS、慢查询、内存、eviction、主从延迟 |
| 数据库 | QPS/TPS、慢查询、锁等待、连接数、复制延迟 |
| MQ | 生产/消费 TPS、堆积量、消费延迟、死信 |
| 业务 | 下单量、支付成功率、转化率、核心接口可用性 |

## 10.4 压测与容量规划

- **全链路压测**：从网关到 DB、缓存、MQ，使用影子库/影子表
- **梯度加压**：找到拐点，而不是只测一个峰值
- **瓶颈定位**：CPU、内存、I/O、网络、连接数、锁、GC
- **容量公式**：所需实例数 = 峰值 QPS / 单实例安全 QPS × (1 + 余量)
- **定期复测**：业务增长、代码变更、依赖升级都会改变容量

**单实例安全 QPS 要留余量**：压测峰值不是安全值，通常按峰值的 50%–70% 规划，给突发和故障转移留空间。

## 10.5 成本

亿级访问的成本主要在带宽、存储、计算和数据库：

- CDN 和缓存提高命中率，直接降低源站成本
- 冷热分离，历史数据转低频/归档存储
- 弹性伸缩，按负载而非峰值常备资源
- 预留实例/包年包月覆盖稳定基线，按量覆盖峰值
- 定期清理无用日志、临时表、孤儿文件

# 十一、亿级访问的典型瓶颈清单

| 瓶颈 | 症状 | 解法 |
| --- | --- | --- |
| 文件描述符耗尽 | `Too many open files` | 调大 ulimit、连接复用、及时关闭 |
| TIME_WAIT 过多 | 端口耗尽、连接失败 | 连接池、`tcp_tw_reuse`、长连接 |
| 线程池打满 | 请求排队、RT 飙升 | 异步化、隔离、限流、扩容 |
| GC 频繁 | CPU 高、STW 抖动 | 减少对象分配、调堆、换收集器 |
| 数据库连接耗尽 | 获取连接超时 | 连接池、慢查询治理、读写分离 |
| Redis 热 key | 单节点 CPU 打满 | 本地缓存、key 拆分、多副本 |
| 大 key | Redis 阻塞、网络抖动 | 拆分、压缩、异步删除 |
| MQ 积压 | 消费延迟增长 | 扩消费者/分区、优化消费逻辑、降级 |
| 带宽打满 | 响应慢、丢包 | CDN、压缩、限流、多线 BGP |
| DNS 解析慢/劫持 | 首屏慢、随机失败 | HTTPDNS、多域名、预解析 |
| 单点故障 | 某实例/机房故障导致整体不可用 | 冗余、健康检查、多活 |
| 慢 SQL | 偶发 RT 飙升、连接堆积 | 索引、限流、隔离、归档 |

# 十二、20 道高频面试题

**Q1：1 亿次访问怎么估算 QPS 和容量？**

先确认口径（PV/API/UV），日均 QPS = 日请求量 / 86400，峰值按 3–5 倍（秒杀另算）。再算带宽 = 日流量 / 86400 × 峰值系数，存储 = 日增量 × 保留天数 × 放大系数，并发 = QPS × 平均 RT。最后按单实例压测能力算实例数，并留 30%–50% 余量。

**Q2：亿级访问系统的架构演进路径？**

单机 → 应用/DB 分离 + 负载均衡 → 缓存 + 读写分离 → 无状态 + 水平扩展 + MQ + 服务拆分 → 分库分表 + 多级缓存 + CDN + ES/OLAP → 多活/单元化。每一步都由当前瓶颈驱动，不要跳级。

**Q3：为什么服务要无状态？**

有状态服务无法简单加机器，请求必须落到特定实例。把会话、文件、缓存、定时任务外置后，服务可以任意扩缩容、滚动发布、故障转移。本地缓存是例外，需要主动失效机制。

**Q4：缓存和数据库怎么保持一致？**

Cache-Aside：先更新 DB，再删除缓存；删除失败用重试/binlog 补偿；延迟双删覆盖并发回填；TTL 兜底。接受最终一致，不要为了强一致引入分布式锁。

**Q5：缓存穿透、击穿、雪崩的区别？**

穿透：查不存在的数据，缓存不命中，打到 DB → 空值缓存/布隆过滤器。击穿：热点 key 过期瞬间大量请求 → 互斥重建/逻辑过期。雪崩：大量 key 同时过期或 Redis 故障 → 随机 TTL/多级缓存/熔断降级。

**Q6：热点 key 怎么处理？**

本地缓存兜底、key 拆分、多副本读、热点探测、限流。根本上是把读压力从单个 Redis 节点分散到本地或多个节点。

**Q7：什么时候分库分表？**

单表数据量过大、单库写入/连接数达到瓶颈，且索引、归档、分区、读写分离都无法解决时。分片键要匹配主要查询模式，接受跨分片查询和分布式事务的复杂度。

**Q8：分片键怎么选？**

按主要查询维度选：C 端按 user_id，订单按 order_id，多租户按 tenant_id，日志按时间。要求分布均匀、大部分查询能带上分片键、避免热点和跨分片 JOIN。

**Q9：读写分离后读不到刚写的数据怎么办？**

主从延迟导致。写后立即读走主库、等待 binlog 位点、业务上容忍延迟；监控复制延迟，延迟过大自动摘除从库。

**Q10：分布式 ID 有哪些方案？**

雪花算法（趋势递增、需处理时钟回拨）、号段模式（DB 批量取号）、Redis INCR、UUID（无序、不适合主键）。按是否需要趋势递增、是否有中心依赖选择。

**Q11：分布式事务怎么选？**

优先避免：本地事务 + 消息 + 幂等 + 对账。必须跨服务时，资金类用 TCC，长流程用 Saga，异步解耦用本地消息表/Outbox/事务消息。2PC 性能差，少用。

**Q12：如何保证接口幂等？**

requestId + Redis SETNX、数据库唯一索引、状态机条件更新、消息消费先查后写。每一层都假设上一层会重复。

**Q13：MQ 在架构里起什么作用？**

解耦、异步、削峰。同时带来最终一致、重复消费、积压和运维成本。消费者必须幂等，生产端要保证可靠投递，消费端要有重试和死信。

**Q14：限流算法有哪些？**

固定窗口（临界突刺）、滑动窗口（较精确）、漏桶（平滑输出）、令牌桶（允许突发）。网关做粗粒度，服务做细粒度，数据库用连接池兜底。

**Q15：熔断和降级有什么区别？**

熔断是「下游故障时快速失败，不再调用」；降级是「主动关闭非核心功能或返回兜底数据」。熔断通常自动触发，降级可以人工开关，二者常配合使用。

**Q16：多活架构最难的是什么？**

数据。跨地域同步延迟、冲突解决、一致性取舍、单元化路由。没有数据层方案的多活只是多机房部署。还要考虑故障切换的 RTO/RPO 和演练。

**Q17：如何做容量规划？**

全链路压测找单实例安全 QPS 和系统拐点，按峰值 / 安全 QPS × 余量算实例数；同时算带宽、存储、连接数、缓存容量；定期复测，给故障转移留余量。

**Q18：线上突然变慢，怎么排查？**

先看全局指标（QPS、RT、错误率、资源水位）→ 定位是单服务还是全链路 → 看依赖（DB、Redis、MQ、下游）→ 用 trace 找慢点 → 检查变更、流量突增、慢查询、锁、GC → 限流/降级/回滚。

**Q19：如何消除单点？**

每一层至少两个实例、跨可用区、健康检查、自动故障转移；DNS/VIP/网关/注册中心/配置中心也要冗余；数据库主从、Redis 主从/Cluster、MQ 多副本；定期做故障演练。

**Q20：什么时候不该上微服务/多活？**

团队规模小、流量未到瓶颈、运维能力不足时。微服务带来网络调用、分布式事务、链路复杂度和运维成本；多活带来数据一致性和成本。架构要匹配当前规模和团队能力，过度设计比欠设计更常见。

# 十三、落地检查清单

## 13.1 接入层

```text
□ DNS 多线路/健康检查，关键业务有 HTTPDNS
□ 静态资源 CDN 命中率 > 95%，发布按版本刷新
□ WAF/DDoS 防护开启，规则灰度
□ 负载均衡多实例 + 健康检查，无单点
□ 网关鉴权、限流、熔断、灰度、traceId
```

## 13.2 服务层

```text
□ 服务无状态，会话/文件/定时任务外置
□ 每个 RPC 有超时、重试预算、熔断、隔离
□ 接口幂等，分布式 ID 方案确定
□ 优雅上下线，扩容预热
□ 服务拆分有边界，不是越细越好
```

## 13.3 缓存与数据库

```text
□ 多级缓存，热点 key 有本地兜底
□ 穿透/击穿/雪崩都有方案
□ 缓存一致性策略明确，TTL 兜底
□ 读写分离，复制延迟监控
□ 索引覆盖核心查询，慢 SQL 有门禁
□ 分片键匹配查询模式，扩容方案确定
□ 大报表走 OLAP，冷数据归档
```

## 13.4 消息与可用性

```text
□ MQ 可靠投递、消费幂等、死信队列
□ 消费 lag 监控与告警
□ 多可用区部署，关键链路无单点
□ 降级开关可一键操作，定期演练
□ 备份可恢复，RTO/RPO 明确
```

## 13.5 可观测与容量

```text
□ Metrics/Logs/Traces 三件套，traceId 全链路
□ SLO 与错误预算，告警分级
□ 全链路压测，容量有余量
□ 成本可观测，缓存命中率和带宽有优化
```

---

支持亿级访问的系统，说到底是在做三件事：

1. **把流量分层**：能在 CDN/网关/缓存挡掉的，不要进核心服务；能在服务层异步掉的，不要同步等
2. **让每一层可扩展**：无状态、分片、多副本，避免任何单点成为天花板
3. **为失败做设计**：超时、重试、熔断、降级、多活、演练——不是假设一切正常，而是假设一切都会坏

架构没有标准答案，只有**在给定规模、团队和成本约束下的合理取舍**。面试时能把这笔账算清楚，比画出多复杂的架构图都更有说服力。
