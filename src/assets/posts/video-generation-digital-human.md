过去两年，视频生成这条线上真正发生的变化，不是"画面更好看了"，而是**约束条件换了**。

第一代视频模型的评价标准是画质：能不能生成一段看起来像那么回事的片子。到了今天，评价标准变成了三个互相拉扯的指标——**质量**（分辨率、时长、音画是否天然同步）、**速度**（首帧延迟、稳态吞吐、是否快于实时播放）、**交互性**（能不能边生成边输出、能不能被随时打断）。这三者不可能同时拉满，所有工程取舍都发生在这三者之间。

本文挑三个有代表性的样本，把这条线串起来：

- **MiniMax-H3**——把视频和音频塞进同一个 Transformer 的 33B 基座模型，解决"音画同步"这件事。
- **Sol-H3**——NVIDIA 研究院围绕 H3 做的一整套推理加速栈，把"快于实时"从口号变成实测数字。
- **SoulX 三件套**——Soul App AI Lab 开源的实时数字人系列，把"音频驱动一个人物、稳定跑几个小时"做成可部署的工程方案。

![视频生成与数字人的三条技术线：基座模型 MiniMax-H3、推理加速 Sol-H3、实时数字人 SoulX，以及质量、速度、交互性三个评价维度](/images/blog/video-generation-digital-human/landscape.svg)

# 〇、先把出处说清楚

这一节不是可有可无的铺垫。这三个东西经常被混为一谈，而它们的作者、许可证、开源范围完全不同，直接决定了你能不能商用、能不能本地部署。

| 项目 | 出品方 | 代码/权重 | 许可证 |
| --- | --- | --- | --- |
| MiniMax-H3 | MiniMax（海螺 Hailuo 线第三代） | 权重开源于 Hugging Face `MiniMaxAI/MiniMax-H3`、ModelScope | MiniMax H3 Community License |

有三点容易搞错：

1. **MiniMax-H3 不是 Soul-AILab 出的**，它出自 MiniMax 自家。
2. **Sol-H3 也不是 Soul 系的**，它是 NVIDIA 的工作，名字里的 "Sol" 指 Sol-Engine 推理框架，不是 Soul App。
3. **"Soul-H3" 这个写法是误传**，正确拼写是 **Sol-H3**。Soul-AILab 在视频这块的产品线叫 **SoulX**，主打数字人。

所以本文的叙事结构是：**MiniMax-H3 是基座，Sol-H3 是它的一条加速路径，SoulX 是数字人这个垂直方向上的落地。** 三者是邻居，不是一家人。

# 一、先把坐标系立起来

在讨论任何一个模型之前，先明确"快"和"好"在不同语境下指的是什么。这几个词经常被混着宣传，是踩坑的重灾区。

| 维度 | 真正在问什么 | 常见误读 |
| --- | --- | --- |
| 分辨率 / 时长 | 单次能生成多长、多清晰 | 时长上限 ≠ 能连续生成，离线拼接会跳帧、会漂移 |
| 音画同步 | 音频和画面是不是同一个模型一起生成的 | "带音频"不等于"原生同步"，很多方案是后期对齐，口型对不上 |
| 首帧延迟 | 从给输入到出第一帧要多久 | 这是交互感的决定因素，不是吞吐 |
| 稳态吞吐 | 稳定阶段每秒能出多少帧 | 只要 ≥ 25–30 FPS 就够，再高用户感知不到，堆上去只是浪费算力 |
| 快于实时 | 生成耗时 < 视频本身的时长 | 有意义的场景是批量生产，不是交互——快于实时不等于能对话 |
| 可交互 | 生成中途能不能接受新输入、被打断 | 需要模型是流式自回归的，离线扩散模型结构上做不到 |

一句话概括这份取舍：**离线生成比画质，流式生成比延迟，交互生成比架构。**

# 二、MiniMax-H3：把音视频塞进同一个 Transformer

## 2.1 三段式系统

H3 不是一个模型，是三个模块串起来的流水线：

![MiniMax-H3 三段式系统：多模态输入经 H3-Context-IR 解析成结构化中间表示，交给开源的 H3-Base 生成 768p 音视频，再由 H3-Regenerate-2K 回灌生成 2K 成品](/images/blog/video-generation-digital-human/h3-system.svg)

1. **H3-Context-IR**——把多模态输入（文本、图像、参考视频、参考音频）解析成一份**结构化的中间表示**，输出的字段包括整体画面描述、整体声景（overall soundscape）、非叙事性配乐（non-diegetic music）等。**未开源，只有 API。**
2. **H3-Base**——真正的生成主体，输出 **768p** 的音视频。**只有这一段的开源权重。**
3. **H3-Regenerate-2K**——把 768p 的结果**重新灌回 Base 模型**，在一个更长的上下文里再生成一遍，得到 2K。**未开源，只有 API。**

第三段值得多说一句：2K 不是外挂一个超分网络，而是让模型**再看一遍自己的草稿并重画**。这意味着它同时修的是分辨率、纹理和细节一致性（超分只能修前两者）。代价是它需要一次额外的、接近完整的前向——也正因为如此，它被留在了 API 里。

> **易错点**：把"H3 开源"理解成"整个 H3 都开源"。实际只有中间那段 Base。想本地跑端到端的 2K，你要么自己补出 IR 解析和重生成两个环节，要么老老实实调官方 API。这是"开源"两个字在当前大模型语境下最常见的模糊地带。

## 2.2 H3-Base 的骨架

![H3-Base 单流 Omni Transformer 结构：文本、视频潜变量与音频潜变量打包成一条序列，送入共享的 50 层 Transformer 联合去噪，AdaLN 分支因只依赖时间步嵌入而可预计算缓存](/images/blog/video-generation-digital-human/h3-base-arch.svg)

H3-Base 是 **33B 的 dense 单流 Omni Transformer**（DiT 架构），公开资料给出的关键参数：

| 部件 | 规格 |
| --- | --- |
| 主干 | 单流共享 backbone，重复 50 层，hidden dim 5376，56 个注意力头 × 128 维 |
| 去噪方式 | 视频与音频在同一条 packed sequence 上**联合去噪**（joint video–audio denoising） |
| 文本编码器 | 冻结的 **Qwen3-VL-32B**，取第 50 层 hidden state，约 66.7 GB |
| 视频 VAE | H3-VisualVAE：ViT + CNN 的 KL VAE，16× 空间压缩 / 4× 时间压缩 |
| 音频 VAE | H3-AudioVAE：32 kHz 立体声 ↔ 40 Hz token（每声道） |
| 输出 | 最高 2K、24 FPS、原生 32 kHz 立体声，单次 4–15 秒，11 种语言 |

这里最关键的设计是**单流**：视频 token 和音频 token 不是两条并行的分支再后期对齐，而是**在同一条序列里、同一次注意力中互相看见**。这直接解释了 H3 的卖点——口型、环境音、配乐天然就是对齐的，不需要额外的对齐模块，也不需要后期配音。代价同样直接：序列长度翻倍，注意力的开销是二次的，这也是后面 Sol-Attn 那类稀疏注意力有存在价值的原因。

另一个值得注意的工程细节是 **AdaLN 分支可以缓存**。33B 里有约 13B 参数位于 AdaLN 的调制分支中，而这类分支**只依赖时间步嵌入、与序列内容无关**，所以可以在推理前一次性算好并缓存。结果是纯推理部署的常驻参数降到约 **20.11B（约 40.3 GB）**。这是"训练参数量"和"推理常驻显存"相差悬殊的一个典型案例，也是为什么 33B 的模型能落到单机多卡上跑。

## 2.3 两个 checkpoint：FL2VA 与 Ref2VA

H3-Base 放出两个权重的使用模式：

| 模式 | 输入 | 典型用途 |
| --- | --- | --- |
| **FL2VA** | 文本提示 + 0–2 张图（首帧、尾帧） | 文生音视频（T2VA）、首尾帧插值、镜头衔接 |
| **Ref2VA** | 全能参考（omni-reference）：最多 9 张图 + 3 段视频 + 3 段音频，合计不超过 12 个文件 | 角色/场景保持、动作编辑、口型编辑 |

**Ref2VA 才是真正有意思的那一个**。"参考"这个能力一旦做扎实，视频生成就从"抽卡"变成了"可控编辑"：给同一张人脸做 9 个不同角度的参考，就能在不同分镜里保持同一个人；给一段原视频加参考音频，就能改口型而不动其余部分。这也解释了为什么它在 Artificial Analysis 的视频编辑榜上位置很高——编辑场景需要的一致性，比纯生成场景苛刻得多。

# 三、Sol-H3：把推理链路压到"快于实时"

## 3.1 基座为什么快不起来

H3 的推理慢在三个地方，而且彼此独立：

1. **采样步数**——扩散/流匹配模型的默认步数是几十步，每步都是一次完整的 33B 前向。
2. **注意力的二次复杂度**——音视频联合去噪让序列变得很长，注意力成为主要开销。
3. **系统开销**——8 卡之间的 all-to-all 通信、视频与音频两个 VAE 的解码，在步数降下来之后，这些"非计算"部分的占比会迅速上升。

**这三件事分别对应三种不同的优化手段：蒸馏降步数、稀疏注意力降计算、系统工程降通信与解码。** Sol-H3 的价值在于它把三件事放进了同一套栈里，而不是只挑一件做。

## 3.2 Sol-Engine：系统层的活

![Sol-H3 加速栈分层：应用层之下是 Sol-Attn 免训练稀疏注意力，再往下是 Sol-Engine 的系统级优化（核融合、通信量化、VAE 并行解码、AdaLN 缓存），最底层是 B300 与 DGX Spark 等硬件](/images/blog/video-generation-digital-human/sol-h3-stack.svg)

Sol-Engine 是承载整套加速的框架，主要做了四件事：

- **核融合**：把 SwiGLU、QK-Norm 加部分 RoPE 等相邻算子合并，减少 kernel 启动与显存往返。
- **通信量化**：8 卡的 Ulysses all-to-all 交换改用 INT8 / FP8 打包。这是一个典型的"用精度换带宽"的取舍——分布式推理里，通信经常比计算更早成为瓶颈。
- **缓存与解码**：AdaLN 预计算缓存（呼应前面 H3-Base 的设计），加上 VAE 的分块并行解码，把解码从串行变成可并行。
- **编译与调度**：图编译、kernel 自动搜索、显存布局优化，属于"不改变算法但改变执行"的一层。

这一层没有漂亮的算法故事，但它决定了前面两层的收益能不能真正兑现——**稀疏注意力省下来的计算，如果被一次低效的 all-to-all 吃掉，就等于没做。**

## 3.3 Sol-Attn：免训练的稀疏注意力

这是整套加速里最"算法"的一块，也是最能复用的思路。

它的做法是：

1. 用轻量的 query–key 打分估计每个块的重要程度，按 **`τ = mean + τ系数 × std`** 算出一个**逐 query 自适应**的阈值——不是固定比例，而是跟着这一行注意力的分布走。
2. 高于阈值的 **64-token 块**做精确注意力；被跳过的块，用**池化的 K/V 摘要**做一次近似修正，而不是直接当零丢掉。
3. 路由判断、稀疏计算、近似修正**共用同一次 online-softmax**，不物化路由图（routing map）。

三个设计选择各有原因，也各自对应一类常见失败：

| 设计 | 解决的问题 |
| --- | --- |
| 阈值随 query 走，而非固定稀疏比例 | 有的 query 本来就该看全局，一刀切比例会误伤 |
| 跳过的块用摘要修正，而非直接丢弃 | 直接丢会在被跳过区域产生可见的伪影/断裂 |
| 与 online-softmax 融合，不落 routing map | 省掉一次显存往返；**免训练**，不需要为稀疏性重训模型 |

工程实现上，它提供了 CuTe 写的 kernel，覆盖 SM90（H100）、SM100（B200/GB200）、SM120（RTX 5090），另有 Triton 与 Metal 回退路径。**"免训练"这一点对落地影响很大**：你不需要重训或蒸馏模型才能享受稀疏带来的加速，这大幅降低了迁移成本。

## 3.4 粗到细的两阶段

在边缘设备上，Sol-H3 换了一套思路：**不追求一步到位，而是分两步画。**

![Sol-H3-Spark 的粗到细两阶段流水线：先用 H3 在 384p 生成四步草稿，经 latent-to-latent 适配器直接升到目标分辨率，再用 LTX-2.5 三步精炼出 768p 成品](/images/blog/video-generation-digital-human/sol-h3-pipeline.svg)

1. **Stage 1 草稿**：用 FastH3 在 **384p、4 步**生成一版草稿，负责运动走向、构图、大色块和音画节奏。
2. **适配器**：一个学到的 **latent-to-latent 映射**，直接在潜空间里升分辨率。关键在于它**省掉了 VAE 解码 → 重编码这一趟往返**——这一步在朴素实现里既费时又引入额外的量化损失。
3. **Stage 2 精炼**：用 **LTX-2.5、3 步**把草稿精炼到 768p，补纹理、修细节。

这个结构的收益很直观：**贵的步数花在已经定型的画面上**。草稿阶段便宜且能定调，精炼阶段的每一步都在修正而不是探索。量化上配合 NVFP4 的 Qwen 文本编码器与 FP8 的 DiT，把模型塞进单台 DGX Spark 的显存里。

## 3.5 实测数字与取舍

8×B300 上的公开实测：

| 配置 | 视频规格 | 生成耗时 | 相对基线加速 |
| --- | --- | --- | --- |
| 8×B300 | 5 秒 · 1344×768 · 立体声 | **1.653 秒** | 约 11.04× |
| 8×B300 | 10 秒 | 3.732 秒 | 约 13.57× |
| 8×B300 | 15 秒 | 6.612 秒 | 约 15.05× |
| 4×B300 | 5 秒 | — | — |
| 单 B300 | 5 秒 | 13.745 秒 | 约 9.45× |
| 单台 DGX Spark | 5 秒 · 768p | 约 56–68 秒 | — |

几个读表时的注意点：

1. **"5 秒视频 1.653 秒生成"是真的快于实时播放**（1.653 < 5），这是这条新闻最有分量的部分。但**加速比是叠加结果**——少步采样、稀疏注意力、系统优化三者共同贡献，不能单独归因给任何一项。
2. **时长越长，加速比越高**，说明固定开销（权重加载、首步）被摊薄，而稀疏与通信优化的收益随序列变长而放大。
3. **快于实时 ≠ 可交互**。这里的场景是批量生产，不是对话。要做交互，得看下一节的流式数字人架构。

> **已知限制（务必在选型前确认）**：固定 121 帧的时长约束、不支持续拍（take continuation）、非 5 秒时长与竖屏场景下的质量缺乏验证。这类限制往往比跑分更能决定一个方案能不能进生产。

# 四、数字人：SoulX 三件套

## 4.1 数字人和通用视频生成差在哪

通用视频生成问的是"这段画面像不像真的"；数字人问的是一组更苛刻的问题：

- **口型同步**——音素和嘴型对不对得上，这是最不能出错的一项。
- **身份一致性**——连续生成几小时之后，还是不是同一个人（身份漂移是长视频的头号问题）。
- **首帧延迟**——能不能做到"你说完半句，画面就跟上"。
- **长时长稳定性**——不是能生成长视频，而是**生成一小时后质量不衰减、不崩**。

这也决定了数字人模型几乎都是 **音频驱动 + 分块自回归 + 流式输出**的架构，而不是一次性生成整段。

![SoulX 数字人三件套对比：14B 的 FlashTalk 主打质量与低首帧延迟，LiveAct 用 Neighbor Forcing 与 ConvKV Memory 做到双卡小时级生成，1.3B 的 FlashHead 面向单卡消费级 GPU 高吞吐](/images/blog/video-generation-digital-human/soulx-matrix.svg)

## 4.2 SoulX-FlashTalk：质量优先的 14B

FlashTalk 是这条线里规格最高的一个：**14B 参数，0.87 秒首帧延迟，32 FPS 吞吐，跑在 8×H800 节点上**。公开资料称它是首个做到亚秒级启动的 14B 级数字人模型。

两个核心机制，正好对应长视频的两个痛点：

- **自校正双向蒸馏（Self-Correcting Bidirectional Distillation）**。常规的流式自回归生成会把注意力限制成严格单向（只能看历史），这会让运动和细节退化。FlashTalk 的做法是**在视频块内部保留双向注意力**，只在块与块之间保持因果性——既保住了块内的时空相关性，又没有破坏流式的因果结构。
- **多步回溯自校正（Multi-step Retrospective Self-Correction）**。生成不是单向往下走，模型会**回看已生成的片段，主动修正累积误差**。这是对抗长视频"越生成越糊、越生成越不像"的关键。

训练上采用两阶段策略，公开资料称约 **1.2k 步**即可收敛，相比需要上万步的方案大幅缩短。

在 TalkBench 上的公开指标：ASE 3.51、IQA 4.79、Sync-C 1.47，身份一致性（Subject-C）**99.22**，并支持全身动作交互与手部细节表现。许可证 Apache-2.0，权重发布在 Hugging Face `Soul-AILab/SoulX-FlashTalk-14B`。

**适用**：7×24 小时的 AI 直播、虚拟主播、需要高画质的品牌内容——这类场景算力预算充足，但对"身份崩掉"零容忍。

## 4.3 SoulX-LiveAct：小时级、双卡跑

LiveAct 走的是另一条路：**用更少的卡，跑更长的时间**。它在 **2×H100/H200 上做到 20 FPS、约 0.94 秒延迟、小时级生成**，架构上自 Wan2.1 与 InfiniteTalk 初始化（分别提供自注意力/文本/图像交叉注意力和音频交叉注意力），采用 **DiT + Flow Matching**，在 3D VAE 的潜空间上做分块自回归。

两个技术贡献都值得细看：

**Neighbor Forcing。** 这是对自回归扩散训练范式的一次修正。已有的几种 forcing 方案各有问题：Teacher Forcing 训练与推理不一致；Diffusion Forcing 与推理时的步进节奏对不齐；Self Forcing 收敛慢且依赖 ODE 初始化训练。

Neighbor Forcing 的做法是：**把时间上相邻的帧，在相同噪声条件下作为 latent 邻居来传播**。这样给出的学习信号与推理时的分布是对齐的，因此训练更稳、更快——公开数据显示只需 **300 蒸馏步**，而 Self Forcing 需要约 1000 步，并且省掉了 ODE 初始化训练这一环。

**ConvKV Memory。** 长时生成的头号敌人是 KV 缓存无限增长。LiveAct 用一个**轻量的一维卷积**把因果注意力中的 K/V 压成**定长记忆**（压缩比 λ=5），压缩后配合 **RoPE 重置**保证位置编码不失效。结果是**显存恒定**，而推理开销只增加约 **+1.9%**。

算力画像上，它 **27.2 TFLOPs/帧**，对比双向注意力的约 50.2 与 Live-Avatar 的约 39.1——稀疏化与定长记忆省下的算力是可量化的。消融实验给出的最优配置是"记忆块 6 / 当前块 8"，对应约 **49 ms/帧**，刚好满足 20 FPS。此外它还带一个**情绪与动作编辑模块**，用于可控的表情与手势。

在 HDTF 上公开的 Sync-C 为 9.40。**注意这个数字不能和 FlashTalk 的 1.47 直接比较**（见下文易错点）。

**适用**：需要长时间陪伴、可打断的交互式场景——虚拟陪伴、在线教育、长时客服。

## 4.4 SoulX-FlashHead：1.3B 跑在消费级显卡上

FlashHead 是这条线里最"接地气"的一个：**1.3B 参数，单张 RTX 4090 上 LITE 版本达到 96 FPS，或者同一张卡并发跑 3 路推流**；PRO 版本在双 RTX 5090 上做到实时。

它延续了同一条技术路线——**Oracle 引导的双向蒸馏**，用大模型的注意力分布去指导学生模型，让小模型也能拿到接近大模型的时序一致性；再配合**时序音频上下文缓存**，解决小模型在长视频上的身份漂移问题。

数据集方面配套发布了 **VividHead**：33 万个片段、782 小时、15 种语言。对小模型来说，数据规模往往比结构设计更能决定上限。

**适用**：高并发直播、游戏 NPC、批量短视频生产——这类场景要的不是单路画质，而是**单卡能同时跑几路**。

## 4.5 三者的选型

| 场景 | 首选 | 理由 |
| --- | --- | --- |
| 7×24 品牌直播、高画质虚拟主播 | **FlashTalk** | 0.87s 首帧 + 身份一致性 99.22，画质与稳定优先 |
| 长时互动、虚拟陪伴、在线教育 | **LiveAct** | 恒定显存 + 小时级时长，双卡成本可控 |
| 高并发直播、游戏 NPC、批量生产 | **FlashHead** | 单卡 96 FPS 或 3 路并发，单位算力产出最高 |

一句话：**FlashTalk 花钱买质量，LiveAct 花钱买时长，FlashHead 花钱买并发。**

# 五、把它们串起来：一条实时数字人流水线

单独看每个模型容易失焦，放到端到端链路里，各自的定位就清楚了。

![实时数字人端到端流水线：脚本文本经语音合成产生音频，驱动数字人模型逐块生成视频帧，经实时传输推给观众；下方标注首帧延迟与稳态吞吐两组互相独立的指标](/images/blog/video-generation-digital-human/digital-human-pipeline.svg)

链路是：**脚本/文本 → TTS（SoulX-Podcast）→ 数字人渲染（FlashHead / LiveAct / FlashTalk）→ 实时传输（LiveKit / WebRTC SFU）→ 观众**，并把用户的打断作为反馈回路接回渲染环节。

这条链路上有三个容易被忽略的工程点：

1. **TTS 必须是流式的。** 如果等整句合成完再送进数字人模型，首帧延迟会被 TTS 的整句时长直接吃掉——优化到最后发现瓶颈根本不在数字人模型上。
2. **首帧延迟和稳态吞吐是两个独立指标，要分开优化、分开验收。** 首帧延迟低但吞吐不够，视频会越播越落后；吞吐高但首帧慢，用户一开口就感到停顿。传播时经常只提一个数字，这是选型时最容易被误导的地方。
3. **可交互意味着架构必须是流式自回归的。** 离线扩散模型无论怎么优化，都做不到"生成到一半接收新输入"。这不是速度问题，是结构问题。

# 六、易错点清单

把上面散落的坑集中列一遍，都是选型或复现时最容易踩的：

1. **把"开源"当成全量开源。** H3 只放出了 Base，IR 解析与 2K 重生成都在 API 后面。端到端能力 ≠ 开源范围。
2. **横向比较不同论文的指标。** 同样是 Sync-C，FlashTalk 报 1.47、LiveAct 报 9.40——**量纲与实现不同，不可比**。任何跨论文的指标对比都必须先确认测试集与工具链一致。
3. **把"加速比"归因给单一技术。** Sol-H3 的 11× 是"少步蒸馏 + 稀疏注意力 + 系统优化"的叠加结果，不是 Sol-Attn 一个模块的功劳。复现时要逐项做消融。
4. **把"快于实时"当成"可交互"。** 前者是吞吐指标，后者是架构属性。批量生产和实时对话是两种完全不同的系统。
5. **忽略许可证的地域与用途限制。** H3 的社区许可证排除美/欧/英/韩；Sol-H3 与 SoulX 系列是 Apache-2.0。上线前逐条核对，不要想当然。
6. **按"最低显存"做容量规划。** 极限量化的配置（低比特 + offload + 极短时长）通常不是生产配置。按"能跑"和"能用于生产"两栏分别评估。
7. **忽略固定帧数等硬约束。** 固定 121 帧、不支持续拍这类限制，往往比跑分更早撞上产品需求。
8. **混淆首帧延迟与吞吐。** 见上节第 2 点，这是宣传材料里最高频的模糊之处。

# 七、小结

把三件事收一下：

- **MiniMax-H3** 解决的是"音画同源"——用单流 Omni Transformer 让视频和音频在同一条序列里联合去噪，换来天然同步的口型和音效，代价是序列变长、计算变重。
- **Sol-H3** 解决的是"这份计算怎么压下去"——蒸馏降步数、Sol-Attn 降注意力、Sol-Engine 降通信与解码，三层叠加把 5 秒视频压进 1.653 秒，并在单台 DGX Spark 上也能跑 768p。
- **SoulX 三件套** 解决的是"一个人在镜头前稳定地待几个小时"——Neighbor Forcing 让自回归训练对得上推理分布，ConvKV Memory 让显存恒定，双向蒸馏让块内质量不退化。

如果只记一句话：**通用视频生成在比"上限"，数字人在比"下限"——前者看单条最好的样本，后者看连续跑几小时之后还是不是同一个人。** 这也是为什么这条线上真正的技术突破，几乎都发生在长时稳定性而不是画质上。

> 说明：本文中的性能数字均来自各项目公开的技术报告、模型卡与第三方评测报道，具体数值以官方仓库和论文为准；不同测试集、不同硬件配置下的数字之间不具备可比性，落地前请以自己场景下的实测为准。
