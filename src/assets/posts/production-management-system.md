本文是一份生产管理系统（MES）的整体设计方案。它把一家典型制造业企业的经营主线——从线索到现金、从物料到产品——拆成若干相互咬合的子系统，并给出各子系统的职责边界、核心单据、状态流转与设计要点。文中穿插的界面截图来自已落地的实现，用于说明设计在实际系统中的样子。

## 设计出发点

传统做法是按部门建系统：销售一套、采购一套、仓库一套、生产一套，靠 Excel 和微信把它们缝起来。问题出在缝上——单据在系统之间靠人工搬运，状态靠人对账，成本靠事后估算。

这套方案的目标是让**单据在同一条主线上自然流转**：

```
商机 → 报价 → 销售订单 → MRP 运算
                            ├─ 采购件 → 采购申请 → 采购订单 → 收货 → 来料检 → 入库
                            └─ 自制件 → 生产计划 → 生产工单 → 领料 → 报工 → 完检 → 完工入库
                                                                                    ↓
                          应收发票 ← 销售发货 ← 成品库存 ←──────────────────────────┘
                              ↓
                        收款核销 → 账龄 / KPI → 成本归集 → 毛利
```

围绕这条主线，设计上守住三条原则：

| 原则 | 含义 |
| --- | --- |
| 单一数据源 | 产品、BOM、工艺路线、客户、供应商等主数据全局唯一，各子系统引用而非复制 |
| 状态机驱动 | 每张单据都有明确的状态流转，业务动作即状态迁移，禁止越级跳转 |
| 前端不重复造轮子 | 同一套单据在 Web、桌面端、移动端表现不同，但共用同一后端与同一状态机 |

技术上，后端为一套 Go 服务（Gin + GORM + PostgreSQL + Casbin），向上支撑三个前端：React Web 管理端、Electron 桌面端（承载固件烧录等需要本地串口与外设的能力）、Flutter 移动端（车间现场扫码与报工）。三端共享同一套 API 与权限模型。

## 总体架构

### 分层与公共能力

后端按 `handler → service → repository → model` 分层，所有响应统一为 `{code, message, data}`。几个横切能力在架构层一次性解决：

- **多公司隔离**：业务表统一携带 `company_id`，按公司维度切分数据。
- **数据权限**：四档可见范围 `all > cross_company > company > personal`，权限来源有三处（用户直授、岗位、组织），取其中最高档；由仓储层统一改写查询条件，业务代码不感知。
- **审计字段**：所有模型继承统一基类，自动填充创建人/创建时间/修改人/修改时间，并带软删除。
- **统一单据编号**：各单据类型（销售订单、采购订单、生产工单、质检单、出入库单等）由统一的编号服务按类型 + 周期（不重置/月/季/年）原子取号，避免并发重号。
- **角色与菜单**：菜单树按角色与端（PC / 移动）二次过滤，同一账号在不同端看到不同的功能面。

# 财务系统

财务系统有两种定位方式：一种是独立的总账系统，业务系统把凭证推给它；另一种是**业务财务**——财务数据由业务动作实时产生，财务系统负责归集、核算与呈现。本方案取后者：不做两套账，业务发生即财务发生。

核心构成：

| 模块 | 职责 |
| --- | --- |
| 会计凭证 | 由采购、生产、销售、库存、工资等业务动作自动生成分录，记录来源单据、借贷方与金额 |
| 发票管理 | 销售发票（应收）与采购发票（应付），关联订单与收付款 |
| 收款 / 付款 | 收付分离建模：收款单、付款单与核销记录各自独立，支持部分核销与多单核销 |
| 产品成本 | 按产品归集材料成本、人工成本、制造费用，得出总成本，并保留核算日期的历史版本 |
| 计件薪资 | 由报工数据驱动：计件单价 × 合格数量，形成工资明细，再汇总为工资单 |
| 经营看板 | DSO / DPO / DIO 周转天数、应收应付总额、库存总值、账龄分布与回收概率 |

其中一个设计要点是**成本归集的口径**。产品成本不是简单的采购价，而是材料成本（BOM 用量 × 实际采购价）、人工成本（工序标准工时或计件工资）与制造费用（工作中心小时成本）三者的叠加。工作中心的小时成本在这里与工艺路线打通——这也是"工艺路线不只是排产资料，还是成本模型"的原因。

# 客户关系系统

CRM 承接经营主线的最前端，负责把"一个联系人"逐步变成"一张订单"。设计上区分三类对象：

- **合作伙伴（Partner）**：统一建模客户与供应商，用类型字段（客户 / 供应商 / 两者）区分，避免同一家公司在库中出现两条记录。客户可带等级字段用于差异化政策。
- **联系人（Contact）**：隶属于合作伙伴，支持生命周期标记。
- **线索与商机（Lead / Opportunity）**：同一实体两种形态，线索经转化后成为商机。线索记录来源渠道（网页、电话、邮件、转介绍、手工录入等），商机则携带销售阶段与成交概率。

**销售阶段本身是可配置的主数据**，而不是硬编码枚举——这允许不同业务线定义各自的漏斗：

| 排序 | 阶段 | 默认概率 | 标记 |
| --- | --- | --- | --- |
| 10 | 初步接触 | 20% | |
| 20 | 需求分析 | 30% | |
| 30 | 方案报价 | 60% | |
| 40 | 商务谈判 | 80% | |
| 50 | 赢单 | 100% | 赢单阶段 |
| 60 | 输单 | 0% | 输单阶段 |

阶段带概率，商机落在哪个阶段就有对应的赢率，销售漏斗因此可以直接用于预测。赢单阶段可一键转销售订单，输单需记录原因；商机状态的每次变更进入时间线，形成可追溯的跟进记录。此外还包含销售团队、客户回访等对象。

# 供应链系统

## 销售系统

销售侧的单据链条是：**报价单 → 销售合同 → 销售订单 → 发货单**，与价目表配合完成定价。

**价目表**是定价的核心，采用三表结构：价目表头、明细行、阶梯价。定价时的匹配优先级为：限定条件匹配（限定客户 / 限定销售员 / 限定产品）优于无限制，日期更近者优先，同条件下取最新记录。价目表自身也有状态机（草稿 → 待审批 → 已审批 → 生效 → 失效/作废），并支持版本链——修改不覆盖历史，而是派生新版本，保证已签合同的价格可回溯。

**报价单**支持版本管理（同一条报价多次修订、保留版本链）与一键转订单。状态流转为草稿 → 已发送 → 已接受 → 已过期 / 取消。

**销售订单**是全系统最关键的单据之一，它同时挂着三条状态线：

| 状态线 | 取值 |
| --- | --- |
| 订单状态 | 草稿 → 已发送 → 已确认 → 已完成 / 取消 |
| 开票状态 | 未开票 / 待开票 / 已开票 |
| 发货状态 | 未发货 / 部分发货 / 已发货 |

把开票与发货从订单主状态里拆出来独立跟踪，是因为实际业务中三者并不同步：订单已确认但只发了一半货、货发完了但发票还没开，都是常态。此外订单支持含税/未税切换与税率字段，并保留客户订单号以便与客户侧对账。

**销售合同**独立成单（可从报价或订单生成），支持模板、状态机（草稿 → 已确认 → 执行中 → 已完成 / 取消）与 PDF 导出。

## 采购系统

采购侧链条为：**采购申请 → 采购订单 → 采购收货**，单据之间可直接转换（申请转订单、订单转收货）。

- **采购申请**：需求由人工提出或由 MRP 运算自动生成，状态为草稿 → 已确认（待审批）→ 已审批 → 部分转单 → 已转单 / 取消。
- **采购订单**：状态为草稿 → 已发送 → 已确认 → 已完成 / 取消，并独立跟踪收货状态（未收货 / 部分收货 / 全部收货 / 超收）。
- **采购收货**：状态为待处理 → 待检验 → 已完成。这里有一个关键设计——**收货不是终点，来料检是收货的必经关口**。

订单成本按实际采购价回写，用于财务的成本归集。采购价目表与销售价目表共用同一套定价模型。

# 产品系统

## 产品管理

产品模型分两层：**产品系列（模板）+ 产品（变体/SKU）**。系列承载共用属性（是否可销售、可采购、可生产、追踪方式、硬件平台等），变体承载具体规格。这一层设计直接决定了后续 BOM、库存与价格的粒度。

产品的**分类编码驱动行为**，而不是仅仅用于归类。例如原材料、委外件、标准件、辅料、主控板组件、本体、成品各自对应不同的采购与生产策略——委外件只采购不生产，成品可销售。

产品的**追踪方式**（不追踪 / 批次 / 序列号）是另一个关键开关，它决定了后续库存是否按批次或序列号记账——这个决定必须在产品建好时就做对，事后切换代价极大。

此外还有产品属性与属性值（用于变体维度的自由组合）、产品供应商信息（同一物料的多供应商与采购价）。

## 工艺流程管理

工艺流程由四个对象构成：

| 对象 | 说明 |
| --- | --- |
| 工作中心 | 机器、产线、工作单元、手工工位等类型，带每日工时、产能、小时成本 |
| 工艺路线 | 一套工序的组合，带版本 |
| 工序 | 路线上的一个作业点，引用工作中心 |
| 工序依赖 | 工序之间的先后关系 |

工序层面的设计细节较多：**工序间关系**支持 完成-开始、开始-开始、完成-完成 三种约束；**多工序并行**支持 与、或、异或 三种汇聚方式；工序可标注是否为**质检点**（决定是否在此触发检验）；可设置**良率**与**物料损耗率**（MRP 与成本计算都要用到）；工序还可挂**分支条件**（按质检结果、产品属性或数量区间走不同路径）。

工作中心的小时成本与产能在这里定义，向上服务于排程，向下服务于成本核算。

## BOM管理

BOM 采用**多行 + 版本**的结构：

- **BOM 头**：类型（普通 / 虚拟件）、状态（草稿 → 已确认 → 已完成 / 已废弃）、消耗方式（严格 / 弹性）、齐套策略（全部可用 / 全部预期 / 尽快）。
- **明细行**：组件、用量、损耗率、是否可选。
- **副产品行**：联产品与副产品。
- **版本历史**：修改 BOM 生成新版本，保留完整的版本链——已下达的工单必须能回看当时用的是哪一版。

BOM 的损耗率与工艺路线的良率共同参与 MRP 的需求放大计算。虚拟件（Phantom）的设计用于处理"中间件不单独入库、直接穿透到下级"的场景。

## 报价管理

报价本质上是"产品 + 数量 + 价目表 + 折扣"的一次计算，因此**报价单与销售价目表共用同一套定价引擎**，不另建一套报价逻辑。报价单可带版本（多项报价方案并行比较）、可转订单、可记录有效期；采购侧的报价同样走价目表模型。

# 品质系统

品质系统的设计核心是**把检验嵌入流程，而不是挂在流程旁边**。四类检验分别对应四个不同的触发时机：

| 检验类型 | 触发时机 | 把关对象 |
| --- | --- | --- |
| 来料检测（IQC） | 采购收货时 | 供应商来料 |
| 首件检测 | 当日该工序第一次报工时 | 工序开工首件 |
| 生产抽检（过程 / 巡查） | 报工过程中或人工发起 | 在制品 |
| 成品检测（FQC） | 完工入库时 | 成品 |

## 来料检测

采购收货单的状态里内建了检验关口：收货后进入"待检验"，只有检验通过才能完成入库。系统可按物料配置是否必须检验，避免"该检的没检"。

## 成品检测（全量、抽检）

成品检测支持三种抽样方式：

- **固定数量**：指定固定抽样数；把抽样数设为送检量即为**全量检测**。
- **百分比抽样**：按送检数量的比例抽。
- **AQL 抽样**：按 ISO 2859-1 标准的抽样方案，由批量范围决定样本量与判定数。

AQL 方案是可维护的主数据——按批量区间给出样本字码、样本量、合格判定数（Ac）与不合格判定数（Re）：

| 批量范围 | 字码 | 样本量 | Ac | Re | 检验水平 |
| --- | --- | --- | --- | --- | --- |
| 2 – 8 | A | 2 | 0 | 1 | normal |
| 9 – 15 | B | 3 | 0 | 1 | normal |
| 16 – 25 | C | 5 | 0 | 1 | normal |
| 26 – 50 | D | 8 | 0 | 1 | normal |
| 51 – 90 | E | 13 | 0 | 1 | normal |
| 91 – 150 | F | 20 | 0 | 1 | normal |
| 151 – 280 | G | 32 | 1 | 2 | normal |
| 281 – 500 | H | 50 | 1 | 2 | normal |
| 501 – 1200 | J | 80 | 2 | 3 | normal |
| 1201 – 3200 | K | 125 | 3 | 4 | normal |
| 3201 – 10000 | L | 200 | 5 | 6 | normal |
| 10001 – 35000 | M | 315 | 7 | 8 | normal |
| 35001 – 150000 | N | 500 | 10 | 11 | normal |

## 生产抽检

过程检验挂在工序的质检点上，报工推进到该工序时自动触发；巡查检验则用于不绑定工单的日常巡检。两者共用同一套质检单模型。

## 首件检测

首件检验在报工"开始"时判断：若这是该工序当天的第一次报工，则触发首件检验。首件未通过不允许批量生产——这是防止批量报废最有效的一道闸门。

## 不合格品处理（NCR）

四类检验发现不合格都汇入同一条 NCR 流程，形成闭环：

```
待确认 → 品质评审 → 生产评审 → 采购评审 → 待判定 → 待判责 → 已完成
```

设计要点有三：**评审是串行的多角色会签**，任一环节驳回都退回"待确认"重新走；**处理方式**包含让步接收、返工、重制、退货、挑选，其中返工与重制会**反向生成新的生产工单**并双向关联，保证不合格品的处置真实进入生产计划；**判责**区分内部责任与外部责任，并按比例分摊，直接支撑供应商考核与内部质量改进。

# 仓储系统

## 仓库管理

库存模型借鉴了成熟的 ERP 设计，分为四层：

| 层 | 说明 |
| --- | --- |
| 仓库 | 支持默认库位（收货、发货、报废、不良品等） |
| 库位 | 树形层级，区分内部/客户/供应商/生产/盘点/报废/不良品等类型，并标记是否可存放 |
| 批次 / 序列号 | 追踪方式由产品决定，记录生产日期、有效期与来源 |
| 库存量 | 按产品 + 库位 + 批次记账，区分在手数量与预留数量 |

**出入库动作统一建模为拣货单 + 库存移动**：拣货单区分入库、出库、内部调拨三类，各有独立的状态流转（草稿 → 等待 → 已确认 → 已完成 / 取消）；每一次库存变化都生成一条库存移动记录并标注来源单据（销售、采购、生产、盘点、内部），使库存可以追溯到任何一张原始单据。此外还有库存盘点（全盘 / 部分盘 / 循环盘）、库存调拨与报废单。

**栈板管理**用于承载"一板一料"的现场约束：栈板分虚拟与实体两类，绑定库位，限制一块栈板只放一种产品，在完工入库与出入库环节使用。

![库位管理：左侧库位树形结构，右侧库位卡片，标注库位类型与是否可存放](/images/blog/production-management-system/location-tree.png)

## 储位管理

储位即库位（Location），采用**树形层级**结构：可无限分级，记录层级与路径，便于表达"仓 → 区 → 排 → 架 → 位"这类物理结构。库位有类型语义（内部、客户、供应商、生产、盘点、报废、不良品、虚拟）与两个关键标记——是否可存放、是否为库位节点。收货默认进"来料待检区"、报废进"报废区"，都是靠库位类型驱动，而不是靠硬编码。

## 地图管理

地图管理的目标是让仓储空间**可计算**：把仓库、库位与栈板映射到一张二维/三维平面图上，给每个库位一个坐标，从而支持：

- 库位占用情况的可视化（空置 / 占用 / 满仓）
- 物料在库内的定位与最优取货路径计算
- 栈板与库位的空间约束校验（尺寸、承重、堆叠层数）
- 与 AGV 调度系统共享同一张地图，作为机器人的运动与定位底图

设计上，地图是库位的**呈现层**而非数据源——库位仍是唯一事实来源，地图只增加坐标与几何属性，这样即便地图未启用，仓储业务也能照常运行。

## AGV机器人调度系统

AGV 调度系统负责把"物料的搬运需求"翻译成"机器人的任务与路径"。它向上对接仓储系统的出入库与移库需求，向下对接机器人本体与调度内核。设计上分为三层：

| 层 | 职责 |
| --- | --- |
| 任务层 | 接收搬运需求（来源库位 → 目标库位 + 物料 + 优先级），生成搬运任务，跟踪执行状态 |
| 交通层 | 路径规划、多车避让、路口与窄道互斥、死锁预防与恢复 |
| 设备层 | 机器人注册与心跳、电量与故障状态、任务下发与状态回报 |

几个关键设计点：**任务与库位解耦**——搬运任务只描述起止库位与物料，具体由哪台车执行由调度层决定；**地图共享**，调度系统与仓储地图管理使用同一份库位坐标，避免两套坐标导致的定位漂移；**异常回落**，机器人在途故障时任务挂起并触发异常系统，由人工介入或重新派单；**人工与自动混合**，AGV 未覆盖的库位仍走人工拣货，两套流程共用同一张出库单。

# 生产制造系统

## 生产计划

生产计划是"要做什么"的汇总层，支持日、周、月、季度四种粒度，来源可以是销售订单、MRP 运算结果、出货计划或人工录入。状态为草稿 → 已确认 → 已下达 → 已完成 / 取消。计划确认时可指定工艺路线，下达后即生成生产工单。

## 生产排程

排程解决"什么时候做、在哪做"。设计上分两个层次：

- **粗排**：按工作中心的日产能与工时，把计划分配到时间段与工作中心，回答"这条线这周排得下吗"。
- **细排**：基于工序之间的依赖关系（完成-开始等约束）、工作中心的产能与班次日历，计算每个工序的计划开始/结束时间，回答"这道工序几点开工"。

产能约束下的排程本质是一个有限产能调度问题。工程上通常从正向/反向有限产能排程入手，再叠加优先级（紧急 / 高 / 普通 / 低）与交期倒排。排程结果落在工单与工序的计划时间字段上，供报工与进度跟踪使用。

## 物料需求分析

MRP 是整个系统里计算最密集、也最能体现"系统替代人对账"的部分。核心公式：

```
净需求 = 销售订单需求 × BOM 用量 − 现有库存 − 在途量 + 安全库存
```

设计要点：

- **逐层展开 BOM**：从成品向下递归展开到所有层级，并限制最大展开层级防止失控。
- **良率与损耗参与放大**：因为下游良率 < 100%，上游投料量需按需求量 ÷ 良率逐级放大；BOM 行的损耗率同理。
- **批次与在途要看得见**：不仅要扣现有库存，还要扣已下达未到货的采购在途量，否则会重复下单。
- **结果按属性分流**：展开后的需求按产品是否自制拆分——自制件生成生产建议，采购件生成采购申请。
- **可定时运行**：支持手工触发、定时任务触发与事件触发，运算留痕（记录每次运行的时间、参数、涉及产品数与建议数），便于回溯。

![MRP 物料需求计划：展开层级、安全库存、含在途与自动生成单据等运算参数](/images/blog/production-management-system/mrp-run.png)

## 生产领料

领料是把 MRP 算出来的物料需求变成实际出库。设计上，领料不是一张孤立单据，而是**工单与库存之间的桥**：按工单展开的用料需求（来自 BOM 与工艺路线的工序用料）生成领料明细，走库存出库流程并过账。支持整单领料与按工序分段领料，实际领用量与理论用量可对比，差异回流到成本核算。

![出库管理：出库类型区分生产领料等场景，并标注来源单据](/images/blog/production-management-system/outbound-list.png)

## 生产报工

报工是车间数据的入口，也是成本与工资的来源。设计要点：

- **三段式状态**：报工记录走 草稿 → 已开始 → 已完成，开始与结束分别打时间戳，工时为两者之差；"开始"这一步同时承担触发首件检验的职责。
- **按工序报工**：报工挂在工序（工单）而非整单上，合格数量、报废数量、工时、员工逐条记录，支持多人多工序并行。
- **异常自动联动**：报废数量或不合格数量大于零时，自动发起 NCR，把"现场问题"与"质量流程"打通，而不需要班组长另外开单。
- **数据回流**：报工的合格数量驱动工单进度与完工入库，工时与数量驱动计件工资与成本核算。

![报工记录：按生产工单 + 工序 + 工作中心记录合格数量、报废数量、工时与员工](/images/blog/production-management-system/productivity.png)

## 委外报工

委外（外协）的建模思路是**把它当作一种特殊的采购 + 一种特殊的生产**：发料给供应商是一次出库，供应商交货是一次收货，加工费按委外订单结算。设计上包含委外订单、发料单、收货单与委外报工，报工口径与自制报工一致（合格数量、报废数量、工时），以便把委外产能也纳入统一的进度与成本视图。关键差异在于**料件所有权的转移需要留痕**：发出多少、回收多少、损耗多少，必须能对账，否则委外损耗会成为成本黑洞。

## 计件薪资

计件薪资由报工数据直接驱动，公式是：

```
计件工资 = Σ(工序计件单价 × 合格数量)
```

计件单价按 **产品 + 工艺路线 + 工序 + 工作中心** 维度维护，因此同一道工序在不同产品上可以有不同单价。工资单汇总基本工资与计件工资得出实发，状态为 草稿 → 已确认 → 已发放 / 取消。这一设计的意义在于：**工资不再依赖车间台账人工统计**，报工一提交，工资即可计算，且可追溯到每一笔工时与数量。

## 出货计划

出货计划是生产与销售的衔接点：它把销售订单的交付需求转成具体的发货安排（发什么、发多少、什么时候发、走哪个仓库），并可以反向作为生产计划的输入来源。状态跟踪与销售订单的发货状态联动（未发货 / 部分发货 / 已发货）。

# 任务管理和创新中心

这一模块解决的是"人"的协同，与前面的"物"的主线并行。

## 创新项目

员工可提出创新思路，提交后进入审核流程；审核通过后给予奖励并可将思路转为立项。设计要点是把创新做成**可闭环的提案系统**：提案 → 评审 → 采纳/驳回 → 奖励发放 → 落地跟踪，每一步都有责任人与时限，避免提案石沉大海。

## 任务

任务带**时效与奖惩**：任务有明确的截止时间、责任人、验收标准，逾期触发提醒与考核。任务可由人工创建，也可由其他模块触发（如异常处理、NCR 判责、创新提案落地）自动生成，从而把跨部门的临时协作也纳入统一跟踪。

## 会议

会议模块的设计目标是**让会议产生可追踪的产出**：会议主题自动记录，会议中形成的决议自动关联并生成任务，任务再进入上面的任务系统。这样"会上说了什么"与"会后做了什么"之间不再断链。

# 异常系统

异常系统的定位是**对主流程的兜底**——凡是打断正常生产、需要人立即介入的事件，都走这条通道。设计流程：

| 步骤 | 说明 |
| --- | --- |
| 1. 异常触发 | 由设备报警、质检不合格、报工停滞、库存差异、交期延误等事件自动触发，也可人工上报 |
| 2. 指派处理人 | 系统管理员（或按规则自动）选择紧急处理人，明确责任与响应时限 |
| 3. 执行反馈 | 处理人反馈处理进展与结果，过程留痕 |
| 4. 异常结案 | 确认异常消除后结案，记录根因与处理措施 |
| 5. 损失统计 | 统计异常造成的停机时长、报废数量、延误交期与金额损失，形成可分析的数据 |

设计上有两点值得强调：**异常要能自动触发**，如果依赖人工上报，异常系统就会退化成一张表单；**损失必须量化**，只有把异常换算成金额与时长，才能进入经营分析，成为改善的依据而非事后追责的工具。

# 小结

把这套系统放在一起看，它的设计逻辑其实只有一句话：**让单据在一条主线上自然流转，让每个业务动作都留下可追溯、可核算的痕迹**。

- 主数据（产品、BOM、工艺路线、客户、供应商）是唯一事实来源；
- 单据靠状态机约束，靠来源字段串联，靠编号服务识别；
- 品质检验嵌入流程而非外挂，不合格品处置闭环回到生产；
- 财务不做第二套账，成本与工资由业务数据实时产生；
- 异常与任务系统兜住主线之外的意外，并把损失量化。

做到了这些，MES 就从一个"记录系统"变成了一个"驱动系统"——它不只是把人的动作记下来，而是在决定下一步该做什么。
